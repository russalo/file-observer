## 1. Motivation

In an agentic loop the pre-read scan is also an **audit artifact**: a small, persistable record of *what was screened, under what config*, that an orchestrator keeps for a trail. u/blah_mad's sharper point: fo proves the file surface, the orchestrator proves what happened next — but "you end up with two honest logs that almost meet." The fix is to make the **observation→decision bridge explicit**: one clear **receipt id** the downstream read/skip log attaches, instead of the consumer stitching `checksum_sha256` + `manifest_checksum` + path together by hand.

**The honest boundary (charter):** the one field requested that fo *cannot* own is "did the agent read or skip the file" — fo observes the file, it never sees the downstream decision. fo's job is to make its record trivially correlatable, not to record the decision. Observe-don't-interpret; never a verdict.

## 2. What already exists

The receipt is **a projection of existing observations**, not new data — a per-file record + the manifest envelope already carry: `context.scanner_version`/`logic_version`/`schema_version`, `checksum_sha256`, `size_bytes`, `mime_type`, `safety_flags`, the lexicon vector's `dictionary_id`, `manifest_checksum`, and (optional) the HMAC `manifest_signature` + `previous_manifest_checksum` chain. v1.40 added `path_id` (a fo-derived, free-text-free path handle). So this release surfaces a **compact projection + one new derived id** — no new observation or judgment.

## 3. Design

A new **`--receipt`** output mode (CLI + MCP), emitting a compact per-file audit record + a manifest-level envelope. It is a **projection of the built manifest** (runs after `manifest_checksum` exists), so the receipt id can bind to the scan with no circularity.

- **Per-file receipt** (the compact trusted subset): `receipt_id`, `path_id`, `checksum_sha256`, `size_bytes`, `mime_type`, `safety_flags`, `dictionary_id` (when a lexicon ran), and a lexicon-hit summary (`lexicon_match` presence + per-category counts — body + metadata, all fo-derived).
- **Envelope:** `scanner_version`/`logic_version`/`schema_version`, `manifest_checksum`, `manifest_signature` (when signed), `scan_id`, `generated_at`, `receipt_doc_version`.
- **`receipt_id`** = a deterministic per-file id binding **(scan + path + content)**: `sha256` over a canonical, unambiguous preimage of `manifest_checksum`, the relative path, and `checksum_sha256`. Tamper-evident: change the file content → `checksum_sha256` → id; change the scan → `manifest_checksum` → id. **Independently verifiable** (a consumer recomputes it from those three inputs). This is the join key a read/skip log references verbatim.
- **Safe by construction:** every receipt field is fo-derived (numbers/hashes/enums/flags) — the raw `path` is NOT emitted (it's file-derived; the orchestrator already has the path it asked fo to scan, and `path_id` correlates back). So a receipt is safe to feed a model *and* to persist as an audit record.

## 4. Preimage (avoid the v1.38 `dictionary_id` collision lesson)

`dictionary_id` (v1.38) originally used a `|`-joined preimage that could collide; it was fixed to canonical JSON. The `receipt_id` preimage MUST be unambiguous from the start — a length-prefixed or canonical-JSON encoding of `(manifest_checksum, rel_path, checksum_sha256)` so no two distinct triples share a preimage. Documented in PUBLIC_CONTRACT so a consumer can recompute it.

## 5. Versioning

- **SCANNER 1.41.0→1.42.0.**
- **LOGIC 1.22.0 UNCHANGED, SCHEMA 1.23 UNCHANGED** — `--receipt` is a projection of the existing manifest; the DEFAULT manifest is byte-identical (the v1.26 `scan()` / v1.28 `--stdout` / v1.37 MCP / v1.40 `--trusted-only` front-door precedent).
- **New `receipt_doc_version`** (starts at `1`) versions the receipt envelope shape as a committed build-time interface (the `schema_doc_version` precedent), so a consumer can pin it.

## 6. Persistence (documented, not built)

Made explicit in the docs (a #133 ask): via **MCP** the receipt is returned to the caller — the server is stateless/read-only and persists nothing itself; via the **CLI** `--receipt` writes to a file or `--stdout`. fo never records the decision; the orchestrator staples the `receipt_id` to its own read/skip log.

## 7. Decisions (LOCKED 2026-07-12, Russell — all recommended leans)

- **D1 = (a) `--receipt` projection** (front-door; LOGIC/SCHEMA frozen; the scan-bound `receipt_id`, no circularity). A FileRecord `receipt_id` field is a deferred add-on (§10).
- **D2 = preimage** `manifest_checksum` + relative path + `checksum_sha256`, canonically/length-prefix encoded (collision-free, recomputable).
- **D3 = `path_id` only** in the receipt (safe, fo-derived); the raw path is NOT emitted.
- **D4 = include the lexicon body+metadata hit summary** — the receipt says what was screened AND what it found.
- **D5 = a `receipt: bool` param** on the existing MCP `scan_file`/`scan_directory` tools (no new tool).

Original recommendations retained below for the record.

## 7-orig. Decisions (original, for the record)

- **D1 — surface.** (a) a `--receipt` **projection** (front-door; LOGIC/SCHEMA frozen; the `receipt_id` can bind `manifest_checksum` with no circularity) vs (b) a `receipt_id` **field in every FileRecord** (SCHEMA additive + LOGIC values-move; but a FileRecord field *cannot* include `manifest_checksum` — circular — so its id would bind only path+content, not the scan). *Recommend (a)* — it's what #133 describes, it's frozen, and it delivers the scan-bound id blah_mad asked for. (b) as an add-on later if a consumer wants the bridge key inside the full manifest.
- **D2 — `receipt_id` preimage.** Confirm the inputs — `manifest_checksum` + relative path + `checksum_sha256` — and the canonical encoding (length-prefixed / JSON) so it's collision-free and independently recomputable.
- **D3 — path in the receipt.** `path_id` only (safe, fo-derived — *recommended*) vs the raw `path` (human-audit-friendly but file-derived/attacker-controllable). *Recommend `path_id`* to keep the receipt safe-by-construction; a consumer wanting the human path already has it (it chose what to scan) and can map via `path_id`.
- **D4 — receipt contents.** Confirm the compact field set (§3). Include the lexicon body+metadata hit summary (v1.38/v1.41) so the receipt captures the screening result, not just identity?  *Recommend yes* — the receipt should say *what was screened AND what it found*.
- **D5 — MCP exposure.** A `receipt: bool` param on `scan_file`/`scan_directory` (return the receipt instead of / alongside the full record) + a `scan_receipt` tool? *Recommend a `receipt` param on the existing tools* (smaller surface than a new tool).

## 8. Testing (falsify-first, `test_v1_42.py`)

- **Determinism + verifiability:** the same scan of the same file → the same `receipt_id`; a consumer recomputing `sha256(preimage)` from the three inputs gets the emitted id.
- **Tamper-evidence:** changing the file content (→ `checksum_sha256`) OR the scan (→ `manifest_checksum`) changes the `receipt_id`.
- **No collision:** two files with swapped path/hash components do NOT share a `receipt_id` (the canonical-preimage guard).
- **Safe by construction:** no file-derived free-text string appears in a receipt (raw path absent; only `path_id`).
- **Default byte-identical:** `--receipt` off ⇒ manifest unchanged; LOGIC/SCHEMA frozen.
- **MCP:** the `receipt` param returns the compact record; the manifest checksum matches a CLI `--receipt`.
- Version axes: SCANNER 1.42.0, LOGIC/SCHEMA unchanged, `receipt_doc_version` 1.

## 9. Review

Full 4-leg (a new output surface consumed for audit + safe to feed a model): leg-1 in-house swarm (preimage collision-safety; does any file-derived string leak into a receipt?; is the id genuinely tamper-evident?), leg-2 cross-model, leg-3 sweep (default byte-identical), leg-4 PR bots. No measure-first (this is a format/API design, not a detection feature — the requirement is the r/mcp thread, not a corpus gap).

## 10. Non-goals / deferred

- **Recording the read/skip decision** — permanently fo's non-goal (§1 boundary).
- **A `receipt_id` FileRecord field** in the full manifest — D1(b), a later add-on if wanted.
- **Signing the receipt independently** — the existing `manifest_signature` already covers integrity; a per-receipt signature is out of scope unless a consumer needs a detached receipt.
