## 1. Overview

### 1.1 Purpose

Close the two remaining residuals from the post-v1.5 PDF arc, surfaced by re-scanning the `corpora_infra` corpus 2026-06-07 against the live v1.11.0 build:

| Residual | Files in corpora_infra | What's blocked | Cause |
|---|---|---|---|
| **(A)** Owner-permission-locked encrypted PDFs | 2 (`2025-standard-plans-locked.pdf` + `2025-standard-plans-errata-no1-locked-a11y.pdf`, Caltrans 2025 specs) | `page_count`, `producer`, all `/Info` fields | pypdf can `decrypt("")` but extraction-permission flags are set; pypdf without the optional `cryptography` package can't decrypt AES-256/V5 at all (these PDFs almost certainly use V5) |
| **(B)** Stdlib decoder uncompressed-xref-stream gap (PIVOTED — see §6.1) | 42 PDFs on corpora_infra (sample: `WSDOT-standard-plans/C80.20-01_e.pdf`) | `page_count` (stdlib-path tier-2 returns None) | `_pdf_xref_stream_map` assumes Flate-compressed xref streams; PDFs that emit uncompressed xref streams (no `/Filter`) are skipped by `_pdf_stream_body`'s inflate path. v1.8's "exotic predictor" framing was theoretical — the actual corpus residuals are no-filter, not predictor-related. |

Both residuals are **strictly additive** — v1.12 fills nulls; never changes a v1.8/v1.11-set value. The recovery is gated by the pypdf-oracle parity test (`TestStdlibOracleParity`), same falsify-first contract that gated v1.8.

**Construction-engineering relevance (Wayne-K).** Caltrans 2025 spec PDFs are exactly the shape an infrastructure-data ingestor sees in the wild: owner-locked, copy-permission-stripped, accessibility-enhanced. The pattern generalizes beyond Caltrans — DOTs and engineering firms commonly distribute owner-locked PDFs. v1.12 makes the observation layer continue to function on this realistic content shape.

### 1.2 What v1.12 is NOT

- **NOT a new specialist.** PDF specialist code is the same surface; we extend two existing helpers (`_pdf_via_pypdf` and `_png_predictor_undo`).
- **NOT a new vector.** No new manifest blocks; no new vector identity digests.
- **NOT a behavior change for non-residual PDFs.** v1.11 manifest output on the 651 non-residual PDFs in corpora_infra is byte-identical post-v1.12. The two residuals are the only files where any field changes.
- **NOT a Sentinel-coupled release.** Intentional. Respects [[soft-contracts-alpha-phase]] + [[positioning-watch-docs]]. Release notes stay dry — "PDF residual closure" not "Sentinel readiness."
- **NOT stdlib decryption.** Implementing PDF encryption algorithms (V1-V5) in stdlib is substantial and out of scope. Encrypted PDFs stay on the pypdf path; the stdlib path nulls on encryption (v1.8 contract, unchanged).
- **NOT text/content extraction from encrypted PDFs.** We observe metadata only (the same observe-only principle that already extracts `producer`/`title`/etc. on unencrypted PDFs). Page content, annotations, attachments — out of scope.
- **NOT a `cryptography` mandatory dependency.** Core install profile is unchanged. `cryptography` is bundled into an existing or new optional extra (§3.2).
- **NOT an external positioning expansion.** README/PUBLIC_CONTRACT.md untouched. PyPI long-description untouched. The new provisional field (if §3.4 lands) shows up in HISTORY.md + the SCHEMA-bump and nowhere else.

### 1.4 Rescope from the original framing

CLAUDE.md and the v1.10 release notes carried the line **"2 empty-password-encrypted (conservative `not encrypted` gate)"** as the v1.8 residual. The 2026-06-07 corpus re-scan corrected the premise:

1. The `not encrypted` gate **is already relaxed** — `_pdf_via_pypdf` already calls `reader.decrypt("")` (scanner.py:3354).
2. The 2 residual PDFs are **not empty-password-user**, they are **owner-permission-locked**: AES-256/V5 encryption with extraction-permission flags set, requiring (a) the `cryptography` package for decryption *at all* and (b) a permission-override decision for metadata reads (§3.1).
3. The framing "tier-2 `/Info` via stdlib" doesn't address a real consumer-facing gap: the 49 unencrypted classic-xref PDFs in corpora_infra with `producer=null` simply **have no `/Info` dictionary at all** (pypdf reads them and returns `metadata=None`). There is nothing to extract — no code change recovers them.

The actual v1.8 residuals were (A) above + (B) the predictor gap that v1.8 RFC §7.1 explicitly banked. CLAUDE.md will be updated post-v1.12 to reflect the corrected residual story (a separate documentation patch, not part of this RFC's scope).

This rescope is itself a vindication of [[feedback_falsify_dont_confirm]]: the builder's documentation framed the residuals one way; the corpus reality is different; the right move was to re-scan before drafting, not to draft on the documentation premise.

## 3. The central decisions (UNRESOLVED, for approval)

### 3.1 Observe-only vs. respect-the-lock for owner-permission-locked PDFs

The design-shape question. When a PDF owner has set extraction-permission flags (`!can_extract`, `!can_modify`), what does file-observer do?

- **(a) Respect the lock — skip metadata extraction.** Owner intent: "do not extract." File-observer respects it. Result: owner-locked PDFs continue to null on producer/page_count/etc. — same as today.
- **(b) Observe regardless — extract metadata, ignore permission flags.** File-observer is an *observer*. The same principle that lets us read filesystem-restricted files (we already do; we observe what we can see). Metadata is read-only, no content extraction, no copy/paste of locked content. Result: owner-locked PDFs get the same metadata treatment as unencrypted PDFs.
- **(c) Observe with transparent disclosure — extract, but record what we did.** Same as (b), plus a new provisional `pdf.permission_flags_bypassed: bool` so downstream consumers can see when the owner's flags were overridden. Builds on v0.7's `safety_flags` precedent (we already disclose macros / JavaScript / external references in PDFs — disclosure of permission-bypass is the same shape).

**Prior recommendation: (c).** File-observer's mission is observation, and metadata is observable by definition (the bytes exist on disk and a PDF reader interprets them). Permission flags are an instruction to a *renderer*, not a deterministic input constraint on an observation tool. (a) loses signal an observer should have; (b) loses the disclosure that a careful consumer would want. (c) preserves the observer mission AND surfaces the override explicitly — a consumer running corpus analytics on a mixed dataset can filter on the field to separate owner-locked from owner-open metadata if they care.

**Risk to evaluate:** does (c) create a positioning attack surface? A bad actor could frame "file-observer extracts metadata from owner-locked PDFs" as a feature designed to bypass owner intent. **Counter:** we already extract metadata from filesystem-restricted files (we just observe what we can read); we already extract Office macros' presence; the README anchor is "deterministic observer." Adding an explicit disclosure field is the cleanest defense. **Decision belongs to Russell.**

### 3.2 How is `cryptography` delivered?

The `cryptography` package is required for pypdf to decrypt AES-256/V5 PDFs (which the Caltrans 2025 specs almost certainly use — V5 is the modern default for accessibility-enhanced PDFs).

- **(a) Required dep for v1.12.** Adds ~5 MB to the install. Decision: core gets bigger.
- **(b) Bundle with the existing `[pdf]` extra.** `pypdf` already lives there; adding `cryptography` extends the same opt-in. Users who installed `file-observer[pdf]` for v1.8 see the upgrade for free; users on core stay on core.
- **(c) New extra `[pdf-crypto]`.** Three-tier install: core / `[pdf]` (page_count) / `[pdf-crypto]` (encrypted PDFs). Most granular; fragments the install matrix.

**Prior recommendation: (b).** The `[pdf]` extra already exists; users opted in for the v1.8 page_count benefit. Adding `cryptography` to it extends the value of the same opt-in (more PDFs covered) without fragmenting the install. Users who care enough to install `[pdf]` almost certainly want owner-locked coverage too. (c) is the most "pure" but trades simplicity for an install-matrix tax that no consumer has asked for.

Side note for the install profile: `cryptography` ships binary wheels for all major platforms (manylinux / macOS / Windows). The same install-profile audit that approved `pypdf` in v1.8 applies — no new platform-dependence concerns.

### 3.3 Stdlib xref-stream gap target (PIVOTED 2026-06-07)

**Pivot record.** The original §3.3 framed the v1.8 stdlib gap as "PNG predictor coverage (avg / paeth / TIFF)." The §6.1 measurement (`scratch/measure_predictor_gap.py`) returned **0 predictor-gap PDFs on corpora_infra** — the v1.8 RFC's "~12% gap on exotic predictors" comment was theoretical or from a different corpus. The actual 43 stdlib nulls in our corpus are:

- **42 PDFs** with **uncompressed xref streams** (no `/Filter` in the xref-stream dict — raw bytes per `/W` widths)
- **1 PDF** with a Flate-inflate edge case (out of scope here; one-off)

Sample uncompressed-xref PDFs: `WSDOT-standard-plans/C80.20-01_e.pdf` and 41 others across the state-DOT spec mirror. Many engineering-spec PDFs apparently skip xref-stream compression — common shape in the construction target.

**Decision options after pivot:**

- **(a) Support uncompressed xref streams (no-filter path).** Extend `_pdf_xref_stream_map` (or its caller `_pdf_stream_body`) to handle the case where the xref-stream dict has no `/Filter` entry — process raw bytes directly via the `/W` field widths, no decompression. Closes the 42-PDF residual on corpora_infra.
- **(b) Original predictor extension (avg/paeth/TIFF).** Implement against the theoretical gap, knowing the corpus has zero such PDFs today. YAGNI by the measurement.
- **(c) Both (a) + (b).** Maximum stdlib robustness, but (b) is implementing against an empty target set.

**Recommendation: (a).** The corpus has spoken; the measured gap is no-filter, not exotic predictors. Predictor extension is the wrong work for v1.12-B — it would burn code complexity against a non-residual. The pivoted (a) is also *simpler* than the original (no decompression at all; no filter undo); risk is correspondingly lower.

**Bounds discipline carries forward.** Same `_safe_inflate` / `PDF_INFLATE_CAP` / `columns` discipline applies — the no-filter path MUST bound the raw-byte read by the xref-stream length declared in the dict (`/Length`) and MUST validate `/W` widths and `/Index` ranges the same way the Flate path already does. The no-filter path skips decompression but inherits every other guard.

**The 1 inflate-failed PDF** stays null — out of scope for v1.12 (one-off; investigate later if recurring).

### 3.4 New provisional field — `pdf.permission_flags_bypassed`?

If §3.1 resolves to (c) — observe-with-disclosure — a new provisional field is needed.

- **(a) Yes — add `pdf.permission_flags_bypassed: bool`.** Per-file, indicates the extraction-permission flags were set AND we extracted metadata anyway. Defaults to `false` for unencrypted/no-flags PDFs. SCHEMA 1.8 → 1.9.
- **(b) No — extract silently.** Same outcome (metadata extracted) but no disclosure surface. SCHEMA unchanged.

**Prior recommendation: (a).** Coupled to §3.1(c). The v1.10 intake stance was "be liberal admitting cheap observe-only provisional fields"; this field is cheap (one bool, derived directly from `reader.permission_flags`), it has a clear consumer story (corpus analytics filtering owner-locked vs owner-open), and the disclosure-as-defense argument from §3.1 needs it to mean anything. Without disclosure (option b) we have observation without transparency, which is exactly the positioning attack surface §3.1 worried about.

If §3.1 resolves to (a) — respect-the-lock — this decision is moot (nothing to disclose).

## 4. Implementation outline

(Brief — full implementation post-approval.)

### 4.1 Owner-locked decode path (decision §3.1(c) + §3.2(b) + §3.4(a))

Extend `_pdf_via_pypdf` (scanner.py:3333):

```python
if getattr(reader, "is_encrypted", False):
    try:
        result = reader.decrypt("")
    except Exception:
        return None
    if result == 0:                    # decrypt failed (real password needed)
        return None
    # check permission flags AFTER successful decrypt
    perms = getattr(reader, "user_access_permissions", None)
    out["permission_flags_bypassed"] = (
        perms is not None and not perms.extract
    )
```

Add a smoke test that imports `cryptography` and confirms AES-256/V5 decrypt path is available:

```python
def _pypdf_can_decrypt_aes256() -> bool:
    try:
        import cryptography  # noqa
        return True
    except ImportError:
        return False
```

When `cryptography` is absent AND the PDF uses AES, log a structured `ErrorRecord` (`pdf_encryption_unsupported`) and null the fields — never crash.

### 4.2 Uncompressed xref-stream support (decision §3.3(a) — PIVOTED)

Extend the xref-stream decode path so it doesn't require Flate compression. Either:

- Modify `_pdf_stream_body` (scanner.py — the inflate caller) to short-circuit when the stream dict has no `/Filter` entry, returning the raw stream bytes.
- Or modify `_pdf_xref_stream_map` (scanner.py:3186) to accept already-uncompressed bytes when the dict signals no filter.

The first approach is cleaner — `_pdf_stream_body` already reads the raw stream bytes; it currently always inflates. Adding a `/Filter` presence check before inflating is a small change with no impact on the existing Flate path:

```python
# Inside _pdf_stream_body, after locating the stream bytes:
if b"/Filter" not in stream_dict:
    # No compression — raw bytes through (bounded by /Length declared in dict)
    return stream_dict, raw_bytes[:declared_length]
# Existing Flate path:
inflated = _safe_inflate(raw_bytes)
...
```

Bounds discipline: the no-filter path MUST respect the declared `/Length` (don't read past). All downstream guards in `_pdf_xref_stream_map` (`/W` validation, `/Index` ranges, the `PDF_XREF_PREV_HOPS` cap) apply unchanged.

### 4.3 New provisional field (decision §3.4(a))

If §3.4 is (a): add `permission_flags_bypassed: bool` to the PDF specialist metadata block, default `false`. Surface it through the existing pypdf path; stdlib path always reports `false` (stdlib doesn't decrypt). SCHEMA 1.8 → 1.9; chatlog/provenance/preservation method_versions unchanged.

### 4.4 The pypdf method_version bump

`pdf.method_version` (current: implicit, tracked in the v1.8 pypdf path) → +1 if §3.4 lands (field surface change). Unchanged if §3.4 is (b).

### 5.3 The bounded-observation discipline carries forward

Per v1.8.1's lesson — the bounded-observation contract (`_safe_inflate`, `PDF_INFLATE_CAP`, `columns < 1 or columns > len(raw)`, per-file ErrorRecord, `_is_safe_zip_entry`) MUST be carried into every new code path:

- The uncompressed-xref path MUST respect the declared `/Length` and MUST NOT read past it (an attacker `/Length` larger than the actual stream bytes is bounded by the existing `endstream` locator).
- All existing `/W` / `/Index` / `/Prev`-hop guards apply to uncompressed xref streams as they do to Flate-compressed ones.
- The encrypted-decode path MUST NOT raise on a malformed encrypted PDF — `try/except` returning None.
- An ABSENT `cryptography` package on an AES-encrypted PDF MUST produce a structured ErrorRecord, not a crash.

A new red-team round at v1.12.1 is recommended after ship (the same discipline that caught v1.8 → v1.8.1's six findings). The encrypted-decrypt + uncompressed-xref paths are two new code surfaces both worth targeted adversarial inputs.

## 8. Out of scope

- **Stdlib decryption** — implementing PDF crypto V1-V5 in stdlib is substantial; pypdf path covers it, stdlib stays null on encrypted PDFs (v1.8 contract preserved).
- **PDF text/content extraction** — file-observer is the observation layer, not an OCR/extraction tool. The metadata fields we extract are the same set v1.8 already extracts; v1.12 only changes *which PDFs* we can extract them from.
- **Real-password (non-empty) PDF decode** — if `reader.decrypt("")` returns 0 (failed), we null cleanly. We MUST NOT prompt for, accept, or store passwords.
- **Anything chatlog-shaped** — `CHATLOG_SPEAKER_LABEL_RE` and the chatlog vector family are alpha-locked (see [[soft-contracts-alpha-phase]]); v1.12 doesn't touch them.
- **Promotion of v1.11 / v1.10 provisional fields to stable** — promotion pass deferred; v1.12 is purely additive PDF work.
- **Predictor coverage extension (avg/paeth/TIFF)** — measured to have zero corpus impact (§6.1); deferred indefinitely. The code framing "scoped out, never wrong" in `_png_predictor_undo` stays as-is. Re-evaluate if a future corpus (post-Wayne-K scan of a new ingestor) shows non-zero predictor-gap PDFs.
- **Stdlib decompression for non-Flate filters** (LZW, ASCIIHex chains, CCITTFax, etc.) — outside the v1.12 scope; the uncompressed-xref pivot addresses the actual corpus residual.
- **`--watch` improvements** — positioning lock; no external `--watch` surface expansion.
- **EXIF / CAD / word-twisting candidates** — sweep-side, separate cadence.

## 9. Open questions

These do not block approval — flagging for record.

1. **Is `cryptography` portable enough?** It ships binary wheels for manylinux / macOS / Windows; should be fine. If a future platform (e.g. termux, alpine without compatible wheels) hits issues, the optional-extra structure means it gracefully degrades (encryption path nulls, structured ErrorRecord, no crash).
2. **Should the ErrorRecord for "cryptography absent + encrypted PDF" be promoted to a top-level field?** Currently `pdf.parser="none"` covers it implicitly. A dedicated field would surface the install-config issue more explicitly. Lean: no — `parser="none"` + ErrorRecord is enough for now.
3. **Should v1.12.1 do a red-team pass on the new encryption path?** The v1.8.1 pattern (a red-team round caught 6 bounded-observation gaps) is reusable here. Owner-locked PDF parsing is an attack-adjacent surface (a malicious owner-locked PDF could try to exploit the decrypt path). Lean: yes — a v1.12.1 red-team round is appropriate after v1.12 ships, scoped to the new code paths.

## 12. Leg-1 review patch (2026-06-07) — pre-PR critical fixes

### 12.1 The five critical bugs

### 12.2 The design-level fix (§12 of the leg-1 review)

The original §3.4 added `pdf.permission_flags_bypassed: bool` as a new pdf-namespaced provisional field. Leg-1 review #12 caught this was at the wrong altitude: it hard-codes "extract was the bypassed bit AND it was PDF" into the schema. The natural home is `FileRecord.safety_flags: list[str]` — the stable cross-format disclosure surface since v0.7 (`has_javascript`, `has_macros`, `has_ole_objects`, `has_external_references`). v0.7 already paid this design tax.

**Patch:** the disclosure now lands on `FileRecord.safety_flags` as `extraction_permission_bypassed` instead of `pdf.permission_flags_bypassed`. The bypass detection still lives in `_pdf_via_pypdf` (it has access to `user_access_permissions`); the result is propagated via a transient `_safety_extras` field in the pdf metadata dict, which `scan_file` pops before constructing the `FileRecord` (merging into `safety_flags`). **SCHEMA stays at 1.8 (no bump)** — the safety_flags list type signature is unchanged; a new well-known value name is documented in HISTORY.md.

## 13. Round-2 leg-1 review patch (2026-06-07) — the patch needed its own patch

The leg-1 review patch (commit `1716eb0`) closed the 5 critical bugs round 1 found. The four-leg apparatus ran AGAIN on the patched commit to verify the fixes held. Leg 2 (Gemini) and leg 3 (sweep) returned clean — same drift signature, workers-equality preserved, no determinism breaks. **Leg 1 (in-house swarm) caught 12 new findings — every one CONFIRMED — across two new categories the round-1 fixes introduced.**

The discipline paid out a second time. Each new finding had a corresponding test or doc-update; the round-2 patch (commit `<TBD>` after this section) closes them.

### 13.1 The two new bug categories

**Category A — `pdf.parser` mis-attribution (6 findings: #2/#3/#5/#7/#8/#10).**

The leg-1 patch added two new code paths that return a "signal-only" dict from `_pdf_via_pypdf`:

1. The `DependencyError` marker dict (the cryptography-absent path, RFC §4.1 / leg-1 #3/#8): `{parser: "pypdf", page_count: None, ..., _pdf_encryption_unsupported: True}`.
2. The bypass-only escape (leg-1 #5/#6): `{parser: "pypdf", page_count: None, ..., permission_flags_bypassed: True}`.

Both dicts have every data field None — they exist purely to propagate a signal. But `_extract_pdf_metadata` at scanner.py:3132 unconditionally set `meta["parser"] = decoded["parser"]` whenever the cascade returned a dict. So `pdf.parser="pypdf"` could appear with every metadata field null — violating the field's own contract: *"parser records which tier produced a recovered value"*.

**Fix:** guard the parser assignment so it only stamps when the null-fill loop actually filled a field. Track `cascade_filled_a_field` locally; only set `meta["parser"]` if True. The transient signals (bypass disclosure, encryption-unsupported marker) remain independent of the data-recovery path.

**Category B — `ERR_PDF_ENCRYPTION_UNSUPPORTED` invisible to aggregate counters (2 findings: #11/#12).**

`ScanQuality.specialist_failures`, per-directory `specialist_failures`, and `specialist_stats[tool].failed` all bucketed failures by checking `e.code == ERR_SPECIALIST_PROBE_FAILED`. The new `ERR_PDF_ENCRYPTION_UNSUPPORTED` code wasn't a member. So a corpus of N AES-encrypted PDFs scanned without cryptography installed would report `pdf_extraction: {attempted: N, succeeded: N, failed: 0}` — a 100% success rate with zero recoveries.

**Fix:** centralize specialist-failure codes in a `SPECIALIST_FAILURE_CODES` frozenset and use `e.code in SPECIALIST_FAILURE_CODES` at all four counting sites. Future specialist-failure codes get observable across counters from one edit.
