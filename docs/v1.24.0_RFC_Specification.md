# v1.24.0 RFC — Office & media extraction (Candidate B)

**Status: APPROVED & IMPLEMENTED (v1.24.0).** Office (`.pptx`/`.odp`/`.odt`/`.ods`)
+ reuse-machinery image (`.jp2`/`.tiff`/`.tif`) extraction shipped; audio (`.mp3`)
+ legacy `.ppt` remain the v1.25.0 follow-up. RFC normative language per BCP 14.

**Phased over two minors (decision §11.2 = Option C):**
- **v1.24.0 (this RFC):** office (`.pptx`/`.odt`/`.ods`/`.odp`) + reuse-machinery
  images (`.jp2`/`.tiff`/`.tif`).
- **v1.25.0 (follow-up RFC):** audio (`.mp3`) + legacy `.ppt` (OLE2).

## 1. Summary

Extend specialist extraction to office & media formats file-observer already
*recognizes* but does not *extract* from — **phased over two minors (§11.2)**.
**v1.24.0 (this RFC):** presentations `.pptx`/`.odp`, OpenDocument `.odt`/`.ods`,
images `.jp2`/`.tiff`/`.tif` — all reusing FO's proven ZIP/XML/ISOBMFF/TIFF
readers. **v1.25.0 (follow-up):** audio `.mp3` + legacy `.ppt`, the net-new
parser surface. New `presentation` namespace (v1.24) and `audio` namespace
(v1.25); extensions to `document`, `spreadsheet`, `image`. Pure additive
extraction in the v1.8 mould — but for *new* types, so `requires_specialist_tool`
flips `False→True` for them (a routing change → LOGIC bump).

## 2. Motivation — and the honest caveat

This is the **Candidate B** observation, scouted 2026-06-17 and **deferred
2026-06-23** after measure-first. The deferral reasons must be stated plainly,
because this RFC does not erase them — it overrides them with a different
rationale:

- **It is NOT a gap-fix.** Recognition already works (see §3). These files are
  not flagged `unsupported_extension`/degraded; they are correctly typed to
  their specific MIME today. We are adding extraction *on top of* solid
  recognition, not closing a recognition hole.
- **It is NOT (yet) demand-driven.** At deferral there was no confirmed consumer
  for office/media metadata.

The motivation (resolved §11.1) is **readiness + consumer-positioning** — not
family-completeness for its own sake, and not a present consumer. Build the
extraction that is *ready to build* (reuses proven machinery, near-zero new
risk) so the observable surface is **positioned to attract and serve a consumer
when one appears.** This is the North-Star posture — build toward where the
destination becomes visible — applied to scope: ship the low-risk, high-readiness
half now (v1.24), hold the net-new-parser half (audio / `.ppt`, v1.25) so each
lands on its own merits. It honestly is *additive* (recognition already works);
the value is strategic position, and the phasing keeps that bet cheap and
reversible.

## 4. Scope — RESOLVED: Option C (phased over two minors)

**v1.24.0 (this RFC) — reuse-machinery only, near-zero new parser risk:**
- OOXML/ODF office (`.pptx`/`.odt`/`.ods`/`.odp`) — stdlib `zipfile` + XML, the
  exact docx/xlsx pattern (128 KB deviation budget).
- `.jp2` — reuse the v1.17 ISOBMFF box reader (`jp2h`→`ihdr` for dimensions).
- `.tiff`/`.tif` — reuse the v1.16 EXIF/TIFF-IFD machinery (dimensions; EXIF
  where present).

**v1.25.0 (follow-up RFC) — the net-new parser surface:**
- `.mp3` — bespoke ID3v2 + bounded frame-header scan (the new `audio` namespace).
- `.ppt` — OLE2 via `olefile` (the lone legacy-binary presentation).

Rationale: the v1.24 set reuses readers already battle-tested and red-teamed, so
the strategic-position bet lands cheaply now; `.mp3` (the only genuinely new
untrusted-binary parser) and `.ppt` get their own minor and their own focused
hardening rather than riding a larger surface.

## 5. Proposed observable surface

### v1.24.0 (SCHEMA 1.14 → 1.15)

- **`presentation`** *(new)* — `slide_count`, `title`, `author`, `application`.
  v1.24 sources: OOXML `ppt/slides/` count + `docProps/{core,app}.xml`; ODF
  `content.xml` slide count + `meta.xml` (Dublin Core). (`.ppt`/OLE2 extends this
  namespace in v1.25.)
- **`document`** *(extend)* — `.odt` → `title`, `author`, `word_count`,
  `application` (ODF `meta.xml`; mirrors the docx fields).
- **`spreadsheet`** *(extend)* — `.ods` → `sheet_names`, `application` (ODF
  `content.xml` table names).
- **`image`** *(extend)* — `.jp2` → `width`/`height`; `.tiff` → `width`/`height`
  (+ EXIF `make`/`model`/`datetime_original` where the IFD carries them).

OOXML/ODF `<Application>` feeds the `provenance` vector (mirrors v1.6).

### v1.25.0 (SCHEMA 1.15 → 1.16, follow-up RFC)

- **`audio`** *(new)* — `duration_s`, `bitrate`, `format`, ID3 `title`/`artist`/
  `album`/`year` (ID3v2 + bounded frame scan).
- **`presentation`** *(extend)* — `.ppt` via OLE2 `SummaryInformation`.

## 6. Implementation approach — stdlib-first, reuse the proven readers

No new *required* dependency. Per format:

- **OOXML office** — `zipfile` + XML (defusedxml when present), the docx/xlsx
  path; 128 KB deviation budget; ZIP entries validated via `_is_safe_zip_entry`,
  decompression capped via `_safe_zip_read` (existing guards).
- **ODF** — same ZIP+XML machinery against `content.xml`/`meta.xml`.
- **`.ppt`** — `olefile` (optional dep, gated like `.doc`/`.xls`), `SummaryInformation`.
- **`.jp2`** — the v1.17 `_read_*` ISOBMFF box walker, bounded.
- **`.tiff`** — the v1.16 EXIF/TIFF-IFD reader, bounded 1 MiB head.
- **`.mp3`** — bespoke: ID3v2 size-prefixed tag read + a bounded frame-header
  scan for bitrate/duration. **The one net-new parser; §7 applies hardest here.**

## 7. Safety — the never-crash / bounded bar, from the first commit (MUST)

Every new parser/IO path **MUST** carry the v1.8.1 discipline from the start —
this is non-negotiable and the explicit lesson of the candidate-tier note
("Candidate B, if built, carries the never-crash/bounded bar from the start"):

- All extraction inside the per-file try → an `ErrorRecord`, never a fatal raise.
- Every read bounded (declared deviation); every count/loop/allocation capped
  against hostile inputs (huge ID3 sizes, zip-bomb office files, oversized/zero
  TIFF IFD counts, `.jp2` box-length overflow).
- Determinism: no wall-clock, no process-repr, no un-fingerprinted rule into any
  emitted value (the v1.8.2 / v1.12.1 classes).
- `.mp3` specifically: cap the frame scan window; reject implausible
  bitrate/sample-rate; never trust a declared size past the file bound.

The capture-metadata hardening guard (`tests/test_capture_metadata_hardening.py`)
SHOULD be extended to cover the new parsers, and the bestiary fuzz leg SHOULD run
on `.mp3` before promotion past provisional.

## 8. Version-axis impact

- **SCHEMA 1.14 → 1.15** — the new `presentation` namespace + new fields are a
  contract-shape change (the `audio` namespace arrives with v1.25 → 1.16). New `--schema` registry entries (MUST regenerate
  `docs/SCHEMA.md`; the completeness tests enforce it).
- **LOGIC 1.12.4 → 1.13.0** — `requires_specialist_tool` flips `False→True` for
  the newly-extracted types (a routing change, the v1.16 precedent), and new
  extracted values are emitted.
- **SCANNER 1.23.3 → 1.24.0.**
- **New provisional fields** (candidate → provisional, per the v1.10 ladder) —
  NOT stable on arrival; season before any promotion.
- **Consumer caveat (NOT byte-identical):** manifests over corpora containing
  these formats change — `requires_specialist_tool` flips and
  `specialist_metadata` populates. `provenance`/`author_aggregate`
  `identity_digest` may move where OOXML/ODF `<Application>` now feeds them.

## 9. Falsifiable contract

- `tests/test_v1_24.py` — written failing-first: each new field extracted to a
  known value on a real fixture per format; `requires_specialist_tool == True`
  for the new types; honest `null` (not a guess) where a field is absent or
  unreadable within bounds.
- An **oracle gate** where one exists (the v1.8 pattern): validate
  office/ODF/ID3 extraction against a reference tool on the real corpus, ship
  only on exact agreement; emit `null` rather than a value that disagrees.
- Workers=1-vs-N byte-identical preserved (the v1.9 Layer-A gate) on a corpus
  including the new formats.

## 10. Residuals / limitations (draft)

- Audio duration from frame headers is approximate for VBR without a full scan
  (bounded); document the precision honestly.
- Headerless/garbled inputs → honest `null`, never a guess (the §2 mp3 edge).
- `.jp2` codestream internals and `.tiff` multi-page/strip details are out of
  scope (dimensions + EXIF only).

## 11. Resolved decisions (Russell, 2026-06-25)

1. **Motivation = readiness + consumer-positioning** — ship what's ready and best
   positions FO for a *future* consumer; not completeness-for-its-own-sake, not a
   present consumer. See §2.
2. **Scope = Option C** (phased over two minors). See §4.
3. **`.mp3` = yes, but in v1.25** — a good addition, taken as the second phase
   alongside `.ppt`, so the lone net-new parser gets its own minor + hardening.
4. **Namespace = distinct `presentation`** (not folded into `document`).
