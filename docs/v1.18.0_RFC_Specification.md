## 1. Motivation

A phone video carries the same capture-provenance signals a phone photo does — the
capturing **device** and whether it was **geotagged** — in the container's metadata. v1.16
surfaced them for HEIC/JPEG (`image.make`/`model`/`gps_present` + the `geotagged`
safety_flag); v1.17 built the video container reader but, lacking real phone-captured
samples, shipped only the device-agnostic container fields. This release closes the gap on
real data, reusing v1.17's `moov` reader and v1.16's presence-not-coordinates discipline.

## 2. Scope

**IN (observe-only):**
- **`video.make` / `video.model`** — the capturing device, from the Apple QuickTime
  metadata keys `com.apple.quicktime.make` / `com.apple.quicktime.model` (`moov`→`meta`→
  `keys`+`ilst`). Observed **as-is** (no normalization — observe-don't-interpret, as the
  v1.16 image make/model are raw `"Apple"`/`"NIKON CORPORATION"`).
- **`video.gps_present`** (bool) + **`video.gps_source`** (str|null) — presence of a
  location box AND **which mechanism it came from** (e.g. `com.apple.quicktime.location.ISO6709`
  or `udta.©xyz`; null when absent). **Presence + source, NOT coordinates.** Recording the
  source is deliberate (§8 Q2, Russell): an ingestor gets the provenance — *which*
  standard/box carried the location — at zero privacy cost (still no coordinates).
- **`geotagged` safety_flag fires for video** when `gps_present` — via the v1.16
  `_safety_extras` channel (already generalized to all specialists). The
  `SAFETY_FLAGS["geotagged"]` description broadens to cover video; `docs/SCHEMA.md`
  regenerated (the deferral noted in the v1.17 RFC §5.3).

**OUT (this release):**
- **GPS coordinates** — never decoded/stored; the disclosure says "carries location," the
  consumer decides (§5.2). Permanent non-goal (privacy; location is personal data).
- **QuickTime `creationdate` key reconciliation** — v1.17's `creation_date` comes from
  `mvhd`; the QuickTime `com.apple.quicktime.creationdate` key (which carries a timezone)
  is a *candidate* for a later release, not folded in here (avoids the "which date is real"
  reconciliation v1.17 §5.2 declined). See §8 Q3.
- Deep per-vendor MakerNote-style decode; full XMP; C2PA (the ungated upgrade).

## 3. Parse mechanism (extends v1.17's `moov` reader — no new I/O)

The Apple keys and the location box live **inside the `moov` box** that v1.17's
`_read_moov` already reads (seek-past-`mdat`, bounded by `MOOV_MAX_BYTES`). `_parse_moov`
gains two walks:

- **Apple keys** — `moov`→`meta`→{`keys`, `ilst`}. The `keys` box declares an ordered key
  table (entries of namespace `mdta` + key string like `com.apple.quicktime.make`); the
  `ilst` box holds values as items indexed **1-based into the key table**, each item a
  `data` box (type+locale header + value bytes). Resolve `make`/`model`/location by matching
  the key string → its ilst value.
  - **Known gotcha (measure-first):** QuickTime's `moov`-level `meta` box is **NOT** a
    FullBox (no version/flags), whereas the ISO/HEIF `meta` box (v1.16 `iloc` work) **is**.
    The walk must handle the QuickTime layout. Confirm against real files (§6).
- **Android location** — `moov`→`udta`→`©xyz` box → ISO-6709 string. Presence → `gps_present`.

All bounded / never-crash / deterministic — the v1.8.1 + v1.17-leg-1 discipline: cap every
attacker-controlled count/size; honest-null on truncation; the v1.17 iloc/tkhd bounds-guard
lessons carry directly into the keys/ilst walk.

## 4. Specs
- **Apple QuickTime metadata keys** — Apple developer docs (QTFF), the `mdta` handler +
  `keys`/`ilst` mechanism and the `com.apple.quicktime.*` namespace (published).
- **ISO 6709** — the location string format used by both the Apple key and Android `©xyz`.
- **ISO 14496-12 / QuickTime File Format** — the box structure (`meta`/`udta`).

## 5. Design decisions

### 5.1 Reuse, don't rebuild
Extends v1.17's `_read_moov`/`_parse_moov` (no second file read) and v1.16's
`_safety_extras`→`geotagged` channel (no new disclosure path). `gps_present` is a `video`
field parallel to `image.gps_present`; `geotagged` is the shared cross-format disclosure.

### 5.2 GPS: presence, not coordinates (observe-with-disclosure)
Identical to v1.16 §5.3: detect the location box's **presence**; never decode/store
coordinates. `geotagged` fires; the consumer decides. Honors the privacy line.

### 5.3 Observe, don't interpret / don't reconcile
`make`/`model` surfaced as-is (raw key values). Multiple time/location signals are reported
per-source, never reconciled (v1.17 §5.2). No inference of intent.

### 5.4 Registry + schema discipline
New `video` fields added to `SPECIALIST_FIELDS["video"]`; `SAFETY_FLAGS["geotagged"]`
description broadened to image+video; `docs/SCHEMA.md` regenerated; the `--schema`
completeness tests must stay green (the standing discipline).

## 6. Validation — the GATE (measure-first + exiftool oracle + falsify-first)

This is the gate that deferred the work from v1.17. **The field set / parser is NOT locked
until measured against real phone-captured video:**

- **Measure-first (load-bearing):** inventory a real **iPhone-`.mov`** corpus (and Android
  `.mp4` if available — the parked path): which `com.apple.quicktime.*` keys are present and
  at what prevalence, the location-box format/placement, the QuickTime-vs-ISO `meta`
  layout in practice. v1.17's conformance corpus had **0/62** of these — that absence is the
  reason this is gated. Do not synthesize the field set from the spec alone.
  - **Source verified 2026-06-16 (partial):** the **VISION dataset**
    (`lesc.dinfo.unifi.it/VISION/`, direct per-file download, Apple devices through iPhone
    6/6 Plus + many Android) is a **confirmed source for `make`/`model`** — an iPhone 6 Plus
    native `.mov` carries `com.apple.quicktime.make`=`Apple` / `.model`=`iPhone 6 Plus`
    (exiftool surfaces both; the oracle agrees), plus `.creationdate` **with timezone**
    (corroborates the deferred-creationdate revisit). **Target iPhone 6/6 Plus** (the 4s has
    the keys but exiftool doesn't surface make/model). **GPS GAP:** that VISION sample had
    **no** `location.ISO6709` box — VISION captures appear location-stripped, so VISION
    likely validates make/model but **not** the GPS-present path. **`gps_present`/`gps_source`
    + `geotagged`-for-video need a confirmed-geotagged sample** — the surest is a real iPhone
    capture with Location Services ON (guaranteed `location.ISO6709`), or a targeted
    geotagged sample. **Implication:** the make/model half is unblockable from VISION now;
    the GPS half still waits on a geotagged sample.
  - **GPS sample IN HAND 2026-06-16 (Apple path now fully data-met):** Russell Taildropped a
    real **iPhone 16 Pro Max** clip (`scratch/v1_18_corpus/video/`, gitignored — real
    coordinates) carrying **all four** signals — `com.apple.quicktime.make`=`Apple`,
    `.model`=`iPhone 16 Pro Max`, **`.location.ISO6709` (GPS PRESENT)**, and `.creationdate`
    (TZ-bearing). exiftool surfaces every field. So the **Apple path is now fully unblocked**:
    make/model (VISION + this), `gps_present=true`/`gps_source=apple-ISO6709` (this), and a
    `gps_present=false` case (VISION iPhone-6 no-GPS). **Still wanted (optional):** a modern
    iPhone clip with Location OFF (clean same-model absent case) + an Android `.mp4` (the
    `©xyz` source) — Apple-first ships without them per §8 Q1.
- **exiftool oracle (dev-only, already installed standalone):** `exiftool` extracts
  QuickTime `Make`/`Model` and reports GPS presence/coordinates — gate `make`/`model`
  against it byte-exact, and gate `gps_present` against "exiftool found a location" — across
  the real corpus, **0 disagreements**. Same discipline that validated the v1.17 container
  half (61/61) and the v1.16 EXIF (exiftool/real photos). Honest-null on anything not
  matched; **never a wrong value** (esp. avoid mis-reading an unrelated key as make/model).
- **Falsify-first** (`tests/test_v1_18.py`): keys-present vs absent, GPS-present vs absent,
  the QuickTime-vs-ISO `meta` layout, truncated/adversarial `keys`/`ilst`/`udta` (carry the
  v1.17 bounds-DoS lesson), determinism (workers byte-identical), corpus-sweep no-drift.
- **Fixtures:** a committable **synthetic** `.mov` with a QuickTime `meta`/`keys`/`ilst`
  carrying `com.apple.quicktime.make/model` + an ISO-6709 location box (exercises
  `make`/`model`/`gps_present`/`gps_source`; structural test,
  license-clean, the v1.16/v1.17 generated-fixture pattern). **But — the builder-bias rule
  from v1.16/v1.17 binds: the field set is accepted only after the exiftool oracle passes on
  the REAL phone corpus**, not on the synthetic fixture alone. Real phone video stays
  **local-gitignored** (privacy — GPS in a public repo).
