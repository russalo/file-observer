## 1. Overview

### 1.1 Purpose

Replace the scanner's "read a bounded window (head, or head + tail, or the whole
file ≤ 64 MB) and regex-scan it" heuristic for container formats with a reader
that **follows the format's own index pointer to the exact region it needs.**

The scanner's default observation reads an 8 KB head sample. Container formats
keep their directory/index elsewhere — almost always at the END:

| Format | Where its index lives | How the scanner reaches it today |
|---|---|---|
| **PDF** | `startxref` (near EOF) → cross-reference table → trailer (`/Root`, `/Info`) | v1.5: read the **whole file ≤ 64 MB** and regex-scan for `/Type /Pages` + `/Info` |
| **ZIP / OOXML** | End-of-Central-Directory record (EOCD, at EOF) → central directory | `zipfile` (already follows EOCD) |
| **OLE2** (`.doc`/`.xls`/`.msg`) | FAT / directory sector chains | `olefile` (already follows the FAT) |

OLE2 and ZIP already read structurally (via `olefile`/`zipfile`). PDF does **not**
— v1.5 reads up to 64 MB and pattern-matches, which is the costly, imprecise,
size-capped fallback this RFC targets. v1.7 introduces a single declared-anchor
abstraction, adopts it first for the PDF index reads, and documents OLE2/ZIP as
the proof the pattern generalizes (they are already instances of it).

### 1.2 What v1.7 adds

- **(a)** A **structural-anchor abstraction** — a small, declared table mapping a
  format (identified by the v1.3 `MAGIC_SIGNATURES` machinery) to *where its index
  lives* and *how to reach it*, plus a bounded region reader keyed on it.
- **(b)** The **PDF index reads adopt it**: `page_count` and `/Info`
  (producer/creator/title/creation_date) are obtained by **following `startxref`
  → the latest trailer → the root catalog → the page tree**, instead of regex
  over the whole file. Wins: correct on **incrementally-updated** PDFs (multiple
  xref sections via `/Prev` — every Acrobat "Save" appends one), correct on
  **> 64 MB** PDFs (the pointer is followed regardless of size), and cheaper
  (read a bounded index region, not up to 64 MB).
- **(c)** A provisional **`pdf.xref_type`** field (`classic`/`stream`/`none`)
  recording the cross-reference form observed — i.e. whether (and how) the
  structural index was followed; `none` means no anchor was followed and the v1.5
  window scan produced the values. (Implementation note: PDF specialist-metadata
  fields do not carry per-field `signal_provenance` entries, so `xref_type` — not a
  separate provenance *trigger* — is the structural observable. An earlier draft
  proposed a `structural_anchor` trigger; the in-house review found it redundant
  with `xref_type` and a mismatch for the provenance model, and it was dropped.)

Honest scope boundary with v1.8: v1.7 **finds and reads the index**. Where that
index is a **classic (uncompressed) cross-reference table**, the trailer and page
tree are read directly. Where it is an **xref *stream*** (PDF 1.5+, object-stream
PDFs), v1.7 locates it and MAY inflate it (stdlib `zlib`) to recover the trailer
dict / `/Info`, but **parsing the compressed cross-reference-stream binary format
and object streams to recover `page_count` is deferred to v1.8** (the per-format
parser fork). Object-stream PDFs continue to return `page_count = None` (honest
null) until then — see §5.

### 1.3 Normative Language

MUST / SHOULD / MAY per BCP 14.

## 2. The structural-anchor abstraction

A declared, closed table — analogous to `MAGIC_SIGNATURES` (which already answers
*"what format is this?"*); this answers *"…and where is its index?"*:

```
# (format_label, anchor_kind, locate_fn)
STRUCTURAL_ANCHORS = {
  "pdf":  ("trailer_pointer", _locate_pdf_index),   # scan tail for `startxref`
  "zip":  ("eocd",            _locate_zip_eocd),     # documented; zipfile already does this
  "ole2": ("fat",             None),                 # documented; olefile already does this
}
```

- `anchor_kind` names the structural discipline (a `trailer_pointer` is followed;
  an `eocd`/`fat` is a known end-region the existing library already walks).
- The **region reader** `read_structural_regions(path, sample, fmt)` returns the
  bounded bytes the specialist needs: the head `sample` PLUS the resolved index
  region(s). It MUST be deterministic, MUST bound every read (no unbounded follow
  of `/Prev` chains — cap the chain length and total bytes), and MUST degrade to
  the v1.5 head+tail window on any malformed pointer (never raise).

The abstraction is **format-keyed off `MAGIC_SIGNATURES`**, so it composes with
the v1.3 content-MIME work: *identify the format, then read its index where the
format keeps it.* OLE2/ZIP are entered into the table for documentation and future
unification; they keep using `olefile`/`zipfile` (which are already structural)
in v1.7 — no behavior change for them.

## 3. PDF structural anchor (the load-bearing case)

Follow the chain, each step bounded:

1. **`startxref`** — scan the file tail (last N KB, `PDF_MARKER_BUDGET`-sized) for
   the last `startxref` keyword → byte offset of the cross-reference section.
2. **Cross-reference section** at that offset:
   - **Classic xref table** (`xref` keyword) → read the trailer dict that follows
     (`/Root`, `/Info`, `/Prev`). Read the bounded region around the offset.
   - **Xref stream** (an indirect object `<< … /Type /XRef … >>stream`) → v1.7
     reads the **stream dict** (uncompressed; carries `/Root`, `/Info`, `/Prev`,
     `/Size`); decoding the stream *body* is v1.8.
3. **`/Prev`** (incremental updates) — follow to earlier xref sections, **bounded**
   (cap the number of hops and total bytes); union the trailer info. The *latest*
   trailer's `/Root` wins.
4. **Root catalog → `/Pages`** — resolve `/Root` to the catalog object, then
   `/Pages` to the root page-tree node; read its `/Count`. This is **more precise
   than v1.5's "max `/Count` anchored to `/Type /Pages` over the whole file"**: it
   reads the page count from the *actual root the trailer points at*, immune to
   stale page-tree fragments left by incremental updates.
5. **`/Info`** — resolve and read producer/creator/title/creation_date via the
   existing `_extract_pdf_string` (shared `_decode_pdf_bytes`, balanced parens,
   `/Encrypt` gate — all retained from v1.5/v1.6).

Bounded-observation: every read is capped; a broken chain falls back to the v1.5
head+tail window (which falls back to the head sample). Null remains "not observed
within bounds," never a wrong value.

## 4. ZIP / OLE2 — already structural (the generalization check)

`zipfile` locates the EOCD and reads the central directory; `olefile` walks the
FAT. They are **already instances of the structural-anchor pattern** — which is
the point: the abstraction is not invented for PDF, it is the shape the proven
specialists already have. v1.7 records them in the anchor table for documentation
and to set up future unification (e.g. reading the EOCD directly to count entries
without instantiating `zipfile`), but makes **no behavior change** to the OOXML or
OLE2 specialists. If a fork (§6.D) elects to unify them, it is additive and
separately validated.

## 5. What changes in outputs (and the honest caveat)

Expected, falsifiable effects — to be **measured on the corpus, not asserted**
(the v1.4/v1.5/v1.6 lesson: the builder's intuition about impact is biased):

- **Incrementally-updated PDFs** — `page_count` becomes the *root* count, not the
  max over all (including superseded) page-tree fragments. A real precision fix if
  the corpus contains incremental updates (common: every save-append).
- **> 64 MB PDFs** — `page_count`/`producer` populate by following the pointer
  instead of the head+tail null. Likely **rare** in the infra corpus; state the
  count honestly.
- **Efficiency** — bounded index read vs up to 64 MB read + whole-file regex.
  Real for large born-digital PDFs; measure wall-clock on the corpus.
- **Possible honest outcome:** on the existing corpus the change may be **near-zero
  diff** (v1.5's whole-file scan already handles ≤ 64 MB single-revision classic
  PDFs — the common case). If so, v1.7's net is *precision on incremental updates +
  efficiency + altitude/maintainability + the v1.8 setup*, NOT a headline accuracy
  jump. This RFC commits to reporting that result plainly, as v1.4 did.

**Unchanged residual (→ v1.8):** object-stream PDFs (xref stream + page tree in a
compressed object stream) still return `page_count = None`. v1.7 may recover their
`producer`/`/Info` from the inflated xref-stream dict (fork §6.B); full
`page_count` needs the v1.8 parser fork.

## 6. Design forks (resolved at approval, 2026-06-03)

- **A. LOGIC scope — RESOLVED: index reads only → `LOGIC_VERSION` UNCHANGED
  (1.4.0).** The PDF *routing* flag `requires_vision`/`text_detected` reads a head
  + 128 KB tail **marker** window (v1.5) and is **left untouched** in v1.7. The
  anchor reader targets only the **index** reads (`page_count`/`/Info` — derived
  specialist metadata, not routing); changing their read method is a
  specialist-extraction change tracked by SCANNER version + the observable
  `pdf.xref_type`, exactly as v1.6 kept LOGIC stable. The marker window's > 64 MB blind
  spot stays a documented residual (a future LOGIC-bumping fork only if real files
  show it bites).
- **B. Xref-stream handling — RESOLVED: locate + inflate the stream *dict* (stdlib
  `zlib`) for `/Info` only.** No new dependency. The xref-stream object's dict
  (carrying `/Root`, `/Info`, `/Prev`, `/Size`) is recovered so producer/creator
  populate for object-stream PDFs; decoding the compressed cross-reference *body*
  and object streams for `page_count` is **deferred to v1.8**. Stdlib-only
  discipline holds.
- **C. Provisional `pdf.xref_type` — RESOLVED: add it** (`classic` / `stream` /
  `none` — v1.7 emits exactly these three; hybrid-reference PDFs are reported as
  whichever section the trailing `startxref` points at). Makes the object-stream
  population **measurable** (the data that sizes the v1.8 decision; a Wayne-K-style
  observable). Additive provisional field → `SCHEMA` 1.5→**1.6**.
- **D. OLE2/ZIP unification — RESOLVED: document-only.** They already read
  structurally (`olefile`/`zipfile`); v1.7 records them in the anchor table for
  documentation with **no behavior change** to those well-tested paths. Unification
  revisited only when a concrete need appears.

## 7. Schema & Version Constants

- `SCANNER_VERSION` 1.6.0 → **1.7.0**.
- `LOGIC_VERSION` **unchanged (1.4.0)** — index reads are specialist extraction,
  not routing (§6.A); the `requires_vision` marker window is untouched.
- `SCHEMA_VERSION` 1.5 → **1.6** — additive provisional `pdf.xref_type` (§6.C);
  this is the structural observable (a drafted `structural_anchor` provenance
  trigger was dropped in review — specialist fields carry no per-field provenance).
- v1.0 public contract holds — no field removed/renamed/retyped.

## 8. Boundary (observe, don't interpret)

v1.7 changes *how reliably and cheaply* the scanner reads what is already in the
file's own index; it adds no interpretation. Null still means "not observed within
bounds." `page_count` for an object-stream PDF stays an honest `None` — v1.7 MUST
NOT guess or approximate a page count it did not read. The structural anchor is a
*more precise observation path*, never an inference.

## 9. Validation Plan (falsify-first)

The v1.4/v1.5/v1.6 lesson is explicit: **the builder's own synthetic corpus omits
the breaking case.** Build the adversarial inputs FIRST.

- **Synthetic unit cases first** — classic xref + trailer; **incremental update**
  (two xref sections, `/Prev`, a superseded page-tree fragment → assert the root
  count wins, not the max); **xref stream** (assert located; `/Info` recovered per
  §6.B; `page_count=None` honest); a **broken `startxref`** (assert graceful
  fallback to the v1.5 window, no raise); a **linearized** ("fast web view") PDF
  (first-page xref at the front + main xref at the back); a **> `PDF_FULL_READ_CAP`
  / mock-large** PDF (assert the pointer is followed without reading 64 MB).
- **Real-data validation on `corpora_infra`** (the 964-file corpus) — re-scan and
  **diff page_count/producer/efficiency vs v1.5**. Report: how many PDFs are
  classic vs xref-stream (the §6.C observable); how many `page_count`/`producer`
  values change and whether each change is *more* correct (spot-check incremental
  updates); wall-clock delta. **If the diff is ~zero, say so** — the win is then
  precision-on-incremental + efficiency + altitude + v1.8 setup, not accuracy.
- **Full suite + the three review legs** (in-house multi-agent swarm + Gemini
  cross-model + PR bots/CI) + the empirical sweep extended to track any new signal
  (`pdf.xref_type` if §6.C) — *the sweep only protects what it measures.*

## 10. Relationship to v1.8

v1.7 builds the road to the index; v1.8 decides whether to drive down it. Once the
anchor reader reliably *locates* a format's index, v1.8 weighs an optional
per-format parser (pypdf-style, graceful-degradation-when-absent like `olefile`)
to *decode* the compressed index — recovering `page_count` for object-stream PDFs,
the residual v1.7 leaves honest-null. The `pdf.xref_type` counts from v1.7 (§6.C)
are the data that sizes that decision.
