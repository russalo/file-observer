# Scanner v0.7.0 RFC Specification (DRAFT)

**Project:** Scanner
**Target Version:** 0.7.0
**Status:** Draft
**Date:** 2026-04-10
**Extends:** v0.6.0 RFC Specification

---

## 1. Overview

### 1.1 Purpose

v0.7 expands visibility. More coverage for the biggest remaining format gap, more honesty about what the scanner couldn't do, and more safety signals for files that carry risk.

1. **XLS specialist** — close the largest unsupported format gap (1,001 files in jobs scan)
2. **Scan quality signals** — manifest-level summary of scan health and degradation
3. **Content safety flags** — detect JavaScript in PDFs and macros in DOCX without executing them

### 1.2 Design Principle

> v0.7 tells you what it couldn't reach and what you should be careful about. The scanner doesn't decide if a file is dangerous — it reports the signals that let downstream systems decide.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 2. Feature A — XLS Specialist

### 2.1 Background

`.xls` is legacy binary Excel (BIFF format), stored in OLE2 compound document containers. 1,001 files in the jobs scan — the largest unsupported population after v0.6.

### 2.2 Classification

* `is_binary`: true
* `requires_specialist_tool`: true
* `specialist_tool`: `"spreadsheet_structure"` (same semantic name as XLSX)

### 2.3 Specialist Metadata (when enabled)

```json
{
  "spreadsheet": {
    "sheet_names": ["Summary", "Detail"],
    "format": "biff"
  }
}
```

### 2.4 Implementation

* use `olefile` (already available as optional dependency) to open the OLE2 container
* extract sheet names from the Workbook stream
* operates on sample buffer via `BytesIO` (same bounded pattern as MSG)
* `format` field distinguishes XLS (`"biff"`) from XLSX (`"ooxml"`) under the same `spreadsheet` namespace

#### Requirements

* `.xls` MUST be added to `SUPPORTED_EXTENSIONS`
* `.xls` MUST be added to `SPECIALIST_TOOLS` as `"spreadsheet_structure"`
* `.xls` MUST be added to `SPECIALIST_NAMESPACE` as `"spreadsheet"`
* specialist MUST operate on sample buffer (bounded observation)
* when `olefile` is unavailable, specialist MUST return `null` and record error
* `header_rows` extraction is NOT required for XLS in v0.7 (BIFF parsing complexity; sheet names are sufficient)

### 2.5 XLSX Format Field

Add `format` field to XLSX specialist metadata for parity:

```json
{
  "spreadsheet": {
    "sheet_names": ["Sheet1"],
    "header_rows": {"Sheet1": ["Col A"]},
    "format": "ooxml"
  }
}
```

## 3. Feature B — Scan Quality Signals

### 3.1 Background

The manifest tells you what's in each file but doesn't summarize how well the scan went. An ingestor reading a manifest can't quickly answer: "how much of this scan should I trust?"

### 3.2 New Manifest-Level Block

Add `quality` to `ScanManifest`:

```json
{
  "quality": {
    "total_files": 34273,
    "clean_files": 31500,
    "degraded_files": 2773,
    "error_files": 142,
    "mime_mismatches": 793,
    "polyglots_detected": 3,
    "specialist_failures": 85,
    "unsupported_extensions": 1720,
    "safety_flags": 12
  }
}
```

#### Field Definitions

| Field | Derivation |
|---|---|
| `total_files` | `len(files)` |
| `clean_files` | files with zero errors and no MIME mismatch |
| `degraded_files` | files with non-fatal errors or MIME mismatch but still produced output |
| `error_files` | files where universal tier failed (`universal_stat_failed`) |
| `mime_mismatches` | files where `mime_analysis.matches_extension == false` |
| `polyglots_detected` | files where `is_polyglot == true` |
| `specialist_failures` | files with `specialist_probe_failed` errors |
| `unsupported_extensions` | files with `unsupported_extension` errors |
| `safety_flags` | files with any content safety flag (see Feature C) |

#### Requirements

* `quality` MUST be derived from scanned records (no additional file reads)
* `quality` MUST be deterministic
* `quality` MUST be present on every manifest
* `clean_files + degraded_files + error_files` MUST equal `total_files`

## 4. Feature C — Content Safety Flags

### 4.1 Background

The edge case fixtures revealed that the scanner produces no signal for JavaScript embedded in PDFs or macros in DOCX files. These are legitimate security concerns for any document pipeline.

The scanner does not decide if a file is dangerous. It reports observable structural indicators that downstream systems can use for routing or alerting.

### 4.2 New Field on FileRecord

```json
{
  "safety_flags": ["has_javascript", "has_macros"]
}
```

* array of string tokens
* empty array when no safety-relevant signals detected
* deterministic — same file always produces same flags
* derived from sample buffer content (bounded observation)

### 4.3 Flag Definitions

#### has_javascript (PDF)

Detected when the sample buffer contains any of:
* `/JS` (JavaScript action)
* `/JavaScript` (JavaScript dictionary)
* `/S/JavaScript` (action type)

#### has_macros (DOCX)

Detected when the ZIP entry listing contains:
* `word/vbaProject.bin` (VBA macro storage)
* `word/vbaData.xml` (VBA data)

Operates within the deviation budget — reads ZIP central directory to check entry names, does not decompress macro content.

#### has_ole_objects (RTF)

Detected when the sample buffer contains:
* `\objemb` (embedded OLE object)
* `\objlink` (linked OLE object)

#### has_external_references (XML)

Detected when the sample buffer contains:
* `<!ENTITY` with `SYSTEM` or `PUBLIC` (external entity declarations)

### 4.4 Requirements

* `safety_flags` MUST be present on every FileRecord (empty array when no flags)
* flags MUST be derived from the sample buffer or ZIP entry listing (no additional file reads beyond existing budgets)
* flags MUST NOT interpret content — they report structural indicators only
* flags MUST be deterministic
* each flag MUST have a stable string token
* new flags MAY be added in future minor versions (additive)
* `safety_flags` is a derived signal; provenance SHOULD be recorded

### 4.5 Specialist MIME Guard Interaction

Safety flags are checked BEFORE the specialist MIME guard, so a text file named `.pdf` that contains `/JavaScript` will still get the flag — safety scanning does not depend on MIME matching.

### 4.6 Design Rule

> Safety flags report what the scanner can see in the bytes. They are not threat assessments. "has_javascript" means the bytes `/JavaScript` appear in the PDF sample. Whether that JavaScript is malicious is not the scanner's job.

## 5. Schema Impact

Schema version bumps to `"0.7"`. All changes are additive:

| Field | Location | Type |
|---|---|---|
| `quality` | ScanManifest | object |
| `safety_flags` | FileRecord | list of strings |
| `specialist_metadata.spreadsheet.format` | specialist metadata | string |

No fields removed, renamed, or retyped.

---

## 6. Dependency Impact

No new dependencies. XLS uses `olefile` (already optional). All safety flag detection uses regex/string matching on existing buffers.

## 7. Implementation Order

### Phase 1 — XLS Specialist

1. add `.xls` to `SUPPORTED_EXTENSIONS`, `SPECIALIST_TOOLS`, `SPECIALIST_NAMESPACE`
2. implement `_extract_xls_metadata()` using olefile on sample buffer
3. add `format` field to XLS output (`"biff"`)
4. add `format` field to existing XLSX output (`"ooxml"`)
5. update `SPECIALIST_MIME_GUARD` for XLS MIME types

### Phase 2 — Safety Flags

6. add `safety_flags` field to FileRecord (empty list default)
7. implement `_detect_safety_flags()` method
8. PDF: scan sample for `/JS`, `/JavaScript`, `/S/JavaScript`
9. DOCX: check ZIP entry names for `vbaProject.bin`
10. RTF: scan sample for `\objemb`, `\objlink`
11. XML: scan sample for `<!ENTITY` with `SYSTEM`/`PUBLIC`
12. call safety detection in `scan_file()` before specialist extraction

### Phase 3 — Scan Quality

13. add `ScanQuality` dataclass
14. add `quality` field to `ScanManifest`
15. implement `_compute_quality()` from file records
16. include `safety_flags` count in quality summary

## 8. Acceptance Criteria

v0.7 is complete when:

* `.xls` is supported with sheet name extraction via olefile
* XLS and XLSX both include `format` field in specialist metadata
* `safety_flags` present on every file (empty array when clean)
* PDF JavaScript detection works on edge case fixture
* DOCX macro detection works on edge case fixture
* RTF OLE object detection works on edge case fixture
* XML external entity detection works on edge case fixture
* `quality` block present on every manifest with correct counts
* `clean_files + degraded_files + error_files == total_files`
* all v0.6 tests pass unchanged
* schema_version is `"0.7"`

---

## 9. Final Statement

v0.7 is about visibility. The scanner already observes files — now it observes itself (quality) and warns about what it sees (safety). More coverage, more honesty, closer to 1.0.
