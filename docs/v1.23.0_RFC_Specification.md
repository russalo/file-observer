# v1.23.0 RFC — promotion pass: `preservation` → stable

**Status: SHIPPED** — released as v1.23.0 (see `docs/HISTORY.md` for the date and the patch releases that rode on this minor). The status line below is the RFC's state at approval time, kept as written.

**STATUS (at approval time): APPROVED 2026-06-19 (Russell).** Designation-only promotion, decided from the
promotion-readiness audit (`scratch/promotion_readiness_audit_2026-06-19.md`). No design forks —
the evidence is in hand; this RFC documents the promotion + a small §2.4 reclassification.

## 1. Why

The readiness audit assessed every provisional field against the criterion (**settled producing
logic + evidence of value**, the v1.10/v1.14 standard). Exactly one is ripe now: **`preservation`**.
- **Settled logic:** a closed format-obsolescence table, rules-hash-fingerprinted, **unchanged
  since v1.10** (~2 weeks seasoned).
- **Evidence of value (corpus-grounded 2026-06-19):** across 19,488 files it produces *accurate*
  obsolescence signal — 155 `at_risk` (legacy MS Office .doc/.xls/.ppt, CAD .dwg/.dgn, .eps) +
  14 `obsolete` (Flash .swf, WordPerfect .wpd/.wp, Lotus .wks/.wq1, old OpenOffice .sxc/.sxw),
  `migration_recommended=True` correctly on the 14 obsolete. Not noise, not all-`current`.
- The **v1.14 hold** ("too new — gather data") is resolved: now seasoned AND demonstrated-valuable.

Everything else stays provisional: image/video capture fields are **days old** (season — next pass);
the chatlog family is **held** (the non-count redesign reworks `content_shape`; alpha-locked for Sentinel).

## 2. The change

- **Promote `preservation` provisional → stable** — both surfaces: the `preservation` **vector** and
  the per-`FileRecord` **`preservation`** field (`format_obsolescence`: `current`/`at_risk`/`obsolete`;
  `migration_recommended`: bool). Remove `preservation` from `PROVISIONAL_VECTORS` and
  `("FileRecord","preservation")` from `PROVISIONAL_MANIFEST_FIELDS`. `--schema` then annotates it `stable`.
- **§2.4 reclassification (doc-only, rides this minor):** `format_signatures` + `is_polyglot` are
  **held-by-design / permanently-informational** — NOT promotion candidates. The signature vocabulary
  intentionally grows every MIME change; `is_polyglot` derives from it; consumers branch on presence
  (like the §2.2 provenance triggers), not exact tokens. Distinguish them in §2.4 so future passes
  stop re-asking "promote these?" (answer: no, by design). They STAY in `PROVISIONAL_MANIFEST_FIELDS`.

## 3. The stable promise (what freezes vs not)
- **Frozen:** the `preservation` field SHAPE — `format_obsolescence` ∈ {current, at_risk, obsolete},
  `migration_recommended` ∈ {true, false}; top-level on every FileRecord (same scope as `filename_patterns`).
  Not removable/retypable without a MAJOR bump.
- **NOT frozen (additive):** the closed obsolescence TABLE may still grow (more formats classified) —
  rules-hash-tracked, exactly like `provenance`'s toolchain table (v1.14 precedent). Table growth is an
  additive value change, not a field-shape change.

## 4. Acceptance bar (falsify-first — `tests/test_v1_23.py`)

2. `preservation` is NOT in `PROVISIONAL_VECTORS` nor `PROVISIONAL_MANIFEST_FIELDS` (the registries == the documented set — the test_v1_14 drift guard, updated).
3. **Designation-only:** the scan manifest is **byte-identical** except the version stamps — no `stability` key leaks into the manifest; `preservation` values unchanged.
4. `format_signatures` + `is_polyglot` STAY provisional in `--schema`.
5. The capture fields (image/video) + chatlog family STAY provisional (not swept up).
