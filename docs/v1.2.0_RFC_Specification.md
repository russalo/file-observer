## 1. Overview

### 1.1 Purpose

v1.2 hardens and generalizes the **chatlog** vector, and lays the **per-speaker structure** foundation for the Project Sentinel use case. Every change here is **data-driven** — it comes from running v1.1 against a deliberately assembled corpus library (Claude session logs, Sentinel roleplay, ConvoKit, OpenAssistant, Anthropic hh-rlhf, ShareGPT, plus doc-heavy OSS repos). That testing produced a clean, three-part diagnosis:

- **True positives are perfect** on `type: user/assistant` JSONL (Claude sessions 41/41, Sentinel 3/3).
- **False positives** on prose markdown (`.md` docs flagged `is_chatlog`, e.g. FastAPI 125, AutoGPT 16), where extraction then fails silently.
- **False negatives** on every *other* conversational schema (ConvoKit `{speaker,text}`, oasst1 nested `prompt.role`, hh-rlhf `Human:/Assistant:` text-in-field, ShareGPT `{from,value}`) and on `.json` entirely.

### 1.2 What v1.2 does

| | Change | Kind |
|---|---|---|
| **(a)** | Reduce markdown/text false positives | detection tuning |
| **(b)** | Populate `detail` on chatlog extraction failures (no more silent fails) | bug fix |
| **(c)** | Generalize JSONL/JSON conversational detection beyond `type: user/assistant` | detection logic |
| **(d)** | Add **per-speaker turn structure** to the chatlog namespace (additive, provisional) | new fields |

(a)–(c) change *detection behavior* (so `LOGIC_VERSION` and the chatlog vector's `method_version` bump); (d) adds new fields (so `SCHEMA_VERSION` bumps). Together they make v1.2 a proper MINOR.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 2. Generalized Conversational Detection (c)

The JSONL detector (v0.10.1) recognizes only flat `{"type": "user"/"assistant"}` objects. v1.2 generalizes it.

- Detection MUST recognize common **role keys** (`role`, `from`, `speaker`, `author`, `type`) paired with common **content keys** (`text`, `value`, `content`, `message`, `body`) in JSON objects.
- Detection MUST handle:
  - **utterance-per-line JSONL** (ConvoKit: `{"speaker","text",...}`),
  - **array-of-messages** within a JSON value (ShareGPT: `{"conversations":[{"from","value"}]}`),
  - **nested message trees** (oasst1: `prompt.role` + recursive `replies`).
- `.json` MUST become a chatlog-candidate extension (alongside `.txt/.md/.mdx/.jsonl`), gated by content as the others are. Plain non-conversational `.json` MUST NOT be flagged.
- Detection SHOULD recognize speaker-labelled dialogue embedded in a JSON **string field** (hh-rlhf: `"\n\nHuman: …\n\nAssistant: …"`), reusing the text speaker-label heuristic on extracted string values.
- The existing `type: user/assistant` behavior MUST remain a detected case (no regression on Claude/Sentinel logs).

**Determinism:** detection MUST stay a pure function of the bounded sample — same bytes in, same `is_chatlog` out.

---

## 3. False-Positive Reduction (a)

Prose documentation (`.md` README/specs) is wrongly flagged `is_chatlog` via the speaker-label / H3 / divider heuristics.

- The `.txt`/`.md`/`.mdx` heuristic MUST be tightened to reduce false positives on prose/documentation while preserving true positives on genuine transcripts. Candidate signals: require speaker labels to recur with **turn-like alternation** (not one-off `Note:`/`Example:` lines — extend the existing stop-list), and/or raise the divider/header thresholds.
- Acceptance is **measured**, not asserted: false-positive rate on the doc-heavy OSS corpora MUST drop materially while true-positive detection on the genuine-transcript corpora MUST NOT regress (see §8).

---

## 4. Extraction Error Hygiene (b)

When chatlog extraction raises `specialist_probe_failed`, the `ErrorRecord.detail` is currently empty.

- Chatlog extraction failures MUST record a non-empty `detail` explaining the cause (e.g. "no speaker turns parsed", "decode error", "empty content"). This brings the chatlog specialist in line with the diagnostic quality of the rest of the scanner.

---

## 5. Per-Speaker Turn Structure (d) — additive, provisional

New fields in the `chatlog` namespace (`specialist_metadata.chatlog.*`), the foundation for the Sentinel provenance trail (who-said-what-first / cross-speaker uptake — see [[project_sentinel]]):

- `speaker_turn_counts`: `{speaker_label: turn_count}` (sorted keys).
- `speaker_turn_chars`: `{speaker_label: {avg, max, min}}` per speaker.
- `alternation`: structural signal — `longest_single_speaker_run` and `speaker_change_ratio`.

These are **pure observation** (counting/attribution by speaker label) — the scanner reports structure; it does **not** judge authority or canon. All ship **provisional** (§2.4). Bound to the chatlog method_version.

> **Note:** the downstream *word-twisting / authority* hypothesis (does introducer + cross-speaker uptake predict canon?) is **not** part of v1.2 — it's future analysis validated against the manually-tagged RPG corpus. v1.2 only emits the raw per-speaker structure that analysis will consume.

## 6. Schema & Version Constants

- `SCHEMA_VERSION`: `1.1` → `1.2` (additive — new `chatlog` namespace fields per §5).
- `SCANNER_VERSION`: `1.1.0` → `1.2.0`.
- `LOGIC_VERSION`: `1.0.0` → `1.1.0` — **changes** because detection behavior changes (§2, §3): some files now flag `is_chatlog` that didn't (and vice-versa). `LOGIC_VERSION` is not a stability commitment (CONVENTIONS §1.2 / PUBLIC_CONTRACT §2.3); this is the correct signal to consumers that routing/flagging logic moved.
- **chatlog vector `method_version`: `3` → `4`** — detection rules and field set change, so the identity digest changes (per the vector identity contract, PUBLIC_CONTRACT §6 / v1.0 RFC §3.4). Same digest still ⇒ same output.

---

## 7. Backward Compatibility

- **`is_chatlog` field is unchanged in shape/type** (stable since 0.8). What changes is *which files it flags* — a detection/`LOGIC_VERSION` change, explicitly permitted (detection logic is not frozen; only the schema is).
- The chatlog `method_version` bump (3→4) means re-scans of the same corpus produce a different chatlog identity digest — this is the contract working as designed (new digest = new rules), not a break.
- §5 fields are **additive and provisional** (PUBLIC_CONTRACT §2.4). Existing chatlog fields are untouched.
- No existing field removed, renamed, or retyped → v1.0 consumers (branch on MAJOR, ignore unknown fields) keep working.

## 8. Validation Plan (measured, with the assembled corpus library)

The chatlog test matrix is already on disk (`scratch/corpora*`, gitignored):

| Class | Corpus | Expectation after v1.2 |
|---|---|---|
| **TP (must not regress)** | `~/.claude` sessions, Sentinel roleplay | still 100% detect + extract |
| **FP (must drop)** | FastAPI / AutoGPT `.md` docs | materially fewer `is_chatlog` |
| **FN → TP (must improve)** | ConvoKit, oasst1, hh-rlhf, ShareGPT | now detected via generalized schemas |
| **Ground truth** | ConvoKit conversations-gone-awry (labeled), oasst1 (tree-structured) | report precision/recall |

- MUST publish before/after detection counts per corpus.
- MUST add unit tests for each new schema (utterance-JSONL, role/from/speaker keys, nested tree, array-of-messages, `.json`, embedded `Human:/Assistant:`), the FP reduction (a doc fixture that should *not* flag), and the non-empty `detail`.
- All prior tests MUST pass (existing `type: user/assistant` fixtures still detect).

## 9. Acceptance Criteria

- `SCHEMA_VERSION` "1.2", `SCANNER_VERSION` "1.2.0", `LOGIC_VERSION` "1.1.0", chatlog `method_version` 4.
- Generalized detection recognizes the four+ schemas in §2; `.json` is a gated candidate.
- Measured: FP rate down on doc corpora, TP preserved on genuine transcripts, FN corpora now detected (before/after table).
- Chatlog extraction failures carry a non-empty `detail`.
- `speaker_turn_counts` / `speaker_turn_chars` / `alternation` emitted, deterministic, documented provisional in PUBLIC_CONTRACT §2.4.
- New + existing tests pass; `COMPLIANCE-v1.2.md` written; HISTORY / CONVENTIONS / README / PUBLIC_CONTRACT updated.
