# v1.27.0 RFC — JSON Schema artifact for the manifest

**Status: APPROVED (Russell, 2026-06-26) — decision: C (generate + validation guard), + `jsonschema` dev-dep, + `--schema --format json-schema`.**
RFC normative language per BCP 14.

| Axis | Current (v1.26.0) | Proposed (v1.27.0) |
|---|---|---|
| SCANNER | 1.26.0 | 1.27.0 |
| LOGIC | 1.14.1 | 1.14.1 (unchanged) |
| SCHEMA | 1.16 | 1.16 (unchanged) |

## 1. Summary

Ship a committed, standard **JSON Schema (draft 2020-12)** describing the manifest, so
**any-language consumer** (trellis in Rust, gazetteer, a future JS/Go reader) can
*validate* a manifest and *codegen* types against the contract — not just trust prose.
Committed as `docs/manifest.schema.json`, version-stamped, and drift-guarded.

## 2. Motivation

Second aim of the adoption-by-lowering-barriers track, and the most **FO-shaped** of them:
it serves the deterministic-JSON-contract strength directly. trellis explicitly asked for a
stable, machine-readable contract; gazetteer is a second consumer; both — and any stranger
— benefit from a schema they can point a validator/codegen at. The import-API (`scan`,
v1.26) lowered the *produce* barrier; this lowers the *consume* barrier, language-agnostic.

## 3. Coverage — rigorous core, open provisional surface

The schema mirrors the contract's own stability tiers:
- **Rigorously typed (stable):** the top-level `ScanManifest` shape (`schema_version`,
  `context`, `meta`, `stats`, `quality`, `routing_summary`, `delta`, `manifest_checksum`,
  `files[]`, `vectors_collected[]`, `summary`) + the **stable `FileRecord` core** (`path`,
  `filename`, `extension`, `mime_type`, `size_bytes`, `created_at`, `modified_at`,
  `checksum_sha256`, `stage_folder`, `directory_depth`, `encoding`, `is_binary`,
  routing flags, `tags`, `safety_flags`, …) + the stable nested records (`mime_analysis`,
  `structural`, `frontmatter`, `delta`) as `$defs`.
- **Open objects (provisional / namespace-keyed):** `specialist_metadata`,
  `signal_provenance`, `file_signature`, `format_signatures[]`, `preservation`,
  `reference_tokens`, `filename_patterns` are typed as `object`/`array` with
  `additionalProperties: true` (or `["object","null"]`). Their *keys* are namespace- and
  release-dependent (provisional surface, PUBLIC_CONTRACT §2.4); pinning them rigidly would
  couple the schema to churn and defeat the "evolve the content side freely" promise that
  trellis is relying on. This is deliberate: validate the durable core strictly, don't
  over-constrain the provisional surface.

`required` lists only the stable, always-present fields (honest-null fields stay
`["T","null"]`, not `required`-omitted).

## 4. Versioning & identity

- `$schema`: `https://json-schema.org/draft/2020-12/schema`.
- `$id` carries the manifest SCHEMA version, e.g. `…/file-observer/manifest/1.16.schema.json`,
  and `title`/`$comment` record the producing SCANNER + SCHEMA version. It's a **build-time
  interface** versioned exactly like the `--schema` JSON envelope (the v1.21.2 precedent,
  `schema_doc_version`) — a MAJOR `schema_version` bump is the breaking-change point a
  consumer pins against (the same MAJOR-pin trellis already does).

## 5. Generation & drift-guard (§8 decides the mechanism)

Whichever mechanism (§8), TWO guards in `tests/`:
- **(a) committed == regenerated** — the `docs/SCHEMA.md` precedent (regenerate on any
  surface change; CI fails if stale).
- **(b) a real scan's manifest VALIDATES against the committed schema** — the correctness
  proof a generator alone can't give (a self-consistent schema can still be *wrong*). Needs
  `jsonschema` as a **dev-only** dep (not a runtime dep — the zero-runtime-dep posture holds).

A new `--schema --format json-schema` (or `--json-schema`) emit is the natural home if
generated; a generator script under `scratch/` if we'd rather not grow the CLI.

## 6. Version-axis impact

- **SCANNER 1.26.0 → 1.27.0** — new committed artifact (+ maybe a `--schema` sub-format).
- **LOGIC 1.14.1 / SCHEMA 1.16 unchanged** — the JSON Schema *describes* the existing
  manifest; it changes nothing the scanner emits. Manifest byte-identical.

## 7. Falsifiable contract

`tests/test_v1_27.py`: the committed `docs/manifest.schema.json` is valid draft-2020-12;
a real scan's manifest validates against it (specialists on AND off; a chatlog corpus; an
empty dir); the stable-core fields are `required` + correctly typed; the open dicts accept
arbitrary keys; `$id`/version stamp matches `SCHEMA_VERSION`; committed == regenerated.

## 8. Decisions (RESOLVED — Russell, 2026-06-26)

1. **Generate vs hand-author = C (GENERATE + validation guard).** Generate from dataclass
   introspection AND drift-guard with committed==regenerated + real-manifest-validation.
   Single source of truth (FO discipline) AND proven-correct. 2. `jsonschema` dev-dep = YES.
   3. CLI surface = `--schema --format json-schema`. (Original options below for the record.)

### Original fork —
   **(A) GENERATE** from dataclass introspection (extend `--schema`): single source of
   truth, can't drift from the dataclasses, consistent with FO's v1.13 discipline + the
   generated `docs/SCHEMA.md`; cost = a ~150–250-line dataclass→JSON-Schema generator (the
   type vocab is bounded, so tractable). **(B) HAND-AUTHOR** + the two §5 guards: faster to
   land, often a cleaner/more-readable consumer-facing artifact, but a hand-maintained
   second copy (the thing FO's culture warns against) — the guards (field-completeness +
   real-manifest-validation) catch the drift that matters. **(C) GENERATE + the validation
   guard** — belt-and-suspenders (single-source AND proven-correct). *Lean: **C*** (most
   FO-consistent and the validation guard is the real correctness proof), accepting it's the
   most work; **B** if you'd rather land it faster.
2. **`jsonschema` as a dev dep for guard (b)?** *Lean: yes* — dev-only, the correctness
   proof is worth it; runtime stays zero-dep.
3. **CLI surface** — add `--schema --format json-schema`, or keep generation in a
   `scratch/` script? *Lean: `--schema --format json-schema`* (discoverable; the artifact is
   a first-class output, like `--format md`).

## 9. Review plan

Leg-1 in-house swarm + leg-4 PR bots; falsify-first. No corpus sweep / red-team (manifest
unchanged, no new parser). The validation guard IS the substantive correctness gate.
