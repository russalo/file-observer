## 1. Overview

### 1.1 Purpose

v0.9 introduces the **Vector abstraction** — the foundation for audit-grade observation. The scanner stops being just a per-file observer and starts being a corpus observer.

A vector is a named, uniquely-identified unit of observation: a rule set + tuning, applied to either a single file or an entire scan, producing counts and summaries that a downstream consumer can verify and reproduce. Two scanner runs against the same input that emit the same vector identity digest MUST produce identical vector output. That contract makes the scanner an evidence engine instead of a heuristic.

The v0.9 release ships:
- The `Vector` abstraction itself
- A new top-level `vectors_collected[]` manifest block carrying vector identity, identity digest, and output for every vector that ran
- Two exemplar vectors that pressure-test the abstraction across two structural angles (content-gated and unconditional)
- Per-directory aggregation in `ScanQuality` so corpus shape becomes manifest-level visible
- A cross-cut: the chatlog vector applied to `.eml` / `.msg` message bodies, extending chatlog visibility into the email corpus
- Dublin Core promoted to the Adopted tier of standards tracking — the first standards graduation through the workflow designed in v0.7

### 1.2 Design Principle

> Every vector carries enough identifying metadata that a downstream consumer can verify which rule set + which configuration produced a given count. Two scanner runs claiming the same vector identity digest on the same input MUST produce identical output. The identity digest is a hash over every input that affects the result; nothing that affects output lives outside the digest preimage.

This is the v0.3 capability-locked determinism principle applied at the vector level.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 2. The Vector Abstraction

### 2.1 What a vector is

A **vector** is a deterministic observation function with three essential parts:

1. **Identity** — a `vector_id` (string namespace.name) and `method_version` (integer) that together name the vector definition
2. **Rules** — the patterns, thresholds, and counting logic that define what the vector observes
3. **Tuning** — the static configuration that parameterizes the rules (thresholds, top-N caps, included subpatterns)

A vector instance produces:
- An identity digest that uniquely identifies (identity + rules + tuning + future configuration)
- A summary of what the vector observed
- A count of which files the vector applied to (for file-scoped vectors)

### 2.2 Vector Scope

| Scope | Applied to | Output shape |
|---|---|---|
| `file` | Each file matching activation criteria | Per-file metadata + corpus-level summary aggregate |
| `corpus` | The entire scan as a unit | Single corpus-level summary; no per-file output |

File-scoped vectors run as the scan walks each file. Corpus-scoped vectors run after the file walk completes, with access to the assembled FileRecord list. Both kinds emit a single entry in `vectors_collected[]` per scan.

### 2.3 Vector Identity — Rules vs. Tuning

Vector identity is composed of two distinct hash components:

- `rules_hash` — hash of the rule set definition (the regex patterns, the activation logic, the counting algorithm). Changing this is a new `method_version`.
- `static_tuning_hash` — hash of the operator-set parameters that the rules consume (thresholds, top-N counts, enabled subpatterns). Changing this is a new configuration of the same vector — same `vector_id` and `method_version`, different `static_tuning_hash`.

The distinction tells consumers what kind of change they're looking at. A new `method_version` means the vector definition itself changed. A new `static_tuning_hash` means the same vector ran with different parameters. Both produce different output; they're different *kinds* of change.

### 2.4 Identity Digest Computation

Every vector emits a composite `identity_digest` field computed as:

```
identity_digest = sha256(
    vector_id + "|" +
    str(method_version) + "|" +
    rules_hash + "|" +
    static_tuning_hash + "|" +
    (dynamic_tuning_hash or "null") + "|" +
    (dictionary_id or "null")
)
```

Two future-proofing slots are reserved but always `null` in v0.9:

- `dynamic_tuning_hash` — placeholder for v0.11+ when reactive auto-configuration may emit runtime-adjusted tuning. MUST be `null` in v0.9.
- `dictionary_id` — placeholder for v0.10+ when vectors may take a configurable dictionary parameter. MUST be `null` in v0.9.

The identity digest hash function is SHA-256, hex-encoded. The preimage is the literal pipe-delimited string above. This is a stable preimage shape — it MUST NOT change between scanner versions without bumping the schema version.

### 2.5 The `vectors_collected[]` Manifest Block

A new top-level array on `ScanManifest`. One entry per vector that ran in the scan, sorted alphabetically by `vector_id`.

```json
{
  "vectors_collected": [
    {
      "vector_id": "chatlog",
      "method_version": 1,
      "scope": "file",
      "rules_hash": "sha256:111...",
      "static_tuning_hash": "sha256:222...",
      "dynamic_tuning_hash": null,
      "dictionary_id": null,
      "identity_digest": "sha256:eee...",
      "applied_to_count": 4,
      "summary": {
        "matched_files": 4,
        "total_turns": 187,
        "distinct_speakers": ["Assistant", "User"],
        "section_marker_count": 47,
        "section_marker_styles": ["---", "### "]
      }
    },
    {
      "vector_id": "reference_tokens",
      "method_version": 1,
      "scope": "file",
      "rules_hash": "sha256:333...",
      "static_tuning_hash": "sha256:444...",
      "dynamic_tuning_hash": null,
      "dictionary_id": null,
      "identity_digest": "sha256:bbb...",
      "applied_to_count": 96,
      "summary": {
        "total_at_mentions": 312,
        "total_wiki_links": 47,
        "total_code_fence_blocks": 89,
        "total_url_count": 521,
        "total_email_mentions": 18,
        "total_path_references": 134,
        "total_numeric_id_patterns": 67,
        "files_with_any_reference": 84
      }
    }
  ]
}
```

The `applied_to_count` field carries the count of files the vector ran against. To find *which* files a vector matched, a consumer cross-references with per-file FileRecord fields.

### 2.6 Determinism Guarantees

For any vector:

- **Same identity digest, same input → same output.** Two scans of the same files with vectors having the same identity digest MUST produce byte-identical vector summary output.
- **Different identity digest → output may differ.** No guarantee across different digests.
- **File order does not affect output.** Vectors operate on a sorted file iteration; output MUST be reproducible regardless of filesystem walk order.
- **Environment does not affect output.** Vectors MUST NOT depend on wall-clock time, hostname, process ID, environment variables, or system state.

### 2.7 What Vectors Do NOT Do (in v0.9)

- **No dynamic tuning.** `dynamic_tuning_hash` MUST be `null`. Vectors take only static configuration.
- **No dictionaries.** `dictionary_id` MUST be `null`. Vectors use only built-in rule sets.
- **No cross-scan state.** Vectors do not remember previous scans or persist state.
- **No NLP / ML / language detection.** Vectors are statically-coded deterministic functions.
- **No interpretation.** Vectors emit counts and lists. Meaning is the consumer's responsibility.

## 3. The Two Exemplar Vectors

v0.9 ships two vectors that exercise the abstraction across two different structural angles.

### 3.1 `chatlog` — Content-gated, file-scoped

**Refactored from v0.8.** The chatlog specialist's detection and extraction functions become the rule set and counting logic of the `chatlog` vector.

| Field | Value |
|---|---|
| `vector_id` | `chatlog` |
| `method_version` | `1` |
| `scope` | `file` |
| Activation | `.txt` / `.md` / `.mdx` files where any of the three v0.8 §2.3 detection rules match |
| Rules | The three v0.8 detection rules (3+ speaker labels, 3+ `### ` headers, 3+ `---` dividers), plus the v0.8 extraction logic for the 11 chatlog metadata fields |
| Static tuning | `{"detection_threshold": 3, "top_capitalized_tokens_n": 20}` |

**Backwards compatibility:** The v0.8 `is_chatlog` FileRecord field and the v0.8 `specialist_metadata.chatlog` namespace BOTH remain in v0.9 manifests. They are now formally defined as **derived outputs of the chatlog vector**:
- `is_chatlog == True` iff the file is in the `chatlog` vector's applied set
- `specialist_metadata.chatlog` is the per-file vector output for that file

A consumer that read v0.8 manifests will read v0.9 manifests identically for these fields. The new `vectors_collected[chatlog]` entry is additive.

**Vector summary fields** (in `vectors_collected[chatlog].summary`):
- `matched_files` — count of files in the applied set
- `total_turns` — corpus sum of `turn_count` across matched files
- `distinct_speakers` — sorted union of all speaker labels across matched files
- `section_marker_count` — corpus sum
- `section_marker_styles` — sorted union of all section marker styles

### 3.2 `reference_tokens` — Unconditional, file-scoped

A new vector that runs on every baseline-decoded text file regardless of content. Generalizes the chatlog specialist's per-file reference token counting and extends it with additional patterns.

| Field | Value |
|---|---|
| `vector_id` | `reference_tokens` |
| `method_version` | `1` |
| `scope` | `file` |
| Activation | Every file where `is_binary == false` AND extension is in the text-eligible set |
| Rules | Seven regex patterns, each independently counted per file |
| Static tuning | `{"enabled_subcategories": ["at_mentions", "wiki_links", "code_fence_blocks", "url_count", "email_mentions", "path_references", "numeric_id_patterns"]}` |

**The seven subcategories:**

| Subcategory | Pattern | Purpose |
|---|---|---|
| `at_mentions` | `@[a-zA-Z0-9_]+` | User/handle mentions |
| `wiki_links` | `\[\[.+?\]\]` | Wiki-style links (Obsidian, MediaWiki) |
| `code_fence_blocks` | Triple-backtick pairs | Embedded code blocks |
| `url_count` | `https?://\S+` | HTTP/HTTPS URLs |
| `email_mentions` | `\b[\w._%+-]+@[\w.-]+\.[a-zA-Z]{2,}\b` | Email addresses |
| `path_references` | Unix `/foo/bar/baz` and Windows `[A-Za-z]:\\` (3+ segments) | File path references |
| `numeric_id_patterns` | `#\d{2,}`, `\bv\d+\.\d+\b`, `\b[A-Z]{2,}-\d+\b` | Ticket numbers, semver, project IDs |

**New per-file FileRecord field** (additive):

```json
"reference_tokens": {
  "at_mentions": 0,
  "wiki_links": 0,
  "code_fence_blocks": 0,
  "url_count": 0,
  "email_mentions": 0,
  "path_references": 0,
  "numeric_id_patterns": 0
}
```

Present on every text-decoded FileRecord; `null` on binary files. The chatlog specialist's existing `specialist_metadata.chatlog.reference_tokens` is preserved unchanged for backwards compatibility. Consumers SHOULD prefer the top-level `reference_tokens` field for new code.

**Vector summary fields:**
- Corpus sums of each subcategory
- `files_with_any_reference` — count of files where at least one subcategory was nonzero

## 4. Cross-Cutting Observation

### 4.1 Chatlog Vector Applied to Email Bodies

The chatlog vector is callable as a library function (a consequence of the refactor). v0.9 wires it into the `email_envelope` specialist so that when an `.eml` or `.msg` body is extracted, the body text is passed through the chatlog vector's detection and extraction logic.

When the chatlog vector fires on an email body:

- `specialist_metadata.email.body_chatlog` is populated with the chatlog vector's per-file output (same shape as `specialist_metadata.chatlog`)
- The email file is added to the `chatlog` vector's `applied_to_count`
- `is_chatlog` on the FileRecord STAYS `false` — the file itself is binary OLE2/MIME; the detection ran on the body, not the file
- A consumer checks for `specialist_metadata.email.body_chatlog` to know if chatlog content appeared in an email

### 4.2 Per-Directory Aggregation in `ScanQuality`

A new field `per_directory_summary` on `ScanQuality`:

```json
"per_directory_summary": [
  {
    "directory": "project_alpha",
    "total_files": 1247,
    "chatlog_files": 0,
    "safety_flags_files": 12,
    "mime_mismatches": 87,
    "polyglots_detected": 0,
    "specialist_failures": 4,
    "unsupported_extensions": 43
  }
]
```

**Aggregation rules:**
- One entry per **top-level subdirectory** of the scan source. Files at scan root use `directory: ""`
- Top-level only — not nested deeper. Keeps the field bounded for large corpora.
- Sorted alphabetically by `directory`
- All fields are non-negative integers

## 8. Acceptance Criteria

v0.9 is complete when:

- `Vector` abstraction exists with documented identity digest computation
- `vectors_collected[]` present on every manifest, sorted by `vector_id`
- Identity digests are deterministic (verified by tests)
- Two scans of the same corpus produce byte-identical `vectors_collected[]` (modulo volatile fields)
- Chatlog vector output exactly matches v0.8 for same files (regression guarded)
- `reference_tokens` populated on every text-eligible file, `null` on binary
- `quality.per_directory_summary[]` populated for every top-level subdirectory
- `specialist_metadata.email.body_chatlog` populated when chatlog fires on email body
- Dublin Core alignment documented in PUBLIC_CONTRACT.md
- Dublin Core moved to Adopted in STANDARDS_TRACKING.md
- All v0.8 tests pass unchanged
- New v0.9 tests cover all additions
- `schema_version` is `"0.9"`

## 9. Open Questions

1. Should `dcterms:modified` be exposed as `specialist_metadata.document.modified_at` alongside Dublin Core graduation? If one-line, do it; if more, defer to v0.10.

2. Should `reference_tokens` include `.json` / `.csv` / `.toml` files? Default: yes (included in activation set). The activation list is part of static tuning, so it can be tightened later by bumping `static_tuning_hash`.

3. Should `vectors_collected[]` entries include a human-readable description? Decision for v0.9: no — keep entries minimal. Revisit in v0.10 if consumers ask.

## 11. Final Statement

v0.9 is the release where the scanner starts being a corpus observer.

The Vector abstraction is the foundation for everything that comes next: corpus-scoped aggregation (v0.10+), customer dictionaries (v0.10+), reactive auto-configuration (v0.11+), eventual schema freeze and v1.0 maturity. Every future vector — built-in or user-configured — inherits the same identity discipline, the same determinism guarantees, the same identity-vs-tuning distinction.

The scanner records. The consumer interprets. The identity digest makes the recording auditable. The corpus, finally, becomes more than the sum of its files.
