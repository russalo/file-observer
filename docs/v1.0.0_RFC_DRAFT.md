# Scanner v1.0.0 RFC Specification (DRAFT)

**Project:** Scanner
**Target Version:** 1.0.0
**Status:** Draft
**Date:** 2026-04-09
**Extends:** v0.4.0 RFC Specification

---

## 1. Overview

### 1.1 Purpose

v1.0.0 is a **schema stabilization release**. It reshapes the manifest for long-term stability before the schema becomes a contract. No new file formats, no new specialists — just fixing the things that will be painful to change after 1.0.

v1.0.0 is the last opportunity to break the manifest shape freely. After this release, schema changes require major version bumps and migration guidance.

### 1.2 Design Principle

> v1.0.0 makes the manifest shape final. Every field, every nesting level, every naming convention is intentional and documented. What ships in 1.0 is what downstream systems can rely on indefinitely.

### 1.3 Version Positioning

| Version | Role |
|---------|------|
| v0.1–v0.4 | Iterative feature development, schema evolving freely |
| v1.0 | Schema freeze + hardening. Shape becomes a contract. |
| v1.1+ | Additive only — new fields, new formats, never remove or rename. |
| v2.0 | Reserved for breaking schema changes (if ever needed). |

### 1.4 Normative Language

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are to be interpreted as described in **RFC 2119** and clarified by **RFC 8174** (BCP 14).

## 2. Schema Changes

### 2.1 Schema Version Field

The manifest MUST include a top-level `schema_version` field.

```json
{
  "schema_version": "1.0",
  "context": { },
  "meta": { },
  "stats": { },
  "routing_summary": { },
  "delta": null,
  "manifest_checksum": "sha256hex...",
  "files": [ ]
}
```

#### Requirements

* `schema_version` MUST be a string in `"MAJOR.MINOR"` format
* `schema_version` MUST be `"1.0"` for this release
* `schema_version` MUST be included in the deterministic checksum preimage
* `schema_version` changes ONLY when the manifest shape changes:
  * MINOR bump: additive changes (new fields, new specialist namespaces)
  * MAJOR bump: breaking changes (field removal, rename, type change)
* Downstream consumers SHOULD use `schema_version` to determine how to parse the manifest

---

### 2.2 Namespaced Specialist Metadata

#### Problem

v0.4 stores all specialist metadata in a flat dict:

```json
{
  "specialist_metadata": {
    "page_count": 5,
    "encrypted": true,
    "subject": "RE: Invoice",
    "width": 1920,
    "sheet_names": ["Summary"]
  }
}
```

This creates collision risk (e.g., a future format with a `title` field that means something different than DOCX `title`), makes it impossible to know which specialist produced which field without reading provenance, and forces consumers to understand the full field set to parse any single format.

#### Resolution

v1.0 namespaces specialist metadata by format category:

```json
{
  "specialist_metadata": {
    "pdf": {
      "has_text_streams": true,
      "page_count": 5,
      "title": "Contract Specs",
      "author": "A. Saadat",
      "producer": null,
      "creator": null,
      "creation_date": null,
      "encrypted": false,
      "pdf_version": "1.4",
      "sample_text_marker_density": 0.00073
    },
    "image": {
      "width": 1920,
      "height": 1080,
      "bit_depth": 8
    },
    "email": {
      "subject": "RE: Project Update",
      "from": "alice@example.com",
      "to": "bob@example.com",
      "date": "2026-03-15T10:30:00",
      "message_id": "<abc123@example.com>",
      "has_attachments": true
    },
    "spreadsheet": {
      "sheet_names": ["Summary", "Detail"],
      "header_rows": {
        "Summary": ["Job", "Status", "Amount"]
      }
    },
    "document": {
      "title": "General Index",
      "author": "Wayne Kimball",
      "word_count": 2400,
      "heading_count": 14
    }
  }
}
```

#### Namespace Registry

| Namespace | Extensions | What it contains |
|-----------|-----------|-----------------|
| `pdf` | `.pdf` | Page count, text streams, doc info, encrypted, version, density |
| `image` | `.png`, `.jpg`, `.jpeg` | Width, height, bit_depth (PNG only) |
| `email` | `.msg`, `.eml` | Subject, from, to, date, message_id, has_attachments |
| `spreadsheet` | `.xlsx` | Sheet names, header rows |
| `document` | `.docx`, `.doc`, `.rtf` | Title, author, word_count (DOCX), heading_count (DOCX) |

#### Rules

* `specialist_metadata` MUST be `null` when specialists are disabled or no specialist applies
* when specialists are enabled and a specialist applies, `specialist_metadata` MUST be an object with exactly one key — the namespace for that file's format
* namespace keys MUST be stable across minor versions
* new namespaces MAY be added in minor versions (additive)
* fields within a namespace MUST NOT be removed or renamed without a major version bump
* field values MAY be `null` (not observed within bounds)

#### Provenance Update

Signal provenance keys for specialist fields change from `specialist_metadata.field` to `specialist_metadata.namespace.field`:

```json
{
  "specialist_metadata.pdf.page_count": {
    "layer": "derived",
    "method": "_pdf_specialist",
    "trigger": "bounded_sample"
  }
}
```

### 2.3 Configurable Baseline Depth

#### Problem

`decode_text()` reads the entire file for text extraction. A 500MB log file gets fully loaded for a 1,000-char preview. This violates the spirit of bounded observation and creates unpredictable memory usage.

#### Resolution

Add `baseline_max_bytes` to `ScannerConfig`:

```python
@dataclass
class ScannerConfig:
    # ... existing fields ...
    baseline_max_bytes: int = 65536  # 64KB default
```

#### Requirements

* `baseline_max_bytes` MUST default to `65536` (64KB)
* `decode_text()` MUST read at most `baseline_max_bytes` from the file for content extraction (preview, tags, structural signals)
* `hash_file()` MUST continue to stream the full file (checksum requires all bytes)
* when a file is larger than `baseline_max_bytes`, the scanner MUST still produce correct signals from the bounded read — preview is truncated, tags from within the window, structural signals from within the window
* `baseline_max_bytes` MUST be recorded in `meta.config` so the manifest documents its own extraction depth
* provenance for `encoding` SHOULD include `detail.bytes_read` when the file was truncated

#### Interaction with sample_size

* `sample_size` (default 8KB) controls the detection buffer — binary detection, encoding inference, specialist extraction
* `baseline_max_bytes` (default 64KB) controls how much text is decoded for content extraction
* `baseline_max_bytes` MUST be >= `sample_size`
* if `baseline_max_bytes` < `sample_size`, the scanner MUST use `sample_size` as the minimum

### 2.4 Error Grouping

#### Problem

`errors` is a flat list with a `stage` field. Consumers must filter by stage to find relevant errors.

#### Resolution

Keep the flat list (backward compatible) but add a convenience accessor. The serialized shape does NOT change — errors remain a flat array with `stage` on each entry. This is a documentation and convention decision, not a schema change.

#### Rationale

Changing `errors` from a flat list to a nested structure would break every consumer. The flat list with `stage` is sufficient — consumers can filter. The convenience of grouped access belongs in client libraries, not the manifest schema.

## 3. Cross-Platform Hardening

### 3.1 CRLF Handling

#### Requirements

* Frontmatter detection MUST handle both `\n` (Unix) and `\r\n` (Windows) line endings
* `FRONTMATTER_RE` and `FRONTMATTER_OPEN_RE` MUST use `\r?\n` in patterns
* PDF text marker detection MUST include `BT\r\n` in addition to `BT\n` and `BT\r`
* all line-based parsing (CSV headers, YAML keys, frontmatter key extraction) MUST normalize line endings before splitting

### 3.2 Path Normalization

#### Requirements

* all path strings in the manifest MUST use forward slashes
* path normalization MUST use `Path.as_posix()` instead of `str.replace("\\", "/")`
* ignore pattern matching MUST work consistently with forward-slash-normalized paths on all platforms

### 3.3 ZIP Entry Validation

#### Requirements

The existing `_is_safe_zip_entry()` MUST be extended to reject:

* drive letter paths (e.g., `C:\evil`, `D:/path`)
* mixed separator traversal (e.g., `foo\../bar`)
* current-directory references (`./`, `/./`)

### 3.4 Hidden File Detection

#### Documentation Requirement

* `exclude_hidden` behavior MUST be documented as Unix-convention only (dot-prefix)
* Windows NTFS hidden attribute detection is explicitly deferred (would require `ctypes` or `pywin32`)
* the limitation MUST be noted in CLAUDE.md and README.md

### 3.5 libmagic on Windows

#### Documentation Requirement

* README MUST document that `python-magic-bin` is the recommended package on Windows
* `ScanContext.dependencies.magic` captures availability — consumers can detect degraded MIME detection

## 4. Silent Failure Fixes

### 4.1 XML Parse Failures

#### Requirements

* when `xml_fromstring()` raises an exception (billion laughs, XXE, malformed XML), the scanner MUST record an `ErrorRecord` with:
  * `code`: `"xml_parse_failed"`
  * `stage`: `"structural"`
  * deterministic message
* `structural.document_keys` MUST be `[]` (already the case)
* the error MUST be recorded whether `defusedxml` or stdlib is used

### 4.2 TOML Parse Failures

#### Requirements

* when `tomllib.loads()` raises an exception, the scanner MUST record an `ErrorRecord` with:
  * `code`: `"toml_parse_failed"`
  * `stage`: `"structural"`

### 4.3 Specialist Null Results

#### Requirements

* when a specialist returns `None` (e.g., olefile unavailable, invalid ZIP, non-OLE file), the scanner SHOULD record an `ErrorRecord` with:
  * `code`: `"specialist_probe_failed"`
  * `stage`: `"specialist"`
  * message explaining why (e.g., "olefile unavailable", "invalid ZIP structure", "not an OLE2 file")

## 5. Provenance Completeness

### 5.1 Required Provenance (unchanged from v0.3)

These fields MUST have provenance:

* `mime_type`
* `encoding`
* `is_binary`
* `requires_vision`
* `requires_specialist_tool`
* `mime_analysis.matches_extension`
* all `specialist_metadata.*` fields when emitted

### 5.2 Recommended Provenance (new)

These fields SHOULD have provenance in v1.0:

* `structural.title` — method varies by format (markdown H1 regex vs HTML `<title>` tag)
* `structural.document_keys` — parser varies (JSON, YAML, XML, TOML)

### 5.3 Provenance Key Format for Namespaced Specialists

Provenance keys MUST use dot-notation matching the namespaced path:

* v0.4: `specialist_metadata.page_count`
* v1.0: `specialist_metadata.pdf.page_count`

## 6. Backward Compatibility Policy

### 6.1 After v1.0

* **Additive changes** (new fields, new specialist namespaces, new supported extensions): MINOR version bump (`schema_version` 1.1, 1.2, ...)
* **Breaking changes** (field removal, rename, type change, nesting restructure): MAJOR version bump (`schema_version` 2.0)
* **Bug fixes and hardening** (no schema change): PATCH version of `SCANNER_VERSION` only; `schema_version` unchanged

### 6.2 Deprecation

* fields MUST NOT be removed without at least one minor version of deprecation notice
* deprecated fields SHOULD emit a warning in `errors` with `code: "deprecated_field"`
* deprecated fields MUST continue to be emitted (possibly as null) until the next major version

### 6.3 Consumer Guidance

Downstream consumers SHOULD:

* check `schema_version` before parsing
* ignore unknown fields (forward compatibility)
* fail gracefully on missing fields (backward compatibility with older manifests)

## 7. Data Model (v1.0 Final Shape)

### 7.1 ScanManifest

```json
{
  "schema_version": "1.0",
  "context": { "ScanContext" },
  "meta": { "ScanMeta" },
  "stats": { "ScanStats" },
  "routing_summary": { "RoutingSummary" },
  "delta": { "DeltaRecord" } | null,
  "manifest_checksum": "sha256hex",
  "files": [ { "FileRecord" } ]
}
```

### 7.2 FileRecord

```
path: str
filename: str
extension: str
mime_type: str
size_bytes: int
created_at: str | null
modified_at: str
checksum_sha256: str
stage_folder: str
directory_depth: int
encoding: str | null
is_binary: bool
requires_vision: bool
requires_specialist_tool: bool
specialist_tool: str | null
sidecar_exists: bool
frontmatter: FrontmatterRecord
tags: list[str]
asset_matches: list[str]
content_preview: str | null
structural: StructuralRecord
mime_analysis: MimeAnalysisRecord
specialist_metadata: NamespacedSpecialistMetadata | null
signal_provenance: dict[str, ProvenanceEntry]
errors: list[ErrorRecord]
```

### 7.3 NamespacedSpecialistMetadata

One key per file, matching the format namespace:

```
pdf: { has_text_streams, page_count, title, author, producer, creator,
       creation_date, encrypted, pdf_version, sample_text_marker_density }
image: { width, height, bit_depth }
email: { subject, from, to, date, message_id, has_attachments }
spreadsheet: { sheet_names, header_rows }
document: { title, author, word_count, heading_count }
```

### 7.4 Unchanged Records

These records are unchanged from v0.4 and are stable:

* `ScanContext` (logic_version, scanner_version, python_version, platform, dependencies)
* `ScanMeta` (scan_id, generated_at, source_dir, config)
* `ScanStats` (total_files, supported_files, unsupported_files, text_files, binary_files, requires_vision, requires_specialist_tool)
* `RoutingSummary` (baseline_ready, binary_only, requires_vision, requires_specialist_tool)
* `DeltaRecord` (previous_scan_id, added, modified, unchanged, removed, rescan_candidates)
* `FrontmatterRecord` (exists, keys, raw)
* `StructuralRecord` (title, heading_structure, csv_headers, document_keys, technology_hints, filename_date)
* `MimeAnalysisRecord` (detected_mime, extension_mime, matches_extension)
* `ErrorRecord` (code, message, stage)
* `ProvenanceEntry` (layer, method, trigger, inputs, detail)

## 8. Implementation Order

### Phase 1 — Schema Shape

1. Add `schema_version: "1.0"` to ScanManifest
2. Namespace `specialist_metadata` (pdf/image/email/spreadsheet/document)
3. Update provenance keys for namespaced specialists
4. Update all tests for new shapes

### Phase 2 — Bounded Baseline

5. Add `baseline_max_bytes` to ScannerConfig (default 64KB)
6. Cap `decode_text()` reads
7. Record bytes_read in provenance detail

### Phase 3 — Cross-Platform Hardening

8. CRLF in frontmatter regex and PDF markers
9. `as_posix()` path normalization
10. ZIP entry validation (drive letters, mixed separators)
11. Document platform limitations

### Phase 4 — Silent Failure Fixes

12. XML parse error recording
13. TOML parse error recording
14. Specialist null result error recording

---

## 9. Acceptance Criteria

v1.0.0 is complete when:

* `schema_version` is present and set to `"1.0"`
* `specialist_metadata` is namespaced by format category
* `baseline_max_bytes` caps text extraction with configurable depth
* frontmatter detection handles CRLF
* PDF text markers handle CRLF
* paths use `as_posix()` normalization
* ZIP entry validation rejects drive letters and mixed traversal
* XML/TOML parse failures produce error records
* all provenance keys match namespaced specialist paths
* backward compatibility policy is documented
* all existing tests pass with updated assertions
* cross-platform limitations are documented

---

## 10. Summary

v1.0.0 is not about adding features. It's about making the shape right before it becomes permanent. Namespace the specialists so they don't collide. Cap the reads so they don't surprise. Fix the line endings so Windows works. Record the failures so nothing is silent. Add the schema version so consumers know what they're reading.

After 1.0, the manifest is a contract. This is the last chance to change the contract for free.

---

## 11. Final Statement

v1.0.0 is successful if, five versions from now, nothing we did in 1.0 needs to be undone. The schema should be boring — predictable, stable, and obvious. The exciting work happens in the formats we add and the depth we reach, not in the shape of the manifest.
