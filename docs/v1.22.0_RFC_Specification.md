# v1.22.0 RFC — content-aware recognition for BINARY (complete the v1.21 arc)

> **Status: SHIPPED** — released as v1.22.0 (see `docs/HISTORY.md` for the date and the patch releases that rode on this minor). Any status line below reflects the RFC's state at approval time and is kept as written.

**STATUS: APPROVED 2026-06-19 (Russell).** Decisions §6 resolved: **A-alone** (puresniff signature
fold-in deferred to a separate measured slice); **single-source `supported` counter** (refined in
implementation to *not-flagged AND not-stat-failure* — the v1.9.1 carve-out); **no binary veto**.
Implemented falsify-first; see `COMPLIANCE-v1.22.md`.

## 1. Why (the data)

v1.21.0 made `unsupported_extension` mean *"couldn't identify it"* — but only for **text**.
The candidate-scout (2026-06-17, `scratch/scout_2026-06-17.md`, 11 corpora / 19,488 files) showed
the diagnostic still cries wolf on **binary**: **944 of 1,119 `unsupported_extension` flags are on
files with a POSITIVELY-IDENTIFIED content MIME** (`application/zip` 412, `audio/mpeg`, `image/vnd.dwg`,
`video/x-msvideo`, office/ODF, …) — only ~175 are genuinely `application/octet-stream`. So a `.avi`
that libmagic typed `video/x-msvideo` is flagged "couldn't identify it," which is false: we identified
it, we just don't *extract* from it. This is the same wolf-cry v1.21 fixed for text, left half-done.

**Recognition ≠ extraction** (the v1.15.1/v1.21.0 pattern): no new parser, no new field, no new
extraction. A recognized `.avi` still has `requires_specialist_tool=False` and no metadata — it just
stops being mislabeled unidentifiable + miscounted *degraded*.

## 2. The change (grounded in the live v1.21.0 gate)

Current gate (scanner.py:3069):
```python
recognized_text = (
    _is_recognized_text(mime_type)
    and mime_prov.trigger != "extension_fallback"
    and not read_failed
    and (_detect_unicode_bom(sample) is not None or self.looks_like_text(sample))
)
if extension not in SUPPORTED_EXTENSIONS and not recognized_text:
    # emit unsupported_extension
```

Proposed unified gate — "recognized = content positively identified the file":
```python
content_identified = (
    bool(mime_type)
    and mime_type != "application/octet-stream"     # octet-stream = NOT identified → keep flag
    and mime_prov.trigger != "extension_fallback"   # content-derived (libmagic / sniff), NOT /etc/mime.types
    and not read_failed                             # no readable content → no positive ID
)
# text MIMEs keep the v1.21 lying-text/plain veto; binary signature-IDs need no veto
recognized = content_identified and (
    not _is_recognized_text(mime_type)
    or _detect_unicode_bom(sample) is not None
    or self.looks_like_text(sample)
)
if extension not in SUPPORTED_EXTENSIONS and not recognized:
    # emit unsupported_extension
```

**Why no binary veto (unlike text):** the text printable-ratio/BOM veto exists because `text/plain`
is libmagic's loose catch-all (it calls NUL-bearing bytes `text/plain`). A *binary* MIME
(`video/x-msvideo`, `application/zip`) is a **content signature match** — a positive ID by
construction. Even a slightly-wrong binary MIME (the v1.15 HEIC-as-`video/mp4` class) still means
"identified as *something*," which is the only thing `unsupported_extension` should care about.

**Behavior preserved + extended (truth table):**
| input | trigger | mime | v1.21 | v1.22 |
|---|---|---|---|---|
| recognized text (BOM/printable ok) | libmagic | text/* | recognized | recognized (same) |
| lying text/plain over NULs | libmagic | text/plain | flagged | flagged (veto, same) |
| **binary, identified** | **libmagic/sniff** | **video/x-msvideo** | **flagged** | **recognized (NEW)** |
| genuinely unknown | libmagic | octet-stream | flagged | flagged (kept) |
| no-libmagic, no sniff match | extension_fallback | (ext guess) | flagged | flagged (§6.2a kept) |
| read_failed | any | any | flagged | flagged (kept) |

## 3. The second load-bearing fix — the supported counter (the v1.21 leg-1 lesson)

`_compute_stats` (scanner.py:2740) currently re-derives supported as
`not-flagged AND (ext in SUPPORTED or _is_recognized_text(mime))`. Under v1.22 a recognized **binary**
is `not-flagged` but `_is_recognized_text=False` → it would be **under-counted as not-supported** —
a drift bug. Fix: make supported the **single source of truth** = `not any(e.code ==
ERR_UNSUPPORTED_EXTENSION ...)`. Drop the re-derivation entirely (it can only drift from the gate).
This is exactly the v1.21 leg-1 catch, applied one level up.

## 4. Acceptance bar (falsify-first — write the corpus FIRST, try to break the premise)

1. **Binary recognized:** `.avi`→`video/x-msvideo`, a bare `.zip`→`application/zip`, `.mp3`→`audio/mpeg`
   → NOT flagged `unsupported_extension`, counted **supported**. (Were flagged in 1.21.)
2. **Genuinely unknown still flagged:** an `application/octet-stream` blob → still `unsupported_extension`.
3. **Extension-fallback still flagged (§6.2a):** force no-libmagic; a binary `_sniff_mime` can't match →
   `extension_fallback` MIME → still flagged. (Recognition rests on CONTENT, never `/etc/mime.types`.)
4. **Lying text/plain over NULs still flagged:** the v1.21 veto is untouched.
5. **read_failed still flagged.**
6. **Text behavior byte-identical to v1.21** (all `test_v1_21` cases still pass unchanged).
7. **Extraction byte-identical:** a recognized `.avi` keeps `requires_specialist_tool=False`, no
   `video.*` metadata, identical `specialist_metadata`. Recognition ≠ extraction.
8. **Counters reconcile:** on a corpus with recognized binaries, `supported` rises / `degraded` falls,
   matching the gate (single source of truth); `clean` unaffected.
9. **Determinism:** `manifest_checksum` stable; **workers=1-vs-N byte-identical** (Layer-A gate).
10. **Corpus sweep re-baselined:** the EXPECTED large `unsupported_extension`-drop (~944 across the
    scout corpora) + `supported`/`degraded` shift, NO other drift. Mirrors the v1.21 re-baseline.

## 6. Open decisions (gate this draft — for Russell)
1. **Scope: A-alone vs A + the puresniff signature fold-in.** A-alone fully fixes the **libmagic path**
   (the common case — libmagic IDs the 944). The puresniff expanded `MAGIC_SIGNATURES` would extend the
   **no-libmagic path** (more binaries content-ID'd by `_sniff_mime` instead of falling to
   extension_fallback → flagged). **Lean: A-alone this minor** — keep it clean recognition-only; the
   signatures are a separate measured/oracle-gated slice (their own LOGIC change, v1.3 precedent). The
   no-libmagic binary gap is then an accepted §6.2a-style residual (consistent with v1.21's no-libmagic text gap).
2. **supported counter: single-source-of-truth (drop the re-derivation) vs extend it.** Lean
   single-source — drift-proof, and the re-derivation can't see `trigger`/`read_failed` anyway.
3. **Any binary veto?** Lean **no** (§2 reasoning). Falsify-first will test whether a real corpus
   surfaces a "lying binary MIME" that argues otherwise.

## 7. Out of scope
- New extraction / specialists (that's Candidate B — `.pptx`/`.odt`/`.mp3` parsing). v1.22 is recognition only.
- The puresniff signature expansion (decision §6.1 — separate slice if deferred).
- Any change to text recognition (v1.21 behavior preserved exactly).
