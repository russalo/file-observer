# File Observer v1.20.0 RFC Specification — video QuickTime creation date

> **Status: IMPLEMENTED 2026-06-16** (pending PR + review). `video.creation_date_qt` ships;
> oracle-exact vs `exiftool` on the iPhone 11 + 16 Pro Max clips (TZ preserved), distinct from
> the mvhd `creation_date`. SCANNER 1.20.0 / LOGIC 1.10.0 / SCHEMA 1.13. 1018 tests.
>
> *(Original.)* Executes the v1.18 §8 Q3 revisit candidate (deferred
> there as "if added, a separate field, observe-don't-reconcile"), now justified by a
> concrete finding (below). A small additive minor: one new `video` field.

## 1. Motivation

v1.17 set `video.creation_date` from the ISOBMFF `mvhd` creation_time (UTC, no timezone).
Apple video ALSO carries `com.apple.quicktime.creationdate` (a QuickTime key in
`moov`→`meta`→`keys`/`ilst`) — an **ISO-8601 string with the capture timezone**, and the
**truer capture moment**.

**The finding that motivates promoting it now (the v1.16-class "real data taught us"):**
investigating an AirDropped clip showed the two timestamps disagree — the iPhone-11 clip's
`mvhd` time was `2026-06-16T12:31:28Z` (file finalization) while its `creationdate` key was
`2026-06-16T05:25:55-07:00` (= `12:25:55Z`, the actual shutter moment). The gap appears on
non-AirDropped clips too (~3 min on the iPhone-16), so `mvhd` is *when the file was
written/finalized*, not *when it was captured* — and it can be perturbed by save/transfer
operations. The `creationdate` key holds the capture moment **with timezone**, which `mvhd`
lacks entirely. Both are real observations; a consumer wants both.

## 2. Scope

**IN:** a new field **`video.creation_date_qt`** — the raw value of the
`com.apple.quicktime.creationdate` key (an ISO-8601 string *with* offset, e.g.
`2026-06-16T05:25:55-0700`), or null when absent. Apple `.mov`/`.mp4` (the keys mechanism
v1.18 already reads).

**OUT:**
- **No reconciliation.** `creation_date_qt` is a SEPARATE field — it is NEVER merged with
  `creation_date`, and `creation_date` (mvhd/UTC) is unchanged (observe-don't-reconcile, the
  PDF-`/Info` lesson; both sources reported, the consumer decides). v1.17's `creation_date`
  stays exactly as-is.
- No normalization/reinterpretation of the string — observe-as-is (it's already valid
  ISO-8601; reformatting it would risk misreading the offset).
- Non-Apple/Android creation dates (different mechanism) — out of scope (with the Android
  GPS work, §ref v1.18 Q1).

## 3. Design

`_parse_moov` already builds the QuickTime keys dict (`_qt_keys`) for make/model. Add one
lookup: `keys.get(b"com.apple.quicktime.creationdate")` → `_qt_text(...)` → `creation_date_qt`.
No new I/O, no new parse path, no new dependency. Both `meta` forms (QuickTime `.mov` +8 /
ISO `.mp4` +12) already handled by `_meta_child_start`.

## 4. Validation

- **Oracle:** the field must match `exiftool`'s `CreationDate` (Keys) on the real iPhone
  corpus (4 clips: iPhone 11 + 16 Pro Max, gps + nogps — all carry the key). Byte-exact on
  the value's instant.
- **Committable synthetic fixture:** add a `creationdate` key to `video_qt_gps.mov` /
  `video_qt_nogps.mov` so CI exercises the field (the real clips are gitignored).
- **Falsify-first** (`test_v1_20.py`): key present → field set (raw, TZ preserved); key
  absent → null; `creation_date` (mvhd) unchanged from v1.17; determinism; workers
  byte-identical; the no-key case doesn't crash.

## 5. Versioning

- SCANNER 1.19.0 → **1.20.0**.
- **LOGIC 1.9.0 → 1.10.0** — a new extracted value.
- **SCHEMA 1.12 → 1.13** — a **new field** `video.creation_date_qt` (a contract-shape change,
  unlike a new value of an existing field). `docs/SCHEMA.md` regenerated.

## 6. Note

This is the cleanest possible minor: one field, one key lookup, design pre-settled in v1.18
§8, validated against a 4-clip real corpus + a synthetic fixture. It also models the
observe-don't-reconcile discipline cleanly — two capture timestamps, both surfaced, neither
overriding the other.
