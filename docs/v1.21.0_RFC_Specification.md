# File Observer v1.21.0 RFC Specification — recognize text content (stop mislabeling it "unsupported")

> **Status: IMPLEMENTED (SCANNER 1.21.0 / LOGIC 1.11.0 / SCHEMA 1.13).** §6 resolved → Option B
> (content-aware) + no-libmagic gap accepted (a). The recognition gate is
> `_is_recognized_text(mime) AND looks_like_text(sample)` (binary-veto for a lying MIME), and the
> `supported` count is derived from the emission decision (single source of truth). From the v1.20 candidate scan:
> ~9,000+ files across the corpora are flagged `unsupported_extension` even though they're
> plain text the scanner already observes (preview, encoding, reference_tokens) and libmagic
> identifies as `text/*`. The diagnostic is firing on *recognized text* — a false "I don't
> know this." This release stops that. **No new extraction** — pure recognition (the v1.15.1
> pattern: recognize ≠ extract).

## 1. Motivation

`unsupported_extension` fires whenever a file's extension isn't in `SUPPORTED_EXTENSIONS`.
But a `.py` / `.java` / `.ts` / `.ini` / `.rst` / `.sql` / `.svg` file IS handled — it goes
through the full text baseline tier — it just isn't *listed*. The candidate scan (19,508
files) found the top "unsupported" extensions are overwhelmingly **source / config / docs
text** that libmagic types as `text/x-script.python`, `text/x-java`, `text/x-c`, etc. The
flag is noise on recognized content, and it inflates the `degraded` quality count.

## 2. Scope

**IN:** stop emitting `unsupported_extension` for files that are **recognized as text**, so
they count as *supported / clean*, not *unsupported / degraded*. Which mechanism decides
"recognized as text" is the §6 fork.

**OUT:**
- **No new specialist / extraction.** These files still get exactly the text baseline they
  already get (preview, encoding, tags, reference_tokens, filename_patterns). Recognition
  only — nothing new is parsed.
- No change for genuinely-unidentified files (octet-stream / unknown binary) — they keep
  `unsupported_extension`. The diagnostic stays meaningful; it just stops crying wolf on text.
- No new fields (SCHEMA shape unchanged); this is a routing/diagnostic change → LOGIC.

## 3. The two designs (§6 fork)

**Option A — curated extension list.** Add a vetted set of common source/config/doc text
extensions to `SUPPORTED_EXTENSIONS` (e.g. `.py .java .ts .tsx .js .c .h .cpp .hpp .cmake
.ini .conf .properties .sql .sh .ps1 .rst .adoc .svg .ipynb .swift .m .mm`). Explicit and
conservative — but a *maintenance list that's always incomplete* (the long tail —
`.effect`, `.idl`, `.j2`, hundreds more — stays flagged), and it's not content-aware (a
`.py` full of binary would still be "recognized").

**Option B — content-aware recognition (lean).** `unsupported_extension` no longer fires
when the file's **content** is identified as text (content MIME `text/*`, or the known
text application types like `application/json` / `javascript` / `xml` / `svg+xml`). One
principled rule, content-first (the scanner's whole philosophy), **complete** (every text
file is recognized, no list to maintain), and *honest* (it recognizes by what the bytes
are, not by a label). The diagnostic then means "couldn't identify it," not "extension not
in our hand-list."
- Trade: it's a **semantic shift** to `unsupported_extension` — from "extension not listed"
  to "not identifiable." The `supported`/`degraded` counters move for any text-with-unlisted-
  extension (a one-time, expected re-baseline).

## 4. Validation
- Falsify-first (`test_v1_21.py`): `.py`/`.java`/`.svg`/etc. no longer carry
  `unsupported_extension` and count as supported; a genuinely-unknown binary still does;
  text baseline output unchanged; determinism; workers byte-identical.
- Corpus sweep: a large, **expected** drop in `unsupported_extension` + rise in
  `supported`/`clean` — review it, re-baseline. Confirm no *other* drift (the actual
  per-file text observations are unchanged).

## 5. Versioning
- SCANNER 1.20.0 → **1.21.0**.
- **LOGIC 1.10.0 → 1.11.0** — `unsupported_extension` routing + the supported/degraded
  counters change (an observed-value change).
- **SCHEMA unchanged 1.13** — no new field; `unsupported_extension` is an existing error
  code, just emitted on fewer files.

## 6. Open question — RESOLVED at sign-off 2026-06-16 (Russell)
1. **Option B (content-aware).** `unsupported_extension` no longer fires when the file's
   content is identified as text (`text/*` MIME + the known text application types). The
   diagnostic now means "couldn't identify it," not "extension not in our list." One-time
   counter re-baseline accepted.
   - **Empty files (validation addendum):** a zero-byte file is typed `inode/x-empty` by
     libmagic — a positive identification, not "unidentifiable" — so it's recognized too
     (an empty `__init__.py`/`py.typed` decodes cleanly as the empty string; never binary).
     Dropped the fastapi residual from 186 to 4 (all genuine git binaries; 0 text misses).
2. **No-libmagic path → (a) accept the gap.** On the fallback (no libmagic), the pure-Python
   sniff only types binary signatures, so signatureless text isn't content-typed as `text/*`
   and stays flagged — kept as-is for v1.21 (already a documented fallback limitation; not
   worth a special "decoded-cleanly-as-text" heuristic now).

### (superseded) original fork
1. **Option A (curated extension list) vs Option B (content-aware "is it text?")** — *Lean:
   **B***. It's the content-first, complete, maintenance-free fix and makes
   `unsupported_extension` mean something useful ("couldn't identify"), at the cost of a
   one-time counter re-baseline. A is safer/smaller but a perpetual incomplete list. (A
   hybrid — B as the rule, plus keeping a few extensions explicitly listed for the
   no-libmagic fallback where content typing is weaker — is possible; note if you want it.)
2. **No-libmagic path:** under B, recognition leans on content MIME; without libmagic the
   pure-Python sniff doesn't type prose as `text/*` (only binary signatures). So on the
   fallback path, signatureless text still wouldn't be "recognized" by content alone — do we
   (a) accept that (fallback stays as-is, honest), or (b) treat "decoded cleanly as text +
   no binary signature" as recognized? *Lean: (a) for v1.21* — keep it simple; the
   no-libmagic text-recognition gap is a documented fallback limitation already.
