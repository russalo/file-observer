# v1.32.0 RFC (DRAFT) — generic kv-fact-block specialist (FR #114)

> **Status: SHIPPED** — released as v1.32.0 (see `docs/HISTORY.md` for the date and the patch releases that rode on this minor). Any status line below reflects the RFC's state at approval time and is kept as written.

**STATUS: DRAFT — pending Russell's approval.** A new content-detected specialist that emits the
observed `key: value` pairs in a file's body as per-file signals. Measure-first (§3) done. On approval
this becomes `docs/v1.32.0_RFC_Specification.md`.

## 1. Summary

When a scanned text file's **body** is dominated by `key: value` lines, emit those pairs — **verbatim,
generic, deterministic** — as a new provisional `fact_block` specialist namespace. fo observes the
pairs; the consumer decides what they mean. This is the same family as `is_chatlog` / `frontmatter` /
`reference_tokens`: a content-shape observation, not a per-consumer format reader.

## 2. Motivation

FR **file-observer#114** (recall, steward): Blueprint's db-corpus renders its records (edges, agents,
services, flags, dns-records, ports) as markdown with a **flat `key: value` body** — but fo's markdown
path maps only *frontmatter* to attrs, so the body (`source: bestiary / target: puresniff / kind:
oracle / status: active`) is FTS-only prose. The federation graph sits **unqueryable** in the body.
A generic fact-block reader makes it queryable end-to-end (Blueprint DB → markdown → fo signals →
trellis attrs+edges → recall) with **zero new trellis capability**.

**recall's pinned consumer contract** (2026-07-03): needs ONLY (1) pairs verbatim, (2) deterministic
order + dedup, (3) a per-file presence signal. **No classification / validation / normalization** —
recall wants the interpretation on *its* side; a schema-aware fo would be a second place to drift when
Blueprint's schema evolves. recall asked me to push back if this RFC ever grows classify/validate.

## 3. Measure-first (`scratch/measure_kv_fact_block.py`, 2026-07-04)

The design question is FP-hygiene: `key: value` collides with dialogue (`Alice: I went to the store`),
the shape the chatlog detector spent a dozen releases suppressing. The gate must fire on fact-blocks
and NOT on prose or dialogue. Measured on real corpora:

| corpus | shape | gate fires |
|---|---|---|
| Blueprint db-corpus (497 md) | real fact-blocks | **497/497 (100%)** — no false negatives |
| Blueprint kb-corpus (397 md) | prose | **0/397 (0%)** |
| ConvoKit → `Speaker:` markdown (60) | dialogue | **0/60 (0%)** |
| same dialogue, **veto OFF** | dialogue | **60/60 (100%)** — the collision |

The **body-kv-ratio** separates cleanly: positives sit at 1.00, prose maxes at 0.47. The load-bearing
piece is the **sentence-value veto** — without it dialogue is a 100% FP; with it, dialogue → 0% while
fact-blocks stay 100%.

## 4. The change

### 4.1 Detection gate (content-shape, the `is_chatlog` precedent)
On a text-eligible file, over the **body with frontmatter stripped** (frontmatter is already extracted;
including it would make every doc trip the gate — §3's key structural finding), counting only non-blank
**non-structural** lines (exclude markdown headings `#`, blockquotes `>`, fences ```` ``` ````, tables `|`):

- a line is a **fact-pair** iff it matches `^\s*-?\s*[A-Za-z][A-Za-z0-9_. -]{0,63}:\s+\S` **AND** its
  value is not sentence-like (the **veto**: reject if the value has a function word AND (≥5 words OR
  ends in `.?!`) — a fact value is data, a dialogue/prose value is a sentence);
- fire `is_fact_block` iff **DISTINCT fact-pairs ≥ 3 AND fact-lines / content-lines ≥ 0.6 AND the MIME
  is a trusted text type** (`text/plain`/`text/markdown`/`text/x-markdown`/`text/html`).

**Distinct-key gate (cross-model review):** a fact-block is a RECORD of DISTINCT facts, so firing is
gated on the *distinct-key* count, not raw matched lines. This rejects degenerate repeated-key LISTS
(a FAQ's `Q:`/`A:`, `id:1/id:2/id:3`) and makes firing consistent with the emitted (deduped) pair count.
(A body of ≥3 *distinct* `key: value` lines fires regardless of the author's semantic intent — a
changelog, a config, a record are all structurally kv-blocks; observe-don't-interpret.)

**MIME-coherence gate (cross-model review + corpus sweep):** `is_fact_block` requires a trusted text
MIME, so the flag is coherent with extraction (never flag-without-pairs) and a source file libmagic
types non-text (a `.py` of `field: Type` annotations → `text/x-script.python`) never flags. `text/html`
is trusted because libmagic mis-types some kv-block `.md` as html (angle-bracket values); real HTML
markup is not kv-dominated so it stays below the ratio.

Runs in the baseline tier like chatlog detection (even with `enable_specialists=False`, the flag fires;
the pair *extraction* is specialist-gated). Bounded (§6). The rule set feeds the vector `rules_hash`
(the determinism contract — a gate/veto/threshold edit MUST move the digest).

### 4.2 What it emits (specialist tier)
A new provisional `fact_block` namespace, emitting the OBSERVED pairs **generically** — whatever keys
appear, verbatim, **first-occurrence order** (deterministic; the source order the author wrote), never
a Blueprint key-schema. Proposed shape (field names = **co-design with recall**, §7):
```
"fact_block": {
  "pair_count": 7,
  "pairs": [ {"key": "source", "value": "bestiary"}, {"key": "kind", "value": "oracle"}, … ]
}
```
- **Generic only** — the bright line recall pinned: no key allow-list, no validation, no normalization.
  fo never knows what `edge`/`source`/`kind` *mean*.
- **Dedup policy (§7 decision):** keep a repeated key's **first** occurrence + a `duplicate_keys` count,
  OR keep all as an ordered list. Blueprint records have unique keys; general kv-blocks may repeat.

## 5. FP-hygiene / coherence with chatlog

The veto (§4.1) is the mechanism; §3 proves it holds on real dialogue. recall **narrowed the scope**
(2026-07-03): it does NOT need fo to *arbitrate* dialogue-vs-fact-block — its target is `.md` KB trees;
if a file lands as both `is_chatlog` and `is_fact_block`, recall reads the pairs and ignores the
classification. So the RFC's job is fo-internal **FP-hygiene** (don't re-admit the `Key:value` noise
chatlog suppressed), NOT a unified/arbitrating detector. The two detectors stay independent; the veto
keeps the fact-block gate from firing on the dialogue the chatlog gate claims. A standing falsify-first
battery (§8) tests the gate against dialogue / FAQ / changelog / config to keep it honest.

## 6. Bounded / never-crash discipline (v1.8.1 + v1.30.2 ReDoS)

A new extractor over untrusted text carries the bar from commit one: cap fact-pair count
(`FACT_BLOCK_MAX_PAIRS`), cap key length (≤64) and value length (bounded, e.g. ≤4096 = PATH_MAX-class),
the kv/veto regexes are **anchored + linearly bounded** (added to `test_regex_redos_hardening.py`'s
all-regex battery), read within `baseline_max_bytes`, deterministic order + dedup. Never raises → an
unreadable/oversized body degrades to no fact-block, never a crash.

## 7. Decisions for approval (forks)

1. **Namespace + field names** — `fact_block` with `{pair_count, pairs:[{key,value}]}` proposed;
   **co-design the exact names with recall** at build time (recall consumes behind its own RFC). Not
   pre-locked to trellis's shape (that mapping is recall's).
2. **Dedup policy** — (a) first-occurrence + `duplicate_keys` count [recommended: simplest, deterministic,
   fits Blueprint's unique-key records] vs (b) keep-all-as-ordered-list [lossless for repeat-key blocks].
3. **Scope of "text file"** — content-shape means it also fires on a `.env`/`.ini`/`.properties`-style
   body that IS a kv-block. That's arguably *correct* (they are fact-blocks), but flag it: do we gate to
   `text/markdown` + plain text, or embrace any text body? [recommended: any text body — it's a generic
   observation; `.yaml`/`.toml`/`.json` already have `document_keys` and keep it.]
4. **Threshold** — ratio ≥ 0.6, pairs ≥ 3 (from §3; the separation is wide enough that 0.5–0.8 all give
   identical results, so 0.6 is safe and not knife-edge).

## 8. Acceptance bar (falsify-first — `tests/test_v1_32.py`)

1. Fires on a body-dominant fact-block (frontmatter-stripped); emits pairs verbatim, first-occurrence order.
2. Does NOT fire on prose, on dialogue (`Speaker:` lines — the veto), on a FAQ (`Q:`/`A:`), on a changelog
   (`Added:`/`Fixed:`), or on a file whose only kv-lines are frontmatter.
3. Generic: emits whatever keys appear; NO Blueprint-specific key handling anywhere.
4. Bounded: hostile inputs (10⁵ pairs, 10⁶-char value, pathological `:` spam) stay capped + never crash;
   the kv/veto regexes pass the ReDoS battery.
5. Deterministic: two scans byte-identical; the `fact_block` vector `rules_hash` moves iff the gate edits.
6. Corpus: 497/497 db-corpus fire, 0/397 kb-corpus, 0 dialogue (the §3 result, as a committed check where
   the corpora are available; else the fixture-level equivalents).

## 10. Out of scope / accepted residuals

- Any interpretation of the pairs (graph edges, agent lanes) — recall's side, behind its own RFC.
- Key validation / normalization / a Blueprint schema — the bright line; never in fo.
- Emitting frontmatter pairs (already handled) — the specialist targets the body only.
- **Accepted residual — prose-value FN (cross-model review #4):** a fact-block whose values are majority
  sentence-like (e.g. a record of long `summary`/`description` fields) may not fire — the veto removes
  those lines, dropping the ratio. The `≥0.6` ratio tolerates up to 40% such lines; measure-first showed
  0 FN on 497 real Blueprint records. Documented, not fixed — tightening the veto re-admits dialogue FPs.
- **Accepted residual — code kv-literals (corpus sweep):** a source file that is structurally a
  `key: value` block AND libmagic types `text/plain` (e.g. a Pygments style dict `TokenType: '#color'`)
  can fire — it is genuinely indistinguishable from a fact-block (observe-don't-interpret). Sweep-measured
  at ~0.1% in a code-heavy repo, 0 in recall's markdown target. No code-specific heuristic added.
