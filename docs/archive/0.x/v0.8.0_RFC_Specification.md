## 1. Overview

### 1.1 Purpose

v0.8 introduces the **chatlog specialist** — drift-visible signal extraction for conversation logs, knowledge management archives, and any structured text where patterns emerge over a corpus rather than within a single file.

The scanner remains per-file. Drift exists in the data whether the scanner sees it or not. This release makes the per-file signals rich enough that a stateful consumer can detect drift across batches without the scanner needing memory.

> The scanner is the scribe. It records what happens as it happens. The drift is what the reader notices when they reread the records.

### 1.2 Design Principle

> Every chatlog signal is something a stateful consumer can diff between files. Counts, sets, distributions, bounded token samples — never narrative, never interpretation.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 2. The Chatlog Specialist

### 2.1 Background

The scanner already extracts metadata from images, documents, spreadsheets, and emails. v0.8 adds a specialist for **structured text with conversational or document-evolution patterns** — chat logs, journals, AI conversation archives, RPG session notes, knowledge management vaults, training data corpora, and legacy document folders where structure has emerged organically over time.

This is the scanner's first specialist whose primary value is **inter-file**. Each file's signals are independent, but the signals themselves are designed so a downstream consumer with memory across files can detect:

* New entities appearing
* Vocabulary growth
* Structural maturation (when ad-hoc text develops headers/sections)
* Speaker pattern shifts
* Reference graph emergence

### 2.2 Classification

* `is_binary`: false (text-decodable)
* `requires_specialist_tool`: true (when chatlog pattern detected)
* `specialist_tool`: `"chatlog_signals"`
* Namespace: `chatlog`

### 2.3 Detection

The chatlog specialist activates for `.txt`, `.md`, and `.mdx` files when **content patterns** suggest conversational or document-evolution structure. It does NOT activate based on extension alone.

Detection rules (any one triggers activation):

1. Three or more lines matching `^([A-Z][a-zA-Z0-9_]{0,15}):\s` (speaker label pattern)
2. Three or more occurrences of `### ` headers in the sample
3. Three or more `---` section dividers in the sample

Files matching none of these get standard baseline/structural processing without the chatlog specialist.

**Rules vs. tuning.** The three rules above *define* the chatlog vector — they are the answer to "what counts as a chatlog?" The threshold of `3` is *tuning* — sensitivity of that definition. In v0.8 both ship hardcoded. When vector fingerprints land in v0.9/v0.10, the rule set becomes part of the vector identity (`vector_id`) and the thresholds become part of its configuration (`config_hash`). Changing a threshold from 3 to 4 will be a re-tuning of the same vector, not a new one. This is the first content-classification vector in the scanner and the first place this distinction needs to be drawn cleanly.

### 2.4 Specialist Metadata

```json
{
  "chatlog": {
    "turn_count": 45,
    "speaker_labels": ["Assistant", "User"],
    "section_marker_count": 8,
    "section_marker_styles": ["---", "### "],
    "avg_turn_chars": 247,
    "max_turn_chars": 1840,
    "min_turn_chars": 12,
    "reference_tokens": {
      "at_mentions": 12,
      "wiki_links": 3,
      "code_fence_blocks": 7,
      "url_count": 2
    },
    "top_capitalized_tokens": ["Sentinel", "Russell", "DM", "Player", "Magic"],
    "capitalized_token_count": 34,
    "vocabulary_size_estimate": 482
  }
}
```

### 2.5 Field Definitions

| Field | Type | Derivation |
|---|---|---|
| `turn_count` | int | Number of speaker label occurrences in sample |
| `speaker_labels` | sorted list[str] | Distinct speaker labels found, sorted alphabetically |
| `section_marker_count` | int | Total section divider occurrences |
| `section_marker_styles` | sorted list[str] | Distinct divider styles (`---`, `===`, `### `, etc.) |
| `avg_turn_chars` | int | Average characters between speaker labels |
| `max_turn_chars` | int | Longest turn in sample |
| `min_turn_chars` | int | Shortest turn in sample |
| `reference_tokens.at_mentions` | int | `@[a-zA-Z0-9_]+` count |
| `reference_tokens.wiki_links` | int | `\[\[.+?\]\]` count |
| `reference_tokens.code_fence_blocks` | int | Triple-backtick block count |
| `reference_tokens.url_count` | int | URL count (http/https) |
| `top_capitalized_tokens` | list[str] | Top N capitalized tokens by frequency, sorted by frequency desc, secondary alphabetical. N=20 default. |
| `capitalized_token_count` | int | Total distinct capitalized tokens (length 3+) |
| `vocabulary_size_estimate` | int | Approximate distinct lowercase token count in sample |

### 2.6 Extraction Rules

* All extraction operates on the bounded text returned by `decode_text()` (respects `baseline_max_bytes` and per-extension overrides)
* Speaker label regex: `^([A-Z][a-zA-Z0-9_]{0,15}):\s` at line starts
* A token must repeat 3 or more times within the sample to count as a speaker label (eliminates one-off proper nouns)
* Capitalized tokens must be length 3+ and appear 3+ times to count
* Section markers detected as lines matching `^([-=*#]{3,})\s*$` or `^(#{1,6})\s+`
* All counts are bounded to the decoded text — no streaming, no full-file reads

### 2.7 What This Specialist Does NOT Do

* No NLP, POS tagging, or entity recognition
* No conversation summarization
* No language detection
* No sentiment analysis
* No cross-file comparison (that's the consumer's job)
* No interpretation of what speakers/entities/references *mean*

The scanner reports tokens. The consumer decides what they are.

## 3. Drift Visibility

### 3.1 Why Per-File Signals Carry Drift

The scanner is stateless. Each file is scanned independently. But every field in `chatlog` is designed so a stateful consumer (an ingestor with memory) can compute drift by diffing files in date order:

| Drift question | How the consumer answers it |
|---|---|
| Is a new speaker appearing? | Set diff of `speaker_labels` between consecutive files |
| Is the corpus introducing new entities? | Running union of `top_capitalized_tokens` across files |
| Are conversations getting longer? | Rolling average of `avg_turn_chars` over time |
| Is structure maturing? | `section_marker_count` trending up |
| Are references emerging? | `reference_tokens` totals trending up |
| Is vocabulary growing? | `vocabulary_size_estimate` trending up |
| Are templates standardizing? | `section_marker_styles` set converging across files |

The scanner doesn't compute drift. It produces the primitives that make drift visible to whoever reads the manifest.

### 3.2 Connection to Existing Features

* **`mime_analysis.matches_extension`** — drift in file conformance over time
* **`is_polyglot`** — drift in file complexity
* **`safety_flags`** — drift in risk surface
* **`structural.filename_date`** — chronological ordering signal for drift comparison
* **`quality` block** — manifest-level drift summary across the whole scan

The chatlog specialist adds the missing primitives for content drift to complement the structural drift signals already present.

## 4. Use Cases

### 4.0 Origin note

The primary use cases below (§4.1 Project Sentinel and §4.2 PKM and AI Conversation Archives) are **the original driving purposes** of this work. The causal chain:

> Project Sentinel's world-schema challenges → drove the creation of PKP → whose document-pipeline challenges → drove the creation of Scanner to address some of them.

The chatlog specialist is the scanner circling back to serve its original motivation: helping bootstrap schema from raw conversation logs. Project Sentinel and the broader PKM/AI workflow use case are why this feature exists at all.

The other use cases (§4.3 LLM Training Data Curation and §4.4 Business Intelligence on Legacy Shares) are **parallel discoveries** — external problems that happen to share the same primitives. They are not what drove the design. They are adjacent markets where the same architecture turned out to fit.

### 4.1 Project Sentinel — primary driver

Manual chat log iteration to bootstrap RPG world schema. Speaker labels become characters, recurring capitalized tokens become entities, section markers become game systems. The Wayne K Bit applies — the scanner reports what's in the metadata, and the GM decides what to make of it.

Sentinel's challenges came first. They surfaced the need for a per-file observation layer that could look at conversation logs without interpreting them. That need became PKP. PKP's document pipeline needed a pre-processing stage. That stage became Scanner.

### 4.2 PKM and AI Conversation Archives — primary driver

Obsidian, Logseq, Notion, custom vaults. Users archive AI conversations and need cheap pre-filtering before vector stores or LLM analysis. Which conversations introduced new topics? Which reference each other? The chatlog specialist answers these from the manifest, no LLM calls required.

This is the personal knowledge management side of the same motivation that drove Sentinel. The shared root problem: raw human-AI conversation logs that contain meaningful structure, but that structure has to be extracted cheaply and without interpretation.

### 4.3 LLM Training Data Curation — parallel discovery

Filter conversation corpora at scale. Quality signals (turn structure, vocabulary diversity), schema drift between batches, detection of synthetic vs human content patterns. Same primitives, millions of files instead of thousands.

This use case was not a design driver. It became visible as an adjacent market when the chatlog specialist's primitives turned out to fit curation workflows.

### 4.4 Business Intelligence on Legacy Shares — parallel discovery

Decades of digital sediment in company file servers. The scanner already proved the concept on CP Construction's data — the chatlog specialist adds structured text understanding to the existing format coverage. Communication graphs from email archives, entity emergence from document folders, process maturation from template evolution.

This use case also became visible as adjacent. It benefits from the same primitives but was not what the chatlog specialist was designed for.

## 5. Schema Impact

Schema version bumps to `"0.8"`. All changes are additive:

| Field | Location | Type |
|---|---|---|
| `specialist_metadata.chatlog.*` | FileRecord | new namespace under existing field |
| `is_chatlog` | FileRecord | bool (for detection without enable_specialists) |

`is_chatlog` is a derived flag that's always present (default `false`), set to `true` when chatlog detection rules match. It runs even when `enable_specialists=False` because detection is cheap.

### 5.1 Updated Specialist Tools

```python
SPECIALIST_TOOLS[".chatlog"] = "chatlog_signals"  # NOT a real extension — see below
```

The chatlog specialist is **detection-based**, not extension-based. It activates when content patterns match, regardless of extension. This is a new pattern for the scanner — previous specialists were registered by extension.

When the chatlog specialist activates:
- `requires_specialist_tool` becomes `true`
- `specialist_tool` is set to `"chatlog_signals"`
- `specialist_metadata.chatlog` is populated (when `enable_specialists=True`)

This is the first content-based specialist activation in the scanner. All previous specialists were extension-driven. The principle stays the same — observe and report — but the gating mechanism is content rather than filename.

### 5.2 Specialist MIME Guard

The chatlog specialist requires text content. The MIME guard for `chatlog_signals` accepts:
* `text/plain`
* `text/markdown`
* `text/x-markdown`

If MIME doesn't match, the specialist is skipped (consistent with v0.6 MIME guard pattern).

## 6. Implementation Order

### Phase 1 — Detection and is_chatlog flag

1. Add `is_chatlog: bool` field to FileRecord
2. Implement `_detect_chatlog_pattern(text)` method (returns bool)
3. Wire into `scan_file()` after baseline text extraction
4. Detection runs even when specialists disabled

### Phase 2 — Chatlog Specialist Extraction

5. Add `chatlog` namespace to `SPECIALIST_NAMESPACE` (special case — content-based)
6. Add `chatlog_signals` to `SPECIALIST_TOOLS` mapping
7. Implement `_extract_chatlog_metadata(text)` method
8. All sub-extractions: speaker labels, section markers, turn stats, reference tokens, top capitalized tokens, vocabulary estimate
9. Wire into `extract_specialist_metadata()` dispatch

### Phase 3 — Provenance and Quality Integration

10. Record provenance for each chatlog field
11. Update `quality` block to include `chatlog_files` count

## 7. Acceptance Criteria

v0.8 is complete when:

* `is_chatlog` field present on every FileRecord
* Detection rules correctly identify conversational text patterns
* `_extract_chatlog_metadata()` produces all specified fields
* All chatlog fields are deterministic
* Top capitalized tokens are sorted by frequency descending, alphabetical secondary
* Speaker labels list is sorted alphabetically
* Section marker styles list is sorted
* Specialist MIME guard accepts text MIME types
* `quality.chatlog_files` count is correct
* All v0.7 tests pass unchanged
* schema_version is `"0.8"`

## 8. Open Questions

1. Should `top_capitalized_tokens` cap be configurable? (Default 20, or 10 for small manifests, 50 for large?)
2. Should detection run on `.eml` and `.html` text bodies? (Probably v0.9 — adds dependency on extracting body from container.)
3. Should the speaker label regex be configurable for non-English scripts? (Defer — English-only for v0.8, document the limitation.)
4. Should we expose a `--chatlog-detection` CLI flag to force on/off? (Probably yes, default auto.)

## 9. Final Statement

v0.8 makes the scanner useful as a scribe. Not just for documents — for the streams of human and AI conversation that are becoming the new substrate of work, knowledge, and storytelling. The Wayne K of every chat log, every journal, every conversation archive: a name in the metadata, a pattern in the corpus, a recurring presence the consumer can name however they like.

The scanner records. The consumer interprets. The drift is in the data.
