# Scanner v0.10.0 RFC Specification

**Project:** Scanner
**Target Version:** 0.10.0
**Status:** Approved
**Date:** 2026-05-27
**Extends:** v0.9.0 RFC Specification (with v0.9.1/v0.9.2 patches)

---

## 1. Overview

### 1.1 Purpose

v0.10 adds a **human-readable scan summary**, the **`author_aggregate` corpus vector**, and the **`filename_patterns` vector** — completing the "corpus observer" story that v0.9 started.

The scan summary is a new top-level `summary` field: a short, plain-language paragraph describing what the scanner found. It answers the question a human asks first: *"What did you scan and what did you find?"* — before they dive into the JSON.

The two new vectors extend the scanner's observation from content-level (v0.9: chatlog, reference_tokens) to metadata-level (author patterns across specialists) and filename-level (date prefixes, version markers, template names).

### 1.2 Design Principle

> The scan summary is a derived, deterministic output — it is computed from the same fields that populate stats, quality, and vectors_collected. Two scans of the same corpus with the same scanner version MUST produce the same summary text. The summary is a convenience, not a new source of truth.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 2. Human-Readable Scan Summary

### 2.1 What it is

A new top-level `summary` field on `ScanManifest` containing a short, deterministic, plain-language description of the scan results.

### 2.2 Format

The summary is a Markdown string, 3-8 lines, structured as:

```
Scanned {total_files} files ({text_files} text, {binary_files} binary) in {directory_count} directories.

{supported_files} supported ({specialist_count} with specialist metadata). {unsupported_files} unsupported extensions. {quality_line}.

{vector_summary_lines}

{top_directories_line}
```

### 2.3 Example Output

```markdown
Scanned 4,366 files (3,526 text, 840 binary) in 31 directories.

1,163 supported (316 with specialist metadata). 3,203 unsupported extensions. Quality: 676 clean, 3,690 degraded, 0 errors. 4 safety flags, 2 polyglots.

Vectors: chatlog matched 22 files (38 turns, 0 speakers after filtering). reference_tokens ran on 806 files (2,164 URLs, 2,273 paths, 262 @mentions). author_aggregate found 47 distinct authors across 234 files.

Largest directories: tika-parsers (1,891 files), docs (168), tika-app (45).
```

### 2.4 Determinism

The summary text is deterministic: same input + same scanner version = identical string. It uses only values from `stats`, `quality`, `vectors_collected`, and `per_directory_summary` — all of which are already deterministic. Counts use locale-independent formatting (comma-separated thousands).

### 2.5 Inclusion in Checksum

The `summary` field IS included in `manifest_checksum` because it is derived from deterministic content. It changes when any underlying signal changes, which is correct.

## 3. `author_aggregate` Vector — Cross-Specialist, Corpus-Scoped

### 3.1 Background

Deferred from v0.9 pending broader validation corpus diversity. The 6-corpus validation in v0.9 provided the evidence needed: the scanner now extracts authors from DOCX, DOC, PDF, MSG, and EML across real-world corpora. The normalization rules can be tested against real data.

### 3.2 Definition

| Field | Value |
|---|---|
| `vector_id` | `author_aggregate` |
| `method_version` | `1` |
| `scope` | `corpus` |
| Activation | Runs when `enable_specialists == True` AND any document/email/pdf specialist produced output |
| Rules | Pull `author` from document, `from` from email, `author` from pdf. Normalize. Aggregate. |
| Static tuning | `{"top_n": 20, "template_default_threshold": 0.4}` |

### 3.3 Normalization Rules

- Whitespace stripped from start and end
- Internal whitespace collapsed to single spaces
- Comparison is case-insensitive
- Output uses the most common casing observed
- Empty strings, `None`, `"unknown"`, `"User"` excluded
- Exchange legacyDN strings (matching `^/o=` or `^/O=`) excluded

### 3.4 Template-Default Candidate Detection

A normalized author is flagged as a "template default candidate" when it appears as the author of files spanning **multiple distinct extensions** at a frequency greater than `template_default_threshold` (40%) of any single extension's files. The intuition: a real author tends to author files of one or two types; a template default appears across heterogeneous file types.

This is not interpretation — it's a list of candidates a consumer can investigate.

### 3.5 Vector Summary Fields

- `distinct_authors` — int
- `top_authors` — list of `[name, count]` pairs, capped at `top_n`
- `template_default_candidates` — sorted list of flagged names
- `per_namespace_counts` — dict mapping each specialist namespace to its contribution count
- `per_extension_distinct_authors` — dict mapping each extension to its distinct author count

## 4. `filename_patterns` Vector — Unconditional, File-Scoped

### 4.1 Background

Filenames carry structural information that no content-based vector can see. Date prefixes, version markers, numbered revisions, and template names are visible at the filename level and correlate strongly with corpus organization patterns.

### 4.2 Definition

| Field | Value |
|---|---|
| `vector_id` | `filename_patterns` |
| `method_version` | `1` |
| `scope` | `file` |
| Activation | Every file (binary and text) |
| Rules | Six regex patterns matched against `filename` (not full path) |
| Static tuning | `{"enabled_subcategories": ["date_prefix", "version_marker", "numbered_revision", "template_name", "uuid_filename", "copy_suffix"]}` |

### 4.3 The Six Subcategories

| Subcategory | Pattern | Example matches |
|---|---|---|
| `date_prefix` | `^\d{4}[-_]\d{2}[-_]\d{2}` | `2026-04-10_report.pdf`, `2024_01_15_notes.md` |
| `version_marker` | `v\d+[._]\d+` anywhere in filename | `report_v2.1.docx`, `schema_v0.9.json` |
| `numbered_revision` | `[-_ ]\(\d+\)` or `[-_ ]\d+$` before extension | `Invoice (2).pdf`, `report_3.docx` |
| `template_name` | Exact matches against known patterns | `Document1.docx`, `Book1.xlsx`, `Untitled.txt` |
| `uuid_filename` | `[0-9a-f]{8}-[0-9a-f]{4}-` pattern | `a1b2c3d4-e5f6-7890-abcd-ef1234567890.json` |
| `copy_suffix` | `Copy of `, ` - Copy`, `(copy)` patterns | `Copy of report.pdf`, `budget - Copy.xlsx` |

### 4.4 Per-File Field

```json
"filename_patterns": {
  "date_prefix": true,
  "version_marker": false,
  "numbered_revision": false,
  "template_name": false,
  "uuid_filename": false,
  "copy_suffix": false
}
```

Boolean per subcategory. Present on every FileRecord (binary and text).

### 4.5 Vector Summary Fields

- Counts per subcategory (how many files matched each)
- `files_with_any_pattern` — count of files with at least one match

## 5. Schema Impact

Schema version: `0.9` → `0.10`. All changes additive.

### 5.1 Additive Changes

| Field | Location | Type | Stability |
|---|---|---|---|
| `summary` | `ScanManifest` | string (Markdown) | **Stable** — deterministic, included in checksum |
| `author_aggregate` entry | `vectors_collected[]` | vector record | Provisional (§2.4) |
| `filename_patterns` | `FileRecord` | dict of booleans | Provisional (§2.4) |
| `filename_patterns` entry | `vectors_collected[]` | vector record | Provisional (§2.4) |

### 5.2 Promotion from Provisional

The following v0.9 provisional fields are candidates for promotion to Stable based on the v0.9.x patch cycle evidence. Promotion decision is made during implementation — if the field shape survived two patches without change, it's stable:

- `vectors_collected[]` — shape unchanged through v0.9.0 → v0.9.2
- `reference_tokens` — shape unchanged (method_version bumped but field structure same)
- `quality.per_directory_summary[]` — shape unchanged

### 5.3 No Removals

All v0.9 fields preserved unchanged.

## 6. Implementation Order

### Phase 1 — Scan summary

1. Add `summary: str` field to `ScanManifest`
2. Implement `_build_summary()` method computing the text from stats, quality, vectors_collected, per_directory_summary
3. Wire into `scan()` after vectors are registered
4. Include in JSON and JSONL output
5. Tests: determinism (two scans → identical summary), content verification against known corpus

### Phase 2 — `author_aggregate` vector

6. Implement `AuthorAggregateVector` as corpus-scoped
7. Normalization rules (whitespace, casing, exclusions)
8. Template-default candidate detection
9. Register after file walk, populate summary
10. Tests: normalization, exclusions, template detection, empty corpus edge case

### Phase 3 — `filename_patterns` vector

11. Six regex patterns at module level
12. `FilenamePatternVector` class running on every file
13. Add `filename_patterns` field to `FileRecord`
14. Register in vector registry, populate corpus summary
15. Tests: each subcategory, boolean field presence on binary and text files

### Phase 4 — Summary integration with new vectors

16. Update `_build_summary()` to include author_aggregate and filename_patterns when present
17. Integration tests with specialists enabled

### Phase 5 — Provisional promotion evaluation and ship

18. Evaluate v0.9 provisional fields for promotion
19. Version bumps, doc updates, compliance report
20. Full test suite, external corpus validation

## 7. Acceptance Criteria

v0.10 is complete when:

- `summary` field present on every manifest, deterministic, human-readable
- `author_aggregate` runs on any scan with specialist output, produces normalization and template-default detection
- `filename_patterns` runs on every file, boolean subcategories populated
- Both new vectors registered in `vectors_collected[]` with identity digests
- Scan summary includes all active vectors in its text
- Provisional promotion decisions documented in PUBLIC_CONTRACT.md
- All v0.9 tests pass unchanged
- New v0.10 tests cover all additions
- External corpus validation (at least 3 corpora)
- `schema_version` is `"0.10"`

## 9. Open Questions

1. Should the scan summary be included in the JSONL header line alongside stats/quality, or as a separate line? Recommendation: in the header, for consistency.

2. Should `filename_patterns` run on files inside `.git/` or other VCS directories? Recommendation: yes, if the scanner is pointed at them — the scanner doesn't filter by convention, only by `.scannerignore`.

3. Should `template_name` matching be configurable (operator can add their own template names to the detection list)? Recommendation: not in v0.10 — hardcode common patterns. User-configurable detection lists are a dictionary feature (v0.11+).

4. Should the summary include a one-line "health grade" (e.g., "This corpus is 74% clean")? Recommendation: no — percentages invite interpretation. The summary states facts; the consumer interprets.

---

## 10. Final Statement

v0.10 is the release where the scanner starts talking to humans.

The scan summary is the simplest possible bridge: a paragraph that answers "what did you find?" without requiring JSON literacy. The two new vectors extend observation into metadata and filenames — the layers above and below content. Together with the v0.9 content vectors, the scanner now observes at every level: filename, content, metadata, corpus.

The scanner records. The consumer interprets. And now the human can read the recording without opening a JSON viewer.
