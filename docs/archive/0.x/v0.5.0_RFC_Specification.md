# Scanner v0.5.0 RFC Specification

**Project:** Scanner
**Target Version:** 0.5.0
**Status:** Approved
**Date:** 2026-04-09
**Extends:** v0.4.0 RFC Specification
**Precedes:** v1.0.0 RFC (schema freeze)

---

## 1. Overview

### 1.1 Purpose

v0.5 implements the structural changes required for v1.0 schema stability. It is the **last breaking release** before the manifest shape freezes. Every shape change, namespace restructure, and hardening fix lands here so that v1.0 is purely a stability declaration.

### 1.2 Design Principle

> v0.5 makes the changes. v1.0 makes the promise.

### 1.3 Version Positioning

| Version | Role |
|---------|------|
| v0.4 | Feature-complete scanner with semantic naming |
| v0.5 | Schema reshaping + hardening. Last breaking release. |
| v1.0 | Schema freeze. Same code as v0.5 + version bump + compatibility policy. |

### 1.4 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

---

## 2. Schema Changes

### 2.1 Schema Version Field

Add `schema_version` to `ScanManifest`:

```json
{
  "schema_version": "0.5",
  "context": {},
  "meta": {},
  ...
}
```

#### Requirements

* `schema_version` MUST be `"0.5"` for this release
* `schema_version` MUST be included in the deterministic checksum preimage
* v1.0 will bump this to `"1.0"` with no other shape change

---

### 2.2 Namespaced Specialist Metadata

Restructure `specialist_metadata` from a flat dict to a single-key namespaced object.

#### v0.4 shape (current)

```json
{"page_count": 5, "encrypted": true, "pdf_version": "1.4"}
```

#### v0.5 shape

```json
{"pdf": {"page_count": 5, "encrypted": true, "pdf_version": "1.4"}}
```

#### Namespace registry

| Namespace | Extensions | Fields |
|-----------|-----------|--------|
| `pdf` | `.pdf` | has_text_streams, page_count, title, author, producer, creator, creation_date, encrypted, pdf_version, sample_text_marker_density |
| `image` | `.png`, `.jpg`, `.jpeg` | width, height, bit_depth |
| `email` | `.msg`, `.eml` | subject, from, to, date, message_id, has_attachments |
| `spreadsheet` | `.xlsx` | sheet_names, header_rows |
| `document` | `.docx`, `.doc`, `.rtf` | title, author, word_count, heading_count |

#### Rules

* `specialist_metadata` is `null` when specialists disabled or no specialist applies
* when populated, `specialist_metadata` MUST contain exactly one key (the namespace)
* the namespace key is determined by the extension-to-namespace mapping, not by the specialist tool name
* `null` field values within a namespace mean "not observed within bounds"

---

### 2.3 Configurable Baseline Depth

Add `baseline_max_bytes` to `ScannerConfig`:

```python
@dataclass
class ScannerConfig:
    baseline_max_bytes: int = 65536  # 64KB default
    # ... existing fields unchanged ...
```

#### Requirements

* `decode_text()` MUST read at most `baseline_max_bytes` from the file
* `hash_file()` continues to stream the full file (unchanged)
* `baseline_max_bytes` MUST be >= `sample_size`; if set lower, `sample_size` is used as minimum
* `baseline_max_bytes` MUST appear in `meta.config`

## 3. Cross-Platform Hardening

### 3.1 CRLF Handling

* `FRONTMATTER_RE` MUST use `\r?\n` instead of `\n`
* `FRONTMATTER_OPEN_RE` MUST use `\r?\n`
* PDF text marker detection MUST include `b"BT\r\n"` 
* all line-splitting for content parsing MUST handle both `\n` and `\r\n`

### 3.2 Path Normalization

* replace all `str(path).replace("\\", "/")` with `path.as_posix()`

### 3.3 ZIP Entry Validation

Extend `_is_safe_zip_entry()`:

* reject drive letter paths (`C:\`, `D:/`)
* normalize mixed separators before checking
* reject `./` prefix and `/./` sequences

### 3.4 Documentation

* document `exclude_hidden` as Unix dot-prefix convention only
* document `python-magic-bin` recommendation for Windows in README

---

## 4. Silent Failure Fixes

### 4.1 New Error Codes

| Code | Stage | When |
|------|-------|------|
| `xml_parse_failed` | structural | `xml_fromstring()` raises any exception |
| `toml_parse_failed` | structural | `tomllib.loads()` raises any exception |

### 4.2 Specialist Null Logging

When a specialist returns `None` due to:
* missing dependency (olefile unavailable)
* invalid format (bad ZIP, not an OLE file)
* extraction failure

The scanner SHOULD record an `ErrorRecord` with `code: "specialist_probe_failed"` and a deterministic message.

---

## 5. Provenance Updates

### 5.1 Namespaced Keys

Provenance keys MUST match the namespaced specialist path:

* `specialist_metadata.pdf.page_count` (not `specialist_metadata.page_count`)

### 5.2 Recommended Provenance

v0.5 SHOULD add provenance for:

* `structural.title` — `method: "extract_md_title"` or `"extract_html_title"`
* `structural.document_keys` — `method: "extract_json_keys"` or `"extract_yaml_keys"` or `"extract_xml_keys"` or `"extract_toml_keys"`

---

## 6. Implementation Order

### Phase 1 — Schema Shape (breaking changes)

1. add `schema_version` field to `ScanManifest`
2. namespace `specialist_metadata` by format category
3. update provenance keys for namespaced paths
4. add `baseline_max_bytes` to `ScannerConfig`
5. cap `decode_text()` reads to `baseline_max_bytes`
6. bump `SCANNER_VERSION` to `"0.5.0"`, `LOGIC_VERSION` to `"0.5.0"`
7. update all tests

### Phase 2 — Cross-Platform Hardening

8. CRLF in frontmatter regex
9. CRLF in PDF text markers
10. `as_posix()` path normalization
11. ZIP entry validation extensions
12. document platform limitations in README

### Phase 3 — Silent Failure Fixes

13. XML parse error recording
14. TOML parse error recording
15. specialist null result logging
16. add recommended provenance for structural.title and structural.document_keys

---

## 7. Acceptance Criteria

v0.5.0 is complete when:

* `schema_version` is `"0.5"` on every manifest
* `specialist_metadata` is namespaced (one key per file: pdf/image/email/spreadsheet/document)
* `baseline_max_bytes` defaults to 64KB and caps text extraction
* frontmatter and PDF markers handle CRLF
* paths use `as_posix()`
* ZIP validation rejects drive letters and mixed traversal
* XML/TOML failures produce error records
* provenance keys use namespaced specialist paths
* all tests pass
* platform limitations documented

When v0.5 ships and stabilizes, v1.0 is a version bump, a compatibility policy document, and nothing else.
