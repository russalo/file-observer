# v1.44.0 RFC — Lexicon category breakdown survives `--trusted-only`

**Status:** APPROVED (2026-07-14)
**Author:** file-observer Claude · **Date:** 2026-07-14
**Version axes:** SCANNER 1.43.0→1.44.0 · LOGIC UNCHANGED (1.22.0) · SCHEMA UNCHANGED (1.23) · `schema_doc_version` bump
**Issue:** #146 (relates to #135)

---

## 1. Motivation

The bring-your-own lexicon (v1.38) is the guardrail **pre-screen**: it counts a consumer's
category-tagged terms per file so a consumer can decide, *before* a model reads the file, whether it's
a risk. `--trusted-only` (v1.40) is the mode that makes a manifest **safe to feed a model**. The two are
meant to be used together — screen untrusted files, then hand the safe projection to the model — but
today **that combination silently drops the category breakdown**, which is the exact signal a consumer
routes on.

Measured, for a file with hits, under `--trusted-only`:

| lexicon signal | default | `--trusted-only` |
|---|---|---|
| `lexicon_match` safety_flag | ✓ | ✓ survives |
| `lexicon_match.total_hits` | `3` | ✓ survives |
| `lexicon_match.categories` | `{secrets:{count:2,…}, profanity:{count:1,…}}` | ✗ `{}` **nulled** |
| corpus `lexicon` vector `category_hits` | `{secrets:2, profanity:1}` | ✗ scrubbed |

A safe-mode consumer learns *that* a file matched and *how many* total, but not *which categories* — so
they cannot do "block on `secrets`, advise on `profanity`." This directly blocks the per-category
**tiered-routing** use case (#135).

## 2. Why the naive fix fails (measure-first on the mechanism)

`_project_metadata_trusted_only` (scanner.py) does two things, both deliberate:

1. **nulls every string leaf** (verbatim file bytes), and
2. **drops every dict *key* not in a static fo-known allowlist** — because a dict *key* can be
   attacker-controlled (chatlog `speaker_turn_counts` is keyed by the speaker *label*:
   `{"<attacker text>": 3}`), which nulling string *values* alone would not catch.

Lexicon category names are **dict keys** (`categories: {secrets: …}`), and they are **consumer config** —
indistinguishable from an attacker label by rule (2), so they're dropped. `total_hits` survives only
because it's an allowlisted key with a numeric value. So a plain "classify the field as trusted" fails
both ways: the name-as-key is dropped by (2), and a name-as-string-*value* would be nulled by (1).

**The finding that makes this safe to fix:** the *entire* `lexicon_match` namespace and the `lexicon`
vector summary are **counts** (fo-derived numbers) keyed by **category names / a `lexicon_id`** that are
**consumer configuration — never bytes from the scanned file**. There is no attacker-controllable text
anywhere on the lexicon path (v1.38's invariant: terms are never emitted; only counts + names +
`dictionary_id`). The over-suppression is the generic safety net catching a safe-but-*dynamic* key set.

## 3. Decision — a third trust class: `consumer_config` (trusted)

The v1.40 trust axis is binary: `fo_derived` (trusted) vs `file_derived` (untrusted / attacker-controllable
bytes *from the file*). Lexicon category names and `lexicon_id` are **neither** — they are a third thing:
**consumer configuration**, supplied by the operator, never sourced from the scanned file. This RFC names
that class and treats it as **trusted in `--trusted-only`** (Decision D1, approved 2026-07-14):

> **`consumer_config`** — a string that originates from the consumer's own runtime configuration (the
> supplied lexicon: its `lexicon_id` and its category names), never from a scanned file. Safe by
> origin: an attacker controls file content, not the consumer's config, and the `--trusted-only`
> manifest is fed to the consumer's *own* model. Kept in the safe-mode projection.

The rejected alternative (numbers-only ordered count vector + `dictionary_id` remap) preserved a strict
"no strings at all" invariant but pushed a remap cost onto every consumer; D1 chose names + counts for
ergonomics, accepting the explicit (and narrow) safety statement above.

## 4. Design

### 4.1 Per-file `lexicon_match` (Decision D2 — keep the whole namespace)

The `lexicon_match` namespace is audited **entirely `fo_derived` ∪ `consumer_config`** — every leaf is a
count/density (number), a category name (consumer_config key), a `lexicon_id` (consumer_config), or the
`metadata` sub-block of the same shape. In the projection, the `lexicon_match` subtree is kept with
**category-name keys preserved** and values recursively projected (numbers pass, and — the one string —
`lexicon_id` is kept as consumer_config). Mechanically this is a **trusted-subtree** pass: inside
`lexicon_match`, rule (2) "drop unknown keys" is relaxed (category names are legitimate dynamic keys) and
`lexicon_id` is kept.

**Guard against future leak (load-bearing):** a completeness test asserts the `lexicon_match` structure
contains *only* the enumerated safe leaves — so if a future field adds a file-content-derived string to
`lexicon_match` (e.g. a hypothetical `matched_snippet`), the guard fails and forces a conscious trust
decision rather than silently leaking it through the trusted-subtree pass.

### 4.2 Corpus `lexicon` vector summary (D2)

The manifest-level scrub currently blanket-empties every `vectors_collected[].summary` (author_aggregate
/ provenance summaries are laced with file-derived author/producer names). The `lexicon` vector summary
(`{lexicon_id, files_matched, category_hits}`) is audited safe, so the scrub becomes **selective**: keep
the `lexicon` vector's summary, still empty the file-derived ones. (Same completeness guard covers it.)

### 4.3 `--schema` trust annotation

The lexicon fields' `trust` annotation flips to reflect the new class (`consumer_config` for the names /
`lexicon_id`; `fo_derived` for the counts). `schema_doc_version` bumps.

## 5. Versioning

A **projection** change — the DEFAULT manifest is untouched and **byte-identical**, so **LOGIC 1.22.0 /
SCHEMA 1.23 FROZEN** (the v1.40 `--trusted-only` precedent). What changes is only the `--trusted-only`
output (now richer) and the `--schema` trust annotation → `schema_doc_version` bumps; SCANNER 1.43.0→1.44.0.

## 6. Testing (falsify-first, `test_v1_44.py`; benign lexicon only)

1. **Category breakdown survives** — a `--trusted-only` scan of a file with hits carries
   `lexicon_match.categories` (names + counts) and the `lexicon` vector `category_hits`.
2. **THE canary — no file content rides along** — a lexicon whose category name is a benign token,
   scanning a file whose *body* contains a distinctive attacker-marker string: assert the `--trusted-only`
   output contains the category name + counts but **NOT** the attacker-marker, and no `content_preview` /
   path / other file-derived string survives (the whole-manifest canary battery from v1.40, extended).
3. **Other namespaces still fully scrubbed** — chatlog `speaker_turn_counts` (attacker-label keys),
   author_aggregate / provenance vector summaries stay nulled/emptied (the trusted-subtree relaxation is
   scoped to `lexicon_match` only — red-verify with an attacker-labeled key that must NOT survive).
4. **Completeness guard** — a synthetic extra string leaf on `lexicon_match` fails the guard.
5. **Default byte-identical** — a non-`--trusted-only` scan is unchanged (checksum identical).

## 7. Non-goals / deferred

- **The numbers-only representation** — rejected at D1 (ergonomic cost); revisit only if a consumer needs
  a zero-string trusted manifest.
- **Per-category routing docs/example** — that's #135, unblocked by this release; a follow-up.
- **Obfuscation-resistance / per-field attribution / per-call MCP `lexicon_path`** — unrelated parked
  lexicon items, untouched.

## 8. Review

Full 4-leg. The **canary (§6.2)** is the load-bearing check — leg-1 + leg-4 both hammer "can any
file-content string survive the lexicon trusted-subtree relaxation?"; leg-3 sweep confirms the default
manifest is byte-identical and other namespaces stay scrubbed. leg-2 cross-model if the infra is up
(else recorded MISSING per review-kit #66/#67).
