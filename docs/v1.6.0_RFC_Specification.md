## 1. Overview

### 1.1 Purpose

Elevate **production provenance** — *what tool produced a file, when, and whether
it is born-digital or a digitized scan* — to a first-class, normalized,
corpus-scoped observation.

This was the strongest seam the v1.5 PDF work surfaced: every "strange fact" we
could conclude from the infra-standards corpus was **provenance**, not content —
the producer toolchain (AutoCAD HDI plot driver behind 138 water drawings,
Bluebeam linking two "independent" agencies), the production era (live standards
stamped 2002/2007), and the digitization origin (a state DOT "standard drawing"
that is an OCR'd photocopy via Adobe Paper Capture). The scanner's natural lane
is *who/what/when made this file* — and that is reliably observable from metadata
**even when the content is opaque** (compressed/object-stream/encrypted). It is
also exactly the "deterministic Tika **+ provenance**, for pipelines" positioning
anchor, and the kind of audit-grade BI the vector-fingerprints idea was seeded for.

**Relationship to `author_aggregate` (v0.10):** complementary, not overlapping.
`author_aggregate` answers **WHO authored** (person/org, from `/Author`/`from`).
v1.6 provenance answers **WHAT TOOL / WHEN / digitization** (from
`producer`/`creator`/`creation_date` + the v1.5 vision signals). Same corpus-vector
machinery; different axis.

### 1.2 What v1.6 adds

- **(a)** A corpus-scoped **`provenance` vector** in `vectors_collected[]`
  (`method_version` 1), modeled directly on `_run_author_aggregate`:
  - `toolchains` — **normalized** producer/creator → count (top-N).
  - `production_years` — year (from `creation_date`) → count.
  - `digitization` — `{born_digital, scanned, ocr_detected, unknown}` counts.
- **(b)** A closed, documented **producer-normalization table** (the vector's
  dictionary; versioned via `rules_hash`/`dictionary_id`).
- **(c)** A **digitization classifier** that reuses v1.5 `requires_vision` +
  `text_detected` and adds known **OCR-producer fingerprints** (Adobe Paper
  Capture, ABBYY FineReader, …) → a stronger born-digital-vs-scanned signal than
  byte markers alone.

Pure observation, additive. **No `LOGIC_VERSION` change** (no routing decision
changes — exactly like the v1.1 corpus-intelligence vectors).

### 1.3 Normative Language

MUST / SHOULD / MAY per BCP 14.

## 2. The `provenance` corpus vector

Modeled on `_run_author_aggregate` (gated behind `enable_specialists`,
corpus-scoped, registered in `VectorRegistry`). For each record, harvest the
producing-tool + era + digitization signals from `specialist_metadata`, normalize,
aggregate, and register one `VectorRecord` with `summary`:

```
summary = {
  "toolchains": [ {"name": "Adobe PDF Library", "count": 71}, … ],   # top-N, normalized
  "distinct_toolchains": <int>,
  "production_years": { "2007": 40, "2018": 32, "2022": 145, … },
  "production_year_range": [<min>, <max>],
  "digitization": { "born_digital": N, "scanned": M, "ocr_detected": K, "unknown": U },
  "per_namespace_counts": { "pdf": …, "document": …, "email": … },
}
```

Identity digest = `compute_vector_identity_digest(PROVENANCE_VECTOR_ID, 1,
rules_hash, tuning_hash)` (the normalization table feeds `rules_hash`/`dictionary_id`).

## 3. Producer-normalization table (closed, documented)

A deterministic, **closed** mapping (the vector's dictionary — like the chatlog
FP-lexicon: bounded and named, not open-ended accretion). Examples:

| raw producer/creator pattern | normalized toolchain |
|---|---|
| `Adobe PDF Library *`, `Adobe PDF Library` | Adobe PDF Library |
| `Acrobat Distiller *` | Adobe Acrobat Distiller |
| `Adobe … Paper Capture *` | Adobe Acrobat (OCR / Paper Capture) → **ocr_detected** |
| `*.hdi *`, `pdfplot*` | Autodesk (HDI plot driver) |
| `Microsoft® Word *`, `Microsoft Office Word` | Microsoft Word |
| `Microsoft: Print To PDF` | Microsoft Print to PDF |
| `Bluebeam *` | Bluebeam |
| `pdfTeX*`, `LaTeX*`, `TeX*`, `dvips*` | TeX / LaTeX |
| `Ghostscript*`, `GPL Ghostscript*` | Ghostscript |
| `ABBYY*`, `FineReader*` | ABBYY FineReader → **ocr_detected** |

An **unrecognized** producer is normalized only mechanically (strip/collapse
whitespace, drop trailing version digits) and passed through — never dropped, so
the long tail is still counted (and surfaces table-expansion candidates).

## 4. Digitization classifier

Per file, classify into one of:
- **`ocr_detected`** — producer matches an OCR fingerprint (Paper Capture, ABBYY…).
  The strongest, most specific signal (the producer *says* it was scanned-then-OCR'd).
- **`scanned`** — `requires_vision` true (image-only, no text) and not OCR-tagged.
- **`born_digital`** — `text_detected` true (extractable text).
- **`unknown`** — none of the above observable (e.g. object-stream PDF, non-PDF
  without the signals).

Reuses v1.5 signals; the only new input is the OCR-producer fingerprint set.

## 5. Cross-format harvest

PDF is the richest source (`producer`/`creator`/`creation_date` already extracted
in v1.5). The producing **application** also exists for other formats and SHOULD
be harvested where it is a cheap add (see fork §6.B):
- **OOXML** (`docx`/`xlsx`): `docProps/app.xml` `<Application>` + `<AppVersion>`.
- **OLE2** (`doc`/`xls`): SummaryInformation "Application Name".
- **EML**: `X-Mailer` / `User-Agent` headers.

Whatever is present feeds the same normalization + aggregation.

## 6. Design forks (for sign-off)

- **A. Corpus-vector-only vs + per-file `provenance` block.** `author_aggregate`
  is corpus-only. Recommend **start corpus-only** (proven pattern, smaller
  surface); add a per-file normalized `provenance` block (`toolchain`,
  `production_year`, `digitization`) in a later minor if consumers want it.
- **B. Formats — PDF-only vs cross-format.** PDF producer is already extracted
  (zero new extraction). Cross-format means *extending the OOXML/OLE2/EML
  specialists* to capture the producing app (§5). Recommend **PDF + the cheap
  OOXML `app.xml` add** (it's one more XML field in an already-parsed file);
  defer OLE2/EML producing-app to v1.7+ unless trivial.
- **C. Normalization-table closure.** Closed + documented (recommend), unknowns
  passed through cleaned — same discipline as the chatlog lexicons; the table is
  the vector's `dictionary_id`, so expansion is a deliberate, versioned change.

## 7. Schema & Version Constants

- `SCANNER_VERSION` 1.5.0 → **1.6.0**.
- `LOGIC_VERSION` **unchanged (1.4.0)** — no routing/decision change (pure
  aggregation, like v1.1).
- `SCHEMA_VERSION` 1.4 → **1.5** (additive: new `provenance` vector in
  `vectors_collected[]`; per-file block only if fork A says so).
- New `provenance` vector `method_version` **1**.
- v1.0 public contract holds — no field removed/renamed/retyped.

## 8. Boundary (observe, don't interpret)

Provenance is **observation**: it normalizes and counts producer strings and
reports digitization from already-observed signals + producer fingerprints. It
MUST NOT infer intent or judgment — "this agency is lazy," "this standard is
neglected." It reports *"138 files were produced by the Autodesk HDI plot
driver"* and *"3 files are OCR'd scans"*; the consumer draws conclusions. Crossing
into interpretation would break the [[feedback_naming]] / observe-don't-interpret
contract.

## 9. Validation Plan (falsify-first)

The `corpora_infra/` corpus is the ready-made test bed — it already exhibits the
producer variety (Adobe / AutoCAD / Bluebeam / Word / Paper Capture), the
2002→2026 production spread, and the scanned holdouts. Plan:
- Synthetic unit cases FIRST: normalization (each table row → expected name;
  unknown producer → cleaned passthrough), digitization classification (OCR
  producer → `ocr_detected`; image-only → `scanned`; text → `born_digital`),
  empty-corpus (zero-count registration), determinism (same corpus → same digest).
- Re-scan `corpora_infra/` and confirm the vector reproduces the Wayne-K
  provenance facts (toolchain counts, year spread, OCR'd holdouts).
- Full suite + golden regen (new vector appears in `vectors_collected[]`) + the
  three review layers (in-house multi-agent + Gemini + PR bots).
