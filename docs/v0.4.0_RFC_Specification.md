# Scanner v0.4.0 RFC Specification

**Project:** Scanner
**Target Version:** 0.4.0
**Status:** Approved
**Date:** 2026-04-08
**Extends:** v0.3.0 RFC Specification (authoritative)

---

## 1. Overview

### 1.1 Purpose

Scanner v0.4 is an **additive extension** of the v0.3.0 RFC. It expands supported file coverage, introduces a formal bounded observation deviation policy, and resolves the naming convention gap identified during v0.3 manifest analysis.

v0.4 does not redefine pipeline stages, output structures, or specialist contracts. All new behavior attaches to existing v0.3 mechanisms.

### 1.2 Design Principle

> Scanner v0.4 turns coverage gaps into coverage, and scanner-internal jargon into downstream-readable signals. The manifest becomes more useful to the ingestor without becoming less honest about what the scanner actually did.

### 1.3 Version Positioning

| Version | Role |
|---------|------|
| v0.1 | Deterministic extraction and routing contract |
| v0.2 | Usable manifest surface + operational metadata + bounded exploration |
| v0.3 | Operational fidelity + specialist depth + format expansion |
| v0.4 | Coverage expansion + deviation policy + semantic naming + security hardening |
| v0.5+ | Async execution model, streaming, broader specialist coverage |

### 1.4 Normative Language

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are to be interpreted as described in **RFC 2119** and clarified by **RFC 8174** (BCP 14).

## 2. Objectives

### 2.1 Primary Objectives

v0.4 MUST:

* preserve full v0.1, v0.2, and v0.3 correctness and compliance
* expand supported file coverage to `.jpg`/`.jpeg`, `.eml`, `.css`, `.vx`, and `.xlsx`
* introduce a formal deviation policy for specialists that require reads beyond the default sample buffer
* rename specialist tool identifiers to be semantic and downstream-readable
* normalize email envelope extraction across `.eml` and `.msg` formats
* harden XML and ZIP handling against known attack vectors

### 2.2 Secondary Objectives

v0.4 SHOULD:

* make the manifest fully consumable by a downstream ingestor without knowledge of scanner internals
* document all deviation budgets and security constraints as normative spec text

### 2.3 Non-Goals

v0.4 MUST NOT:

* redefine the pipeline model (Universal → MIME Analysis → Baseline → Structural → Specialist → Provenance is unchanged)
* introduce new top-level output structures on `FileRecord` or `ScanManifest`
* introduce parallel specialist output contracts
* add async execution, threading, or timeout enforcement
* perform full document parsing, content understanding, or ML-based extraction

---

## 3. Architectural Constraints

### 3.1 Additive Extension Rule

v0.4 SHALL be defined as an additive extension to the v0.3 RFC. This means:

* no duplication of existing signals
* no redefinition of pipeline stages
* no parallel output structures
* all new specialist outputs go into `specialist_metadata`, `structural.document_keys`, `FileRecord.errors`, and `signal_provenance`

### 3.2 Canonical Pipeline (unchanged)

```
Universal → MIME Analysis → Baseline → Structural → Specialist → Provenance
```

All new behavior MUST attach to existing stages.

## 4. Bounded Observation Deviation Policy

### 4.1 Background

v0.3 established the bounded observation mandate: specialists operate within the `sample_size` buffer (default 8KB). However, certain binary container formats (e.g., ZIP-based OOXML) store critical structural metadata beyond the sample window. v0.4 introduces a formal deviation mechanism.

### 4.2 Deviation Rules

A specialist MAY read beyond the default sample buffer only if ALL of the following are true:

1. The deviation is **declared in this RFC** with a specific extension and justification
2. The deviation defines a **fixed maximum byte budget** (not "read the whole file")
3. The deviation applies to **specialist tier only** — universal, baseline, and structural tiers MUST NOT deviate
4. The deviation is **surfaced in signal provenance** via `detail.read_budget_bytes` on every affected field
5. The deviation MUST NOT change global scanner behavior — it applies only to the declared specialist

### 4.3 Declared Deviations

| Extension | Specialist | Byte Budget | Justification |
|---|---|---|---|
| `.xlsx` | `spreadsheet_structure` | 131072 (128KB) | ZIP central directory is at end of file; local file headers may not contain workbook.xml within 8KB |

No other deviations are declared in v0.4. All other specialists MUST operate within the default sample buffer.

### 4.4 Provenance for Deviations

When a deviation is used, every specialist metadata field extracted under the deviation MUST include provenance with:

```json
{
  "layer": "derived",
  "method": "_xlsx_specialist",
  "trigger": "bounded_deviation",
  "detail": {
    "read_budget_bytes": 131072,
    "bytes_read": 94208,
    "reason": "zip_central_directory_required"
  }
}
```

When the specialist succeeds within the default sample buffer, the trigger MUST remain `bounded_sample` (no deviation used).

## 5. Semantic Naming Convention

### 5.1 Problem

v0.3 specialist tool identifiers (`pdf_scanner`, `png_header`, `msg_envelope`, `docx_parser`, `rtf_parser`) are scanner-internal implementation names. A downstream ingestor reading `specialist_tool: "pdf_scanner"` cannot distinguish scanner routing metadata from file content signals.

### 5.2 Resolution

v0.4 renames the values in `SPECIALIST_TOOLS` to be **semantic and downstream-readable**. The field name `specialist_tool` is unchanged. The values describe **what the file needs**, not what the scanner does.

### 5.3 Renamed Values

| Extension | v0.3 Value | v0.4 Value | Rationale |
|---|---|---|---|
| `.pdf` | `pdf_scanner` | `pdf_extraction` | Describes downstream need |
| `.png` | `png_header` | `image_structure` | Format-neutral for image types |
| `.jpg`/`.jpeg` | (new) | `image_structure` | Same specialist as PNG |
| `.msg` | `msg_envelope` | `email_envelope` | Format-neutral for email types |
| `.eml` | (new) | `email_envelope` | Same semantic category as MSG |
| `.docx` | `docx_parser` | `document_extraction` | Describes downstream need |
| `.rtf` | `rtf_parser` | `document_extraction` | Same category as DOCX |
| `.xlsx` | (new) | `spreadsheet_structure` | Describes what the file contains |

### 5.4 Rules

* specialist tool values MUST be stable across minor versions once assigned
* values MUST describe the **downstream processing requirement**, not the scanner implementation
* values SHOULD be format-neutral where multiple extensions share the same downstream need
* implementation detail (which method ran, which library was used) belongs in `signal_provenance`, not in `specialist_tool`

### 5.5 Migration

This is a **breaking change** to the `specialist_tool` string values. v0.4 manifests will emit different values than v0.3 for the same files. This is intentional — the old names were implementation leaks. Downstream consumers MUST update their routing logic.

`routing_logic_version` in `ScanContext` MUST be bumped to `"0.4.0"` to signal this change.

## 7. Extension Specifications

### 7.1 `.jpg` / `.jpeg` — Image Structure

#### Classification

* `is_binary`: true
* `requires_vision`: true
* `requires_specialist_tool`: true
* `specialist_tool`: `"image_structure"`

#### Specialist Metadata (when enabled)

```json
{
  "width": 1920,
  "height": 1080
}
```

#### Implementation

* Parse JPEG SOF0 (0xFFC0) and SOF2 (0xFFC2) markers from the sample buffer
* Extract height (2 bytes big-endian) and width (2 bytes big-endian) from the SOF frame header
* If no SOF marker found within sample, fields MUST be `null` with provenance trigger `missing_from_bounds`
* EXIF extraction is explicitly deferred to v0.5

#### Bounded Observation

* Operates within default sample buffer (8KB)
* No deviation required — SOF markers typically appear within first few hundred bytes

---

### 7.2 `.eml` — Email Envelope

#### Classification

* `is_binary`: false (text-decodable)
* `requires_specialist_tool`: true
* `specialist_tool`: `"email_envelope"`

#### Specialist Metadata (when enabled)

```json
{
  "subject": "RE: Project Update",
  "from": "alice@example.com",
  "to": "bob@example.com",
  "date": "2026-03-15T10:30:00",
  "message_id": "<abc123@example.com>",
  "has_attachments": true
}
```

#### Implementation

* Use Python stdlib `email.parser.BytesParser` or `email.parser.Parser`
* Extract from decoded headers only — no body parsing, no attachment content extraction
* `has_attachments`: derived from `Content-Type: multipart/mixed` or presence of `Content-Disposition: attachment` parts
* `date`: parse `Date` header; emit as ISO-8601 string or null if unparseable
* `message_id`: raw `Message-ID` header value or null

#### Bounded Observation

* `.eml` files are text-decodable; headers are at the top of the file
* Operates within default sample buffer
* If headers are truncated by sample boundary, affected fields MUST be `null` with provenance trigger `missing_from_bounds`

---

### 7.3 `.msg` — Email Envelope (Normalized)

v0.4 normalizes `.msg` specialist output to match `.eml` parity.

#### Specialist Metadata (when enabled)

```json
{
  "subject": "Project Update",
  "from": "alice@example.com",
  "to": "bob@example.com",
  "date": "2026-03-15T10:30:00",
  "message_id": "<abc123@example.com>",
  "has_attachments": true
}
```

#### New Fields (added to v0.3 baseline of subject/from/to)

* `date`: extract from OLE property `PR_MESSAGE_DELIVERY_TIME` or `PR_CLIENT_SUBMIT_TIME`
* `message_id`: extract from OLE property `PR_INTERNET_MESSAGE_ID`
* `has_attachments`: derived from `PR_HASATTACH` property or attachment table presence

#### Bounded Observation

* Operates on sample buffer via `BytesIO` (v0.3 behavior, no change)
* Fields that cannot be extracted within bounds MUST be `null`

---

### 7.4 `.css` — Stylesheet

#### Classification

* `is_binary`: false
* `requires_specialist_tool`: false
* `specialist_tool`: null

#### Processing

* Standard baseline: encoding detection, content preview, tag extraction
* Technology hints already detect CSS frameworks (Bootstrap, Tailwind) from content patterns
* No specialist required — CSS files are plain text with no structural metadata beyond what baseline provides

---

### 7.5 `.vx` — WinCan XML

#### Classification

* `is_binary`: false
* `requires_specialist_tool`: false
* `specialist_tool`: null

#### Processing

* Treated as XML subtype — existing `extract_xml_keys()` handles it
* Root element (`<wcfile>`) and direct children extracted into `structural.document_keys`
* No new parser or specialist required

#### Spec Note

> `.vx` is a domain-specific XML format (WinCan sewer inspection data). It does not require special handling beyond XML structural extraction.

---

### 7.6 `.xlsx` — Spreadsheet Structure

#### Classification

* `is_binary`: true
* `requires_specialist_tool`: true
* `specialist_tool`: `"spreadsheet_structure"`

#### Specialist Metadata (when enabled)

```json
{
  "sheet_names": ["Summary", "Detail", "Billing"],
  "header_rows": {
    "Summary": ["Job", "Status", "Amount"],
    "Detail": ["Item", "Qty", "Unit Price"]
  }
}
```

#### Implementation

* Use stdlib `zipfile.ZipFile` to open the file (or bounded read buffer under deviation)
* Parse `/xl/workbook.xml` for sheet names
* Parse `/xl/worksheets/sheet1.xml` (etc.) first row for header columns
* All XML parsing within the ZIP MUST use hardened parsing (see §8)
* If ZIP structure is invalid or workbook.xml is missing, return `null` with error record

#### Bounded Observation — Deviation

* `.xlsx` specialist operates under a **declared deviation** (§4.3)
* Byte budget: 131072 bytes (128KB)
* The scanner MUST read at most 128KB from the file for specialist extraction
* If the file is smaller than 128KB, the full file is read (this is not a deviation — it's within budget)
* All provenance entries MUST include `detail.read_budget_bytes` and `detail.bytes_read`

#### Constraints

* No full data extraction — only sheet names and first-row headers
* No cell typing, formula evaluation, or style extraction
* No `extractall()` — individual entries read via `ZipFile.read()`

## 8. Security Hardening

### 8.1 XML Parsing

#### Requirement

XML parsing SHOULD use `defusedxml.ElementTree` when available. If `defusedxml` is not installed, the scanner MUST fall back to stdlib `xml.etree.ElementTree` with the following mitigations:

* Sample buffer size (8KB default) naturally limits billion-laughs expansion
* No external entity resolution (stdlib ET does not resolve external entities by default in modern Python)
* Parser errors are non-fatal (existing behavior)

#### Dependency Policy

`defusedxml` is an **optional dependency**, following the existing pattern (like `PyYAML`, `olefile`):

```python
try:
    from defusedxml.ElementTree import fromstring as safe_fromstring
except ImportError:
    from xml.etree.ElementTree import fromstring as safe_fromstring
```

`ScanContext.dependencies` MUST include `defusedxml` with availability and version.

### 8.2 ZIP Handling (.xlsx)

For `.xlsx` specialist extraction:

* `ZipFile.extractall()` MUST NOT be used
* Individual entries MUST be read via `ZipFile.read(entry_name)` with explicit name validation
* Entry names MUST be validated: reject paths containing `..`, absolute paths, or paths starting with `/`
* Malformed ZIP files MUST produce an error record and `null` specialist metadata, not a crash

### 8.3 Provenance for Security-Relevant Decisions

When `defusedxml` is used vs stdlib fallback, `signal_provenance` for `structural.document_keys` on XML files SHOULD include `detail.xml_parser: "defusedxml"` or `detail.xml_parser: "stdlib"`.

## 9. Data Model Changes

### 9.1 No New Top-Level Fields

v0.4 adds no new fields to `FileRecord` or `ScanManifest`. All new data flows through existing fields:

| Data | Destination |
|---|---|
| JPEG dimensions | `specialist_metadata.width`, `specialist_metadata.height` |
| EML envelope | `specialist_metadata.subject`, `.from`, `.to`, `.date`, `.message_id`, `.has_attachments` |
| MSG enrichment | same fields as EML (parity) |
| XLSX structure | `specialist_metadata.sheet_names`, `specialist_metadata.header_rows` |
| `.vx` keys | `structural.document_keys` (existing XML path) |
| CSS signals | existing baseline fields |
| Errors | `FileRecord.errors` |
| Provenance | `signal_provenance` |

### 9.2 ScanContext Updates

* `routing_logic_version` MUST be `"0.4.0"`
* `dependencies` MUST include `defusedxml` (available + version)
* `dependencies` MUST continue to include `olefile` (for MSG)

### 9.3 Specialist Tool Value Migration

All `specialist_tool` string values change per §5.3. This is a breaking change in manifest output. `routing_logic_version` bump signals this.

## 10. Dependency Policy

### 10.1 Existing Dependencies (unchanged)

| Dependency | Purpose | Required | Fallback |
|---|---|---|---|
| `python-magic` | Content-based MIME detection | Yes | Extension-based inference |
| `chardet` | Encoding detection | Yes | Fixed cascade |
| `PyYAML` | Frontmatter parsing | Optional | String-splitting fallback |
| `olefile` | MSG OLE2 extraction | Optional | `specialist_metadata = null` |

### 10.2 New Dependencies

| Dependency | Purpose | Required | Fallback |
|---|---|---|---|
| `defusedxml` | Hardened XML parsing | Optional (SHOULD install) | stdlib `xml.etree.ElementTree` + documented risk |

### 10.3 No New Required Dependencies

v0.4 does NOT add any new required dependencies. `.xlsx` parsing uses stdlib `zipfile` + XML parsing. `.eml` parsing uses stdlib `email`. `.jpg`/`.jpeg` parsing uses stdlib `struct`. `defusedxml` is optional.

## 11. Testing Requirements

### 11.1 Unit Tests

Must cover:

* JPEG SOF0/SOF2 marker parsing (valid, progressive, no SOF in sample, truncated)
* EML header extraction (valid, multipart, missing headers, truncated by sample)
* MSG enriched fields (date, message_id, has_attachments) when olefile available
* XLSX sheet name and header row extraction (valid, encrypted, corrupt ZIP, path traversal attempt)
* XML parsing with defusedxml vs stdlib fallback
* ZIP entry name validation (reject `..`, absolute paths)
* Deviation provenance (bytes_read, read_budget_bytes present)
* Semantic specialist tool names (verify new values)

### 11.2 Integration Tests

Must cover:

* Full scan with new extensions produces correct specialist metadata
* `.vx` files get XML structural extraction without special handling
* `.css` files get baseline processing without specialist
* JPEG/EML/XLSX specialist metadata present when specialists enabled, null when disabled
* EML and MSG produce same field set (parity)
* Specialist tool values in manifest match new semantic names

### 11.3 Golden Tests

Must confirm:

* Determinism for all new specialist outputs
* Deviation provenance is deterministic
* Manifest checksum stable across runs

### 11.4 Edge Cases

Must include:

| Case | Expected |
|---|---|
| JPEG with no SOF marker in sample | width/height null, trigger `missing_from_bounds` |
| JPEG progressive (SOF2) | width/height extracted normally |
| EML with truncated headers | affected fields null |
| EML with no attachments | `has_attachments: false` |
| MSG without olefile | specialist_metadata null |
| XLSX encrypted (ZIP password) | specialist_metadata null, error record |
| XLSX with path traversal entry | entry rejected, error record |
| XLSX larger than 128KB budget | reads stop at budget, provenance records bytes_read |
| XLSX smaller than 8KB | no deviation needed, trigger `bounded_sample` |
| `.vx` with `<wcfile>` root | document_keys includes "wcfile" |
| Zero-byte .jpg | specialist_metadata null |
| Billion-laughs XML (with defusedxml) | parse rejected, error record |
| Billion-laughs XML (without defusedxml) | bounded by 8KB sample, degraded but safe |

## 12. Acceptance Criteria

v0.4 is complete when:

* all v0.1, v0.2, and v0.3 guarantees remain intact
* `.jpg`, `.jpeg`, `.eml`, `.css`, `.vx`, `.xlsx` are in `SUPPORTED_EXTENSIONS`
* JPEG specialist extracts width/height from SOF markers within sample buffer
* EML specialist extracts subject/from/to/date/message_id/has_attachments via stdlib
* MSG specialist output normalized to match EML field set
* XLSX specialist extracts sheet_names and header_rows under 128KB deviation budget
* `.vx` handled by existing XML parser (no new code beyond extension addition)
* `.css` handled by existing baseline (no specialist)
* specialist tool values are semantic and downstream-readable
* `routing_logic_version` is `"0.4.0"`
* deviation policy is enforced with provenance on every deviated field
* XML parsing uses `defusedxml` when available, stdlib fallback documented
* ZIP entry names validated against traversal attacks
* all changes are tested and deterministic

## 13. Explicit Tradeoffs

### 13.1 Chosen Tradeoffs

v0.4 prioritizes:

* coverage — more file types with bounded, deterministic extraction
* clarity — semantic naming makes manifests readable by downstream systems
* safety — security hardening for XML and ZIP without heavy dependencies

over:

* depth — no full document parsing, no cell data, no email bodies
* purity — XLSX deviation breaks the "sample-only" rule, but does so explicitly and traceably
* backward compatibility — specialist tool values change (intentional, versioned)

### 13.2 Deferred Work

Explicitly deferred beyond v0.4:

* `.xls` specialist (legacy binary Excel, needs `xlrd`)
* `.doc` OLE metadata extraction (low volume, 87 files in jobs scan)
* `.db3` SQLite table introspection (niche)
* EXIF extraction for images (v0.5)
* async execution model and timeouts (v0.5)
* streaming scan output
* full XLSX data extraction beyond headers
* `.mpp` MS Project support (too niche)

## 14. Recommended Implementation Order

### Phase 1 — Naming + Security

1. rename specialist tool values (SPECIALIST_TOOLS dict)
2. bump `LOGIC_VERSION` to `"0.4.0"`
3. add `defusedxml` optional import with stdlib fallback
4. add ZIP entry name validation utility
5. update `ScanContext.dependencies` for `defusedxml`

### Phase 2 — Simple Promotions

6. add `.jpg`, `.jpeg`, `.css`, `.vx` to `SUPPORTED_EXTENSIONS`
7. JPEG SOF specialist (width/height via `struct`)
8. `.vx` gets XML handling automatically (just extension addition)
9. `.css` gets baseline handling automatically (just extension addition)

### Phase 3 — Email Normalization

10. `.eml` specialist via stdlib `email.parser`
11. MSG specialist enrichment (date, message_id, has_attachments)
12. add `.eml` to `SUPPORTED_EXTENSIONS` and `SPECIALIST_TOOLS`

### Phase 4 — XLSX + Deviation

13. implement deviation-aware file reader (bounded to declared budget)
14. `.xlsx` specialist via stdlib `zipfile` + XML parsing
15. add `.xlsx` to `SUPPORTED_EXTENSIONS` and `SPECIALIST_TOOLS`

## 15. Summary

v0.4 is the version where the scanner stops leaking implementation details into its output and starts speaking the ingestor's language. Specialist tool names become semantic. Coverage expands to the highest-value unsupported formats from the real jobs scan. The bounded observation rule gets a formal escape hatch that's explicit, budgeted, and traceable.

The pipeline model doesn't change. The output structures don't change. The discipline stays.

---

## 16. Final Statement

v0.4 is successful if a downstream ingestor can read the manifest and route every file without needing to know that "pdf_scanner" is a Python method name or that "msg_envelope" means olefile. The specialist tool field should read like an instruction to the next program, not a diary entry from the scanner.
