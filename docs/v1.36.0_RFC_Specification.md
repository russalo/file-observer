# v1.36.0 — defusedxml → purexml changeover (XML dependency swap)

**Status:** DRAFT (gated on Russell's production-swap GO — the plan, not yet shipped).
**Date:** 2026-07-08.
**Proposed axes:** SCANNER 1.35.0→1.36.0 · **LOGIC 1.19.0→1.20.0** · SCHEMA unchanged (1.21).
**Depends on:** purexml 1.0.0 (LIVE on PyPI, MIT) — capability-proven + contract-ratified (see below).

## 1. Motivation
fo hardens its XML parsing (the OOXML/ODF specialists + the structural XML-keys tier) with the optional
`defusedxml` dependency; when it's absent, fo falls back to the plain stdlib parser with **no** XXE/entity/DTD
protection — so the fallback itself is the unsafe path, and safety hinges on whether one library happened to
be installed. `defusedxml` is also effectively frozen (0.7.1, last real release 2021), while the libexpat
threat under it keeps moving.

**purexml** — fo's dependency-elimination-lab replacement (`/srv/projects/pkplab/purexml`) — is a pure-stdlib,
zero-runtime-dependency, oracle-gated-to-defusedxml drop-in that **also** adds the structural-DoS caps defusedxml
never had. It reached 1.0 (frozen contract, MIT) on 2026-07-08. This RFC swaps fo onto it.

## 2. Why now (the adoption gate is cleared)
- **Capability-proven on fo's OWN data:** purexml 1.0.0 vs defusedxml over fo's full corpus — **2,695 XML parts /
  507 files, 0 disagreements** (2,658 C14N-identical + 37 both-raise-same-type), in fo's exact raw-bytes usage
  shape (the load-bearing `docProps/app.xml` encoding-decl path included). purexml's own sweep adds 467/0 across
  OOXML+ODF+standalone.
- **Contract enforced in purexml's CI:** fo's 6-point consumer contract is 22 named tests in purexml's
  `test_fo_contract.py` (import path `purexml.ElementTree.fromstring`, forbid-* defaults, the defusedxml.common
  exception hierarchy, determinism, the ≥3.10 floor, plain-string `__version__`) — it cannot silently drift.
- **1.0 freeze RATIFIED both sides** (all 6 fo points frozen; `Limits` intentionally PROVISIONAL/opt-in).
- The only remaining gate was Russell's production-swap timing; this RFC is that step.

## 3. What changes (four edits, mechanical)
1. **Dependency:** `pyproject.toml` `[project.optional-dependencies]` `security = ["defusedxml"]` →
   `security = ["purexml>=1.0.0"]`. (Pin `>=1.0.0`; a 2.0 is a breaking-contract re-review. `[all]`/`[dev]`
   re-derive automatically.) defusedxml is REMOVED from fo's deps — the dep-elimination win.
2. **Import** (`scanner.py:74`): `from defusedxml.ElementTree import fromstring as xml_fromstring`
   → `from purexml.ElementTree import fromstring as xml_fromstring`. The stdlib fallback line (no-purexml →
   `xml.etree`, unhardened) is UNCHANGED — same two-tier structure.
3. **Opt into the structural caps** (the security gain): route the 16 `xml_fromstring(...)` call-sites through a
   thin `_xml_parse(data)` wrapper that applies `limits=RECOMMENDED_LIMITS` **only when purexml is the backend**
   (a no-op on the stdlib fallback, which can't take `limits=`). `RECOMMENDED_LIMITS` = `max_depth=1000` /
   `max_attributes=256` / `max_bytes=100 MiB`; raises a catchable `LimitExceeded` (a `ValueError` subclass, so
   fo's existing `except` around XML parsing already catches it → the field degrades to null/error, never a crash).
4. **ScanContext provenance** (`scanner.py:~3156`): record `purexml` in place of `defusedxml` in
   `ScanContext.dependencies` (name + version via the existing `_dep_version_str` guard), AND record the
   `RECOMMENDED_LIMITS` values + purexml's recommended expat floor — so the manifest audit-trail is explicit
   about the caps in force (per the [[project_rules_fingerprint_lens]] discipline: rule data that gates output
   is recorded, not implicit).

## 4. Behavior & the manifest
- **Parse output is byte-identical on real files** — purexml == defusedxml, proven 2,695/0 + 467/0. No extracted
  value changes on any real corpus.
- **New behavior on PATHOLOGICAL input only:** with `RECOMMENDED_LIMITS`, fo now REJECTS a pathologically-deep
  (>1000) / attribute-flooded (>256) / oversized (>100 MiB) XML that defusedxml would have dutifully parsed →
  that field degrades to null/error. On fo's corpora this fires on nothing (sweep expected NO-DRIFT); it changes
  output only on crafted adversarial input. This is a genuine derivation-behavior change (the v1.30.2
  bounded-time precedent: output changes only on pathological inputs → LOGIC bump).
  - fo's XML input is ALSO size-bounded upstream (the 128 KB OOXML deviation / `baseline_max_bytes`), so
    `max_bytes` is largely moot; the load-bearing new defense is `max_depth` — the structural gap defusedxml has
    NO answer for (bestiary's 2026-07-08 resoak confirmed: defusedxml is entity-class-only; structural blowup was
    held solely by fo's size cap until now).

## 5. Versioning (and the consumer caveat)
- **LOGIC 1.19.0→1.20.0** — driven by the `RECOMMENDED_LIMITS` structural-rejection (fo's parse behavior changes
  on pathological inputs; the v1.30.2 precedent). (A *pure* drop-in with limits OFF would be a no-LOGIC dep swap.)
- **SCHEMA unchanged (1.21)** — no new field/shape; `ScanContext.dependencies` is an existing structure.
- **⚠ CONSUMER CAVEAT (prominent):** `manifest_checksum` covers `context.dependencies`, so swapping the dep record
  (defusedxml→purexml) moves the checksum for **EVERY manifest**, not just XML-bearing ones — exactly as a chardet
  or python-magic version bump would (Pillar 1: ScanContext exists to *explain* environment variance). A consumer
  pinning `manifest_checksum` (trellis/recall) sees it move universally on the swap; the extracted values are
  unchanged. Flag trellis + recall before shipping so a re-index is expected, not a surprise.

## 6. The stdlib fallback (unchanged, documented)
No-purexml installs still fall back to plain `xml.etree` (unhardened, `LIMITATIONS` documents the risk) — and get
no `limits` (the wrapper no-ops there). Installing `file-observer[security]` (now purexml) is still the hardened
path; the swap does not change the fallback posture, only makes the hardened path pure-stdlib + maintained +
structurally capped.

## 7. Validation
- Reuse the equivalence evidence (2,695/0 + 467/0) as the transparency proof; re-run fo's full-corpus differential
  in-tree (purexml vs defusedxml → identical extracted values) as a one-shot swap-gate.
- Falsify-first `test_v1_36.py`: (a) a real OOXML/ODF scan yields identical extracted values purexml-vs-defusedxml
  (parse transparency); (b) `RECOMMENDED_LIMITS` REJECTS a crafted >1000-deep XML (the new defense engages) and the
  field degrades to null/error, not a crash; (c) the no-purexml stdlib fallback path still parses (no `limits` kwarg
  leaks to it); (d) `ScanContext.dependencies` records purexml + the limits (provenance); (e) workers byte-identical.
- Corpus sweep: expect NO-DRIFT on extracted values (corpora lack pathological XML); the checksum moves universally
  (the dep record) — assert the EXTRACTED VALUES match, not the checksum.

## 8. Review
Four legs via review-kit `route.sh --format json` (the upgraded aggregation). Particular focus: the `_xml_parse`
wrapper's limits-only-when-purexml gating (a stdlib-fallback `limits=` leak would crash), and the exception path
(`LimitExceeded` ⊂ `ValueError` lands in fo's existing except). bestiary re-soaks the structural-XML surface AFTER
the swap (newly defended). purexml's `test_fo_contract.py` is the standing cross-repo guard.

## 9. Out of scope / notes
- Not vendored — purexml is a first-party PyPI dep (its ratified adoption model).
- `Limits` is PROVISIONAL in purexml 1.x: fo pins the exact purexml version and takes a caps change only on a
  deliberate bump + re-test (a caps change can't affect real-file output, only the pathological boundary; keeping
  it provisional lets purexml track new expat CVE classes without a 2.0 — the right posture for a security control).
- Post-swap, fo's full-corpus run becomes purexml's standing second equivalence pass on each purexml release.
