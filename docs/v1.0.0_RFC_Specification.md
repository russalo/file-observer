## 1. Overview

### 1.1 Purpose

v1.0 declares File Observer stable. The schema is frozen. The public contract is binding. Downstream consumers can build on this without fear of breakage.

This is not a feature release. Nothing is added, nothing is removed. v1.0 is the moment the project says: **what you see is what you can count on.**

### 1.2 What v1.0 means

- **The schema is frozen.** Fields will not be removed, renamed, or change type without a MAJOR version bump (v2.0).
- **Additions are always safe.** New fields, vectors, and specialist namespaces may appear in MINOR bumps (v1.1+). Existing fields are untouched.
- **The public contract is binding.** PUBLIC_CONTRACT.md becomes the stability commitment to downstream consumers. Pre-1.0, it described intent. Post-1.0, it describes obligations.
- **Vectors are permanent.** The `vectors_collected[]` shape, identity digest computation (SHA-256 pipe-delimited preimage), and determinism guarantees are part of the contract.
- **The summary is permanent.** The `summary` field, its inclusion in the checksum, and the standalone Markdown report are stable.
- **Patches tune, they don't break.** PATCH releases (v1.0.x) may tune vector thresholds (method_version bumps) but never change the schema shape.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 3. Backward Compatibility Policy

### 3.1 Version semantics

| Component | What it means | When it happens |
|---|---|---|
| **MAJOR** (1.x → 2.0) | Breaking change. Field removed, renamed, or type changed. | Rare. Preceded by deprecation. |
| **MINOR** (1.0 → 1.1) | Additive change. New fields, vectors, namespaces. | Regular feature releases. |
| **PATCH** (1.0.0 → 1.0.1) | No schema change. Bug fixes, vector tuning. | As needed. |

### 3.2 Consumer guarantees

- Code written for schema `1.x` WILL work with schema `1.y` where `y > x`
- Code written for schema `1.x` is NOT guaranteed to work with schema `2.0`
- Consumers SHOULD ignore unknown fields for forward compatibility
- Consumers SHOULD branch on the MAJOR version component

### 3.3 Deprecation policy

Before a MAJOR bump:
- The affected field MUST be marked deprecated for at least one full MINOR release
- Deprecation MUST be documented in PUBLIC_CONTRACT.md and HISTORY.md
- A migration guide MUST be provided in the compliance report

### 3.4 Vector identity contract

The identity digest contract is permanent at v1.0:
- Preimage shape: `vector_id|method_version|rules_hash|static_tuning_hash|dynamic_tuning_hash|dictionary_id`
- Hash function: SHA-256, hex-encoded
- Null representation: literal string `"null"`
- Same digest + same input = same output. No exceptions.

This shape MUST NOT change without a MAJOR version bump.
