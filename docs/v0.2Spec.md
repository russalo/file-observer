# Scanner v0.2 Design Document

**Project:** Scanner
**Target Version:** 0.2.0
**Status:** Design Proposed
**Date:** 2026-04-06

---

## 1. Overview

### 1.1 Purpose

Scanner v0.2 extends the v0.1 scanner from a spec-complete extraction engine into a more usable pipeline component while preserving its role as an **observation-only system**.

v0.2 has two goals:

1. Make scanner output easier for downstream systems and humans to consume.
2. Safely probe adjacent capability areas to understand what future expansion will require.

Scanner v0.2 remains:

* deterministic
* read-only
* non-semantic
* non-classifying
* non-mutating
* non-OCR

---

### 1.2 Design Principle

> Scanner v0.2 exposes more usable signals and better operational metadata, without becoming an ingestor, classifier, or document processor.

---

### 1.3 Version Positioning

| Version | Role                                                                 |
| ------- | -------------------------------------------------------------------- |
| v0.1    | Deterministic extraction and routing contract                        |
| v0.2    | Usable manifest surface + operational metadata + bounded exploration |
| v0.3+   | Downstream consumption, routing, and broader specialist integration  |

---

## 2. Objectives

### 2.1 Primary Objectives

Scanner v0.2 MUST:

* preserve full v0.1 correctness and compliance
* improve manifest usability for downstream systems
* add operational metadata for auditing and orchestration
* support efficient re-scanning workflows
* allow limited, bounded exploration of adjacent formats and specialist metadata

---

### 2.2 Secondary Objectives

Scanner v0.2 SHOULD:

* reduce friction for scanning real-world repos and working directories
* expose mismatch/anomaly signals without interpreting them
* provide optional outputs suitable for streaming workflows

---

### 2.3 Non-Goals

Scanner v0.2 MUST NOT:

* perform classification
* infer document meaning
* rank importance
* create semantic summaries
* generate embeddings
* run OCR
* mutate source files
* link files into graphs
* make ingestion decisions
* execute downstream routing

---

## 3. Architecture Direction

### 3.1 Current v0.1 Pipeline

```text
scan_file()
  ├── Universal
  ├── Baseline
  ├── Structural
  └── Specialist (optional, minimal)
```

---

### 3.2 Target v0.2 Pipeline

```text
scan_file()
  ├── Universal
  ├── Baseline
  ├── Structural
  ├── Accessibility Layer      (new grouping / usability surface)
  ├── Diagnostics Layer        (new visibility into detection paths)
  ├── Specialist Metadata      (bounded expansion only)
  └── Routing Signals          (unchanged contract, clearer consumption)
```

At scan level:

```text
scan()
  ├── File discovery
  ├── Ignore filtering
  ├── Optional incremental comparison
  ├── File scan execution
  ├── Manifest summaries
  └── Integrity metadata
```

---

## 4. Design Themes

### 4.1 Theme A — Make Output More Accessible

v0.1 output is correct and complete.
v0.2 should make it easier to consume by:

* adding manifest-level metadata
* adding summaries
* improving output organization
* supporting JSONL output
* exposing routing state more clearly

---

### 4.2 Theme B — Safely Expand Reach

v0.2 may explore adjacent capabilities only where they are:

* low-cost
* deterministic
* bounded
* metadata-oriented
* non-transformative

This includes:

* MIME mismatch signaling
* limited specialist metadata
* formal support for a small set of already-nearby file types

---

## 5. Functional Scope

## 5.1 Track A — Accessibility and Operability

### 5.1.1 Manifest Metadata Block

Add manifest-level metadata to improve auditability and orchestration readiness.

#### Proposed shape

```json
{
  "meta": {
    "scan_id": "uuid",
    "generated_at": "2026-04-06T17:30:00+00:00",
    "source_dir": "/path/to/source",
    "config": {
      "preview_max_chars": 1000,
      "sample_size": 8192,
      "enable_specialists": false,
      "exclude_hidden": false,
      "format": "json"
    }
  }
}
```

#### Requirements

* `scan_id` MUST be unique per scan execution
* `config` MUST reflect actual runtime configuration
* metadata MUST be deterministic except for `scan_id` and `generated_at`

---

### 5.1.2 Manifest Statistics

Add a manifest-level summary block for quick inspection and downstream orchestration.

#### Proposed shape

```json
{
  "stats": {
    "total_files": 142,
    "supported_files": 131,
    "unsupported_files": 11,
    "text_files": 96,
    "binary_files": 46,
    "requires_vision": 8,
    "requires_specialist_tool": 14
  }
}
```

#### Requirements

* stats MUST be derived directly from scanned records
* stats MUST be deterministic
* stats MUST NOT require additional file reads

---

### 5.1.3 Routing Summary

Add an aggregate view of likely downstream handling categories without performing routing.

#### Proposed shape

```json
{
  "routing_summary": {
    "baseline_ready": 96,
    "binary_only": 30,
    "requires_vision": 8,
    "requires_specialist_tool": 14
  }
}
```

#### Requirements

* this block MUST be descriptive only
* it MUST NOT choose or execute downstream actions
* it MUST derive only from existing per-file fields

---

### 5.1.4 Output Format Options

Add support for alternate serialization output.

#### Initial formats

* standard JSON manifest
* JSONL / NDJSON, one file record per line

#### Requirements

* JSON remains default
* JSONL MUST preserve full per-record fidelity
* JSONL mode MAY emit manifest metadata separately or via header/footer strategy, but behavior must be documented

---

### 5.1.5 Field Grouping for Usability

v0.2 SHOULD improve output readability through clearer grouping.

This may be done by:

* additional nested objects
* consistent layer-based organization
* keeping backward compatibility where possible

Example grouping direction:

```json
{
  "universal": { ... },
  "baseline": { ... },
  "structural": { ... },
  "routing": { ... }
}
```

#### Constraint

This MUST NOT destabilize the existing contract unless versioned explicitly.

---

## 5.2 Track B — Operational Efficiency

### 5.2.1 Ignore Rules

Add support for `.scannerignore` or equivalent ignore pattern handling.

#### Goals

Allow exclusion of:

* vendor directories
* dependency directories
* build artifacts
* generated outputs
* user-defined noise

#### Examples

```text
node_modules/
.git/
dist/
build/
*.log
*.tmp
```

#### Requirements

* ignore behavior MUST be deterministic
* pattern format SHOULD be simple and documented
* hidden file exclusion and ignore patterns MUST coexist predictably
* source files excluded by ignore rules MUST not appear in the manifest

---

### 5.2.2 Incremental / Delta Scanning

Allow scanner to compare current state against a prior manifest.

#### Purpose

Avoid full reprocessing when:

* files are unchanged
* only a subset changed
* pipeline runs repeat frequently

#### Proposed shape

```json
{
  "delta": {
    "previous_scan_id": "uuid",
    "added": ["new/file.md"],
    "modified": ["docs/spec.md"],
    "unchanged": ["README.md"],
    "removed": ["old/file.txt"]
  }
}
```

#### Requirements

* delta detection MUST be based on deterministic signals
* checksum SHOULD be primary identity for file content changes
* path MUST participate in added/removed detection
* unchanged files MAY skip deeper reprocessing if implementation supports it
* behavior MUST be correct before it is optimized

#### Constraint

Incremental scanning must not alter correctness guarantees.

---

### 5.2.3 Streaming / Chunked Baseline

Reduce memory pressure when scanning large text-like files.

#### Goals

* avoid reading very large files fully unless necessary
* bound preview extraction cost
* bound tag/structural extraction effort for large files

#### Requirements

* preview SHOULD be extractable from a bounded prefix
* baseline extraction SHOULD use streaming or chunked reads when possible
* changes MUST NOT reduce correctness for normal-sized documents without explicit tradeoff documentation

#### Constraint

Determinism MUST be preserved.

---

## 5.3 Track C — Bounded Expansion

### 5.3.1 MIME Truth Layer

Expose mismatch information between:

* extension-based expectation
* content-based detection

#### Proposed shape

```json
{
  "mime_analysis": {
    "detected_mime": "image/png",
    "extension_mime": "text/plain",
    "matches_extension": false
  }
}
```

#### Purpose

Surface anomalies such as:

* spoofed files
* mislabeled files
* unexpected binary content in text-like extensions

#### Requirements

* this layer MUST be descriptive only
* it MUST NOT block scanning
* mismatches SHOULD be available as explicit signals

---

### 5.3.2 Specialist Metadata Expansion

Expand specialist tier only in metadata-safe ways.

#### Allowed direction

Specialist tier MAY expose bounded metadata such as:

##### PDF

* page count
* has text stream markers
* document metadata fields (title, author, producer, creation date)

##### DOCX

* heading count
* image count
* document properties
* approximate word count

##### RTF

* basic text extractability
* document metadata if cheaply available

#### Not allowed in v0.2

* OCR
* full semantic parsing
* layout reconstruction
* table extraction pipelines
* heavy content transformation
* deep document rewriting or normalization

#### Design rule

> Specialist v0.2 may expose metadata about the file, but must not become a document processing engine.

---

### 5.3.3 Controlled File Type Expansion

Formally add a small number of file types only where support is already nearby and low-risk.

#### Candidate additions

* `.html` / `.htm`
* `.xml`
* `.toml`

#### Conditions for inclusion

A new type should only be added if:

* baseline decoding is straightforward
* structural signals are deterministic
* no heavy new dependencies are required
* behavior can be specified clearly

#### Constraint

Do not expand formats merely for coverage. Expand where downstream value clearly outweighs complexity.

## 6. Data Model Additions

### 6.1 Manifest-Level Additions

Proposed new top-level fields:

```python
scan_id: str
meta: dict
stats: dict
routing_summary: dict
delta: dict | None
```

These may be grouped under a single top-level `meta` object if preferred.

---

### 6.2 File-Level Additions

Potential additions for v0.2:

```python
mime_analysis: MimeAnalysisRecord | None
specialist_metadata: dict | None
```

#### Example record

```python
@dataclass
class MimeAnalysisRecord:
    detected_mime: str
    extension_mime: str | None
    matches_extension: bool
```

## 7. Determinism and Integrity

### 7.1 Determinism Requirements

Scanner v0.2 MUST preserve:

* deterministic file ordering
* deterministic arrays and summaries
* deterministic delta comparison
* deterministic manifest statistics
* deterministic mismatch signaling

---

### 7.2 Integrity Metadata

v0.2 SHOULD include a manifest checksum.

#### Proposed shape

```json
{
  "manifest_checksum": "sha256(...)"
}
```

#### Purpose

* verify manifest integrity
* support caching and reuse
* support downstream audit workflows

#### Constraint

Checksum generation must be well-defined and documented.

---

## 8. CLI and UX Additions

### 8.1 Proposed CLI Additions

```bash
scanner ./project \
  --exclude-hidden \
  --ignore-file .scannerignore \
  --previous-manifest ./manifests/last.json \
  --format jsonl
```

### 8.2 Candidate Flags

| Flag                  | Purpose                                    |
| --------------------- | ------------------------------------------ |
| `--ignore-file`       | custom ignore file path                    |
| `--previous-manifest` | enable delta comparison                    |
| `--format`            | `json` or `jsonl`                          |
| `--no-stats`          | optional suppression of manifest summaries |

## 9. Testing Requirements

### 9.1 Unit Tests

Must cover:

* ignore rule matching
* delta classification
* MIME mismatch detection
* manifest stats generation
* routing summary generation
* JSONL serialization
* specialist metadata extraction boundaries

---

### 9.2 Integration Tests

Must cover:

* scanning with ignore rules
* scanning with previous manifest comparison
* mixed supported and unsupported files
* mismatch examples (extension vs content)
* large text file handling behavior

---

### 9.3 Golden Tests

Must confirm:

* deterministic manifest summaries
* deterministic delta output
* deterministic JSONL ordering
* identical outputs for identical inputs/config

---

### 9.4 Edge Cases

Must include:

* spoofed extension files
* huge text files
* ignored directories
* removed files between scans
* malformed prior manifests
* content-based MIME unavailable
* specialist dependency unavailable

---

## 10. Acceptance Criteria

Scanner v0.2 is complete when:

* v0.1 guarantees remain intact
* ignore rules work predictably
* incremental comparison works correctly
* manifest-level usability metadata exists
* routing summaries are accurate
* JSONL output works
* MIME mismatch signaling is implemented
* bounded specialist metadata exists for at least one declared specialist format
* all changes are tested and deterministic

---

## 11. Explicit Tradeoffs

### 11.1 Chosen Tradeoff

v0.2 prioritizes:

* usability
* observability
* operational readiness

over:

* aggressive extraction breadth
* heavy parsing
* semantic richness

---

### 11.2 Deferred Work

These are explicitly deferred beyond v0.2:

* OCR
* semantic classification
* graph linkage
* confidence scoring
* AI-based signal generation
* deep specialist content extraction
* parallel scanning unless determinism and ordering guarantees are fully preserved

---

## 12. Recommended Implementation Order

### Phase 1 — Accessibility

1. manifest metadata
2. stats
3. routing summary
4. JSONL output

### Phase 2 — Operability

5. `.scannerignore`
6. incremental / delta scanning
7. manifest checksum

### Phase 3 — Bounded Expansion

8. MIME mismatch signaling
9. one specialist metadata probe
10. formal support for `.html` or one additional format

---

## 13. Summary

Scanner v0.2 should not try to become a smarter scanner in the abstract.

It should become:

> a more operable, more consumable, and slightly more exploratory observation layer

That means:

* making v1 output easier to use
* exposing more about how decisions were made
* safely measuring how far the next layer of capability can go
* preserving the discipline that made v0.1 stable

---

## 14. Final Statement

Scanner v0.2 is successful if it expands **system usefulness** more than it expands **scanner complexity**.
