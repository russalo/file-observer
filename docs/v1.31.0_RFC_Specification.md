# v1.31.0 RFC (DRAFT) — promotion pass: capture-metadata (`image` EXIF + `video`) → stable

**STATUS: DRAFT — pending Russell's approval.** Designation-only promotion, the second promotion
pass after v1.23.0. No design forks — the evidence is in hand; this RFC documents the promotion.
On approval this becomes `docs/v1.31.0_RFC_Specification.md`.

## 1. Why

The v1.23.0 promotion pass (2026-06-19) promoted `preservation` and explicitly deferred the capture
fields in its §6: *"The capture fields (image EXIF, video) — season first (days old); next promotion
pass, weeks out."* This IS that pass. Assessed against the standing criterion (**settled producing
logic + evidence of value**, the v1.10/v1.14 standard), the capture-metadata surface is now ripe:

- **`image` EXIF** (v1.16, shipped 2026-06-16, ~2.5 weeks) — the EXIF / TIFF-IFD reader is
  **unchanged since ship**; settled logic.
- **`video`** (v1.17 container → v1.18 device+GPS → v1.20 `creation_date_qt`, ~2 weeks) — the ISOBMFF
  reader is **unchanged since ship**; settled logic.

**Evidence of value (corpus-grounded + oracle-gated):**
- **Oracle-validated against `exiftool`** — image EXIF and video fields matched exiftool exactly on
  the real corpora (61/61 real `.mov` for the v1.17 container; real iPhone 16 clips for v1.18; the
  synth capture corpus gated against exiftool for v1.18/v1.20).
- **Corpus coverage was deliberately built for exactly this** (2026-06-28): the shared corpus grew to
  20 corpora with `wikimedia-exif` (70 real CC/PD photos — 70/70 carry make/model, 40 geotagged, 6
  makes) + `synth-video-capture` (3 spec-valid `.mov` carrying the Apple QuickTime keys, oracle-gated).
  This closed the thin/zero coverage these fields had before.
- **Adversarial-hardened:** the capture-metadata in-house red-team (2026-06-22) battered these exact
  parsers — 21 vectors, **0 bounds/crash/determinism violations** — codified as the standing guard
  `tests/test_capture_metadata_hardening.py`. (A decorrelated bestiary fuzz pass, bestiary#23, is also
  in flight in bestiary's lane — belt-and-suspenders, NOT a gate for this promotion; see §3.)

**One honesty note for the approval:** `video.creation_date_qt` (v1.20) is the youngest field in the
set (~2 weeks). It promotes with the rest because it's part of the same oracle-gated, red-teamed
capture surface — but if you'd prefer maximum conservatism, holding *just* `creation_date_qt` one more
pass is a clean carve-out. Recommend promoting the whole surface together; flagging the choice.

## 2. The change

- **Promote the capture-metadata fields provisional → stable** — remove these 16 tuples from
  `PROVISIONAL_SPECIALIST_FIELDS`:
  - **`image` (6 EXIF):** `make`, `model`, `orientation`, `datetime_original`, `gps_present`, `xmp_present`.
    (The image dimensions `width`/`height`/`bit_depth` are already stable since v0.5 — untouched.) This
    makes the **entire `image` namespace stable.**
  - **`video` (10):** `codec`, `duration_s`, `width`, `height`, `creation_date`, `creation_date_qt`,
    `make`, `model`, `gps_present`, `gps_source`. This makes the **entire `video` namespace stable.**
- `--schema` then annotates all 16 as `stable`. No other registry changes.

## 3. The stable promise (what freezes vs not)

- **Frozen (not removable/retypable without a MAJOR bump):** the field SHAPES and presence-semantics —
  each field's name, type (`str|null`, `bool`, `float|null`, `int|null` as emitted today), and its
  place in the `image` / `video` specialist namespace. Also frozen by design intent: `gps_present` is
  **presence, not coordinates** (bool), and `gps_source` names the mechanism, not a location — that
  observe-don't-over-capture boundary is part of the stable contract.
- **NOT frozen (additive / bounded-observation stays):** `null` continues to mean *"not observed within
  bounds,"* never *"not present"* (Pillar 4) — a promoted field may still be `null` on files where the
  metadata isn't reachable, and a later release may fill more of those nulls. That's an additive value
  improvement, not a shape change (the `preservation`-table / `provenance`-table precedent).
- **Promotion freezes the SHAPE, not the parser internals.** A future bounded-safety fix (e.g. anything
  bestiary#23 surfaces) patches the EXIF/ISOBMFF reader without touching the frozen field shape — the
  always-on never-crash/bounded discipline is orthogonal to the stability tier. So promoting now does
  not pre-empt or conflict with the in-flight hardening.

## 4. What STAYS provisional / held (not swept up)

- **chatlog family** (`content_shape`, `speaker_turn_counts`, `speaker_turn_chars`, `alternation`) —
  **held**: alpha-locked (Sentinel-mirrored soft contract) and the non-count redesign will rework
  `content_shape`. Producing logic is NOT settled by design. Unchanged.
- **`presentation`** (v1.24, ~1 week) + **`audio`** (v1.25, ~1 week) — **held: too young.** Provisional
  is the data-gathering tier; these have not had a seasoning interval yet (the same discipline that
  deferred the capture fields at v1.23). Next promotion pass, weeks out.
- **`format_signatures` + `is_polyglot`** — **held-by-DESIGN** (v1.23 §2.4): the signature vocabulary
  intentionally grows every MIME change; never promotion candidates. Untouched.

## 5. Acceptance bar (falsify-first — `tests/test_v1_31.py`)

1. `--schema` annotates all 6 `image` EXIF fields + all 10 `video` fields as **`stable`**; the whole
   `image` and `video` namespaces read stable.
2. None of the 16 promoted `(namespace, field)` tuples remain in `PROVISIONAL_SPECIALIST_FIELDS` (the
   registry == the documented set — the `test_v1_14` drift guard, updated).
3. **Designation-only:** the scan manifest is **byte-identical** except the version stamps — no
   `stability` key leaks into the manifest; every image/video value is unchanged.
4. The held sets STAY provisional in `--schema`: chatlog family, `presentation`, `audio`,
   `format_signatures`, `is_polyglot`.

## 6. Version axes

- **SCHEMA 1.16 → 1.17** — a promotion is a contract change (v0.11/v1.10/v1.14/v1.23 precedent). The
  observed field VALUES are byte-identical (no value changed), but `schema_version` is in the
  `manifest_checksum` preimage, so the checksum moves for every manifest on v1.31.0 (as on any SCHEMA
  bump) — a consumer pinning the checksum will see it change; every extracted value is unchanged.
- **LOGIC unchanged (1.15.3)** — designation-only; no routing/value change.
- **SCANNER 1.30.2 → 1.31.0.** Regenerate `docs/SCHEMA.md`; update PUBLIC_CONTRACT §2.4 (drop the
  image-EXIF + video fields from the provisional list) / §3 + CONVENTIONS §1.1 version cells /
  README / HISTORY / CLAUDE.md; `COMPLIANCE-v1.31.md` before merge; STANDARDS_TRACKING touch pass;
  4-leg review.

## 7. Out of scope

- `presentation`, `audio`, chatlog family — held (see §4); season / redesign first.
- Any change to what the capture fields OBSERVE — the EXIF/ISOBMFF logic is untouched; promotion is
  designation-only.
- `creation_date_qt` carve-out (see §1) — a decision input for approval, not a separate change.
