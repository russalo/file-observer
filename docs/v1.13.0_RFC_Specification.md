# File Observer v1.13.0 RFC Specification

> **Status: SHIPPED** — released as v1.13.0 (see `docs/HISTORY.md` for the date and the patch releases that rode on this minor). Any status line below reflects the RFC's state at approval time and is kept as written.

> **Status: Specification (approved 2026-06-09).** First minor after the v1.12 PDF-residual arc + the v1.12.1 red-team / v1.12.2 error-code-centralization patches. Use-case-anchored: a prospective ingestor (and any downstream consumer) needs to know what file-observer *can* emit without reading the source or running many scans.

The genuinely-independent half (error-code centralization) already shipped as the v1.12.2 de-risk patch. This RFC covers the remaining minor-defining architecture: the provenance-trigger registry + the `--schema` surface.

## 1. Overview

### 1.1 Purpose

file-observer's output is **self-evidencing for its inputs** but **not self-describing for its capabilities**. A consumer can answer "what does this manifest say about these files?" but cannot answer "what fields / vectors / flags / errors *could* file-observer emit, and under what conditions?" — without either reading the source or running enough scans to observe the full surface empirically.

This surfaced concretely on 2026-06-08 while assembling training fixtures for a prospective ingestor: to build a corpus exercising the full output surface, a filesystem-having agent had to read `scanner.py` and enumerate everything that *can* appear. **That enumeration is the missing capability** — a consumer can't do it. And even that careful read missed two error codes (`xml_parse_failed`, `toml_parse_failed`) because they were inline literals (since centralized in v1.12.2).

`--schema` closes the gap: any installed build describes its own complete output surface, with no drift between docs and code (the schema IS the code's introspection).

```
file-observer --schema [--format json|md]
```

### 1.2 What `--schema` is NOT

- **NOT a manifest change.** `--schema` is a separate output surface, emitted only when the flag is passed. A normal scan's manifest is byte-identical to v1.12.2. `SCHEMA_VERSION` stays 1.8; `LOGIC_VERSION` stays 1.4.3.
- **NOT a new observed field.** It describes the surface; it doesn't add to it.
- **NOT runtime-config-dependent.** `--schema` reflects what the installed build CAN emit, not what a particular scan did emit.
- **NOT a replacement for PUBLIC_CONTRACT.md.** PUBLIC_CONTRACT.md is the stability *commitment* (stable / provisional / candidate). `--schema` is the *surface description* (what exists). Complementary; §4.3 explores annotating each element with its tier.

### 1.3 Normative Language

MUST / MUST NOT / SHOULD / MAY per BCP 14.

## 2. Scope discipline (what v1.13 is NOT)

- v1.13 MUST NOT change `LOGIC_VERSION` — no observation-logic change.
- v1.13 MUST NOT change `SCHEMA_VERSION` — the manifest is unchanged; `--schema` is a separate surface.
- v1.13 MUST NOT add or modify any manifest field, vector, specialist, safety_flag, or error code. It only *describes* the existing surface.
- v1.13 MUST NOT add a mandatory dependency.
- The v1.12.2 patch already centralized error codes (the genuinely-independent prerequisite). v1.13 does NOT re-do that; it builds on it.

## 3. The central decision (for approval): how to introspect

The v1.12.2 work + the corpus build established that the surface comes from three source-of-truth classes:

1. **Dataclass fields** — FileRecord, ScanManifest, etc. Introspectable via `dataclasses.fields()`.
2. **Module-level registries** — SPECIALIST_TOOLS, SPECIALIST_NAMESPACE, MAGIC_SIGNATURES, FORMAT_OBSOLESCENCE, the vector definitions, and (post-v1.12.2) all `ERR_*` error-code constants. Introspectable by reading the live module objects.
3. **signal_provenance triggers** — currently scattered as inline `trigger="..."` literals across the `detect_*` / `extract_*` methods. NOT centrally registered. This is the one remaining non-enumerable class.

### 3.1 Decision: register the provenance triggers

- **(A) Central registry (recommended).** Introduce a `PROVENANCE_TRIGGERS` registry (a module-level structure enumerating every `(method, trigger, layer, when)` tuple). Each `ProvenanceEntry(trigger=...)` site references a registry entry instead of an inline literal — same pattern v1.12.2 applied to error codes. `--schema` then reads the registry. Clean, no drift surface, one place per surface-element-class. The minor-defining work.
- **(B) AST-walk the source at build time.** Parse `scanner.py`, find all `ProvenanceEntry(trigger=...)` literals. Complete but fragile (breaks on code-shape change); heavy; reintroduces an indirect drift surface (the walker can fall out of sync with code patterns).
- **(C) Hand-maintained supplement.** A static `_SCHEMA_PROVENANCE` dict. Fast but reintroduces exactly the drift problem `--schema` exists to solve.

**Prior recommendation: (A).** Consistent with the v1.12.2 error-code centralization and the existing rule-fingerprint discipline. The registry is the minor's substance; `--schema` is a clean read on top of it. Estimated the larger half of the implementation.

### 3.2 Decision: output home

- **(A) CLI-only** (`--schema`). Source of truth; always reflects the installed build.
- **(B) CLI + committed `docs/SCHEMA.md`** regenerated per release. Browsable without running the tool; a test asserts the committed doc matches `--schema --format md` output (so it can't drift).

**Prior recommendation: (B).** CLI is the source of truth; the committed doc is the convenience + a drift-guard test target. The regeneration becomes a release-checklist step (CONVENTIONS.md).

### 3.3 Decision: stability annotation

The highest consumer value: tag each surface element with its stability tier (stable / provisional / candidate per the v1.10 ladder), so `--schema` answers not just "what fields exist" but "which can I build against."

- **(A) In scope for v1.13.** Attach tier data to the field/registry definitions; `--schema` emits it; PUBLIC_CONTRACT.md's hand-maintained tier lists become generated. Strongest value, most machinery.
- **(B) Follow-on (v1.14).** Ship `--schema` without tiers first; add annotation once the surface-enumeration is proven.

**Prior recommendation: (B) unless the tier data attaches cheaply.** The enumeration is the load-bearing capability; tiers are an enhancement. Decide at approval based on how invasive the annotation is.

## 4. Design — implementation shape (assuming recommended decisions)

### 4.1 The provenance-trigger registry (§3.1-A)

A module-level `PROVENANCE_TRIGGERS` enumeration. Each entry: `{method, trigger, layer, description}`. The `detect_*`/`extract_*` sites reference entries (or a helper validates `trigger` against the registry at construction). A guard test (mirroring v1.12.2's `test_no_inline_error_code_literals`) asserts no inline `trigger="..."` literals remain outside the registry.

### 4.2 The introspection assembler

A `build_schema_document()` function that reads:
- `dataclasses.fields(FileRecord)` + `dataclasses.fields(ScanManifest)` + the other dataclasses → field names, types, always-vs-conditional
- `SPECIALIST_TOOLS` + `SPECIALIST_NAMESPACE` + each specialist's emitted-field set
- the vector registry → vector_id, scope, method_version per vector
- the `ERR_*` constants (collected by name-prefix introspection of the module)
- `PROVENANCE_TRIGGERS`
- `MAGIC_SIGNATURES` → format list
- `FORMAT_OBSOLESCENCE` → preservation tiers
- the reference_tokens / filename_patterns subcategory lists
- the safety_flags vocabulary (from `detect_safety_flags` — may need its own small registry if not enumerable)

Emits a stable, sorted, deterministic schema document.

### 4.3 CLI surface

`--schema` short-circuits the normal scan path (like `--help`): it never reads a source directory, never emits a manifest. `--format json` (default) | `--format md`. Mutually exclusive with a scan target.

## 5. Schema & Version Constants

- `SCANNER_VERSION` 1.12.2 → 1.13.0
- `LOGIC_VERSION` unchanged 1.4.3
- `SCHEMA_VERSION` unchanged 1.8
- New CLI surface `--schema`; no new dependency.
- (If §3.3-A adopted: stability-tier data attached to definitions — still no manifest change.)

## 6. Validation Plan (falsify-first)

The falsifiable contract — `--schema` MUST be complete:

- **Error-code completeness:** scan the fixtures zoo, collect every `errors[].code`, assert each appears in `--schema` output. (This test would have caught the v1.12.2 inline-literal gap.)
- **Safety-flag completeness:** every flag the corpus can trigger MUST be in `--schema`.
- **Specialist / vector / format-signature completeness:** same cross-check against the training-fixtures bundle (`scratch/training_fixtures/`, which empirically triggers all 6 specialists, all 5 safety_flags, all 6 vectors).
- **Provenance-trigger completeness:** every `trigger` value appearing in a real manifest MUST be in the registry + in `--schema`.
- **Determinism:** same build → byte-identical `--schema` output.
- **Drift guard (if §3.2-B):** committed `docs/SCHEMA.md` equals `--schema --format md`.
- **No-inline-literal guards:** the v1.12.2 error-code guard + a new provenance-trigger guard.

The cross-checks use the training-fixtures corpus as the empirical trigger set — anything it produces must be in the schema. That makes "the corpus exercises X but `--schema` doesn't list X" a hard test failure.

## 7. Open questions to resolve at approval

1. **§3.3 — stability annotation in v1.13 or v1.14?** Depends on how cheaply tier data attaches to definitions.
2. **§3.2 — committed `docs/SCHEMA.md` or CLI-only?** Lean committed (drift-guarded), adds a release-checklist step.
3. **Ingestor timing** — is the consumer far enough along to need `--schema` near-term, or does the curated training-fixtures corpus (already delivered) suffice for now, deferring `--schema` until the consumer's requirements are concrete? *This question is partly why the RFC is in DRAFT: the corpus may be enough for the experiment's current phase.*
4. **safety_flags enumeration** — `detect_safety_flags` returns flags by inline logic; does it need its own small registry (like error codes / provenance triggers) to be `--schema`-enumerable, or is the vocabulary cleanly extractable as-is?

## 8. Provenance

This RFC was drafted from what building the v1.12.1 training-fixtures corpus surfaced (`scratch/notes_self_description_gap.md`, `scratch/output_surface_map.md`, `scratch/v1_13_schema_capability_rfc_draft.md`). The corpus-first sequencing was deliberate: building the corpus revealed (a) the surface isn't centrally enumerable, (b) the two inline error codes a constants-read misses, (c) that the long-tail (obsolete formats, exotic signatures, rare errors) is exactly what a consumer can't discover empirically and most needs `--schema` for. The central design decision (§3.1, how to introspect) is shaped directly by findings (a) and (b). The v1.12.2 patch closed (b) as the de-risk step.
