# v1.47.0 RFC — Promotion pass: `presentation` + `audio` → stable

> **Status: SHIPPED** — released as v1.47.0 (see `docs/HISTORY.md` for the date and the patch releases that rode on this minor). Any status line below reflects the RFC's state at approval time and is kept as written.

**Status:** APPROVED (scope confirmed by Russell 2026-07-17)
**Type:** Minor — field-stability promotion (contract change; extracted VALUES byte-identical, manifest_checksum moves only via schema_version)
**Version deltas:** SCANNER 1.46.8 → 1.47.0 · SCHEMA 1.23 → 1.24 · LOGIC **unchanged** 1.24.6
**Date:** 2026-07-17

## 1. Motivation

The third promotion pass, in the established cadence (v0.11 → v1.10 → v1.14 → v1.23 → v1.31).
The promotion criterion is **settled producing logic + evidence of value, NOT age** — and its
inverse (a young field stays provisional because provisional *is* the data-gathering tier).

v1.31.0 (2026-07-03) promoted the image-EXIF fields + the entire `video` namespace and
**explicitly deferred the `presentation` and `audio` namespaces**: its §6 held them as
*"presentation/audio (v1.24/1.25 — too young, season next pass)."* **This is that next pass.**
Both have now seasoned ~3 weeks — the same bar v1.31 applied to the capture-metadata fields it
promoted (v1.16–1.20, June, promoted early July) — with their producing logic unchanged since
ship.

## 2. What promotes (provisional → stable)

Remove these entries from `PROVISIONAL_SPECIALIST_FIELDS`:

**`presentation`** (introduced v1.24.0, 2026-06-25):
- `slide_count`, `title`, `author`, `application`

**`audio`** (introduced v1.25.0, 2026-06-26):
- `format`, `bitrate`, `duration_s`, `title`, `artist`, `album`, `year`

After promotion, `--schema` annotates these `stable` and `docs/SCHEMA.md` /
`docs/manifest.schema.json` regenerate to match. No other change.

Both meet the v1.31 bar (settled logic + corpus/hardening evidence). Neither is a routing flag,

## 4. What is HELD, and why (the pass is deliberately narrow)

- **The entire `chatlog` family** — `content_shape`, `speaker_turn_counts`, `speaker_turn_chars`,
  `alternation`, `first_timestamp`, `last_timestamp`, `cwd`. **Alpha-locked** ([[soft-contracts-alpha-phase]]):
  the `CHATLOG_SPEAKER_LABEL_RE` is a soft external contract with Sentinel, and the parked
  **chatlog non-count-signal redesign** (the highest-strategic backlog item, freshly motivated by
  the LongMemEval ≥3-object-floor finding + recall as a 2nd consumer) will likely rework
  `content_shape` and the session axes. Promoting a field we intend to change would be exactly
  the "promote-and-extend" mistake v1.10 avoided for `provenance`.
- **`fact_block`** (v1.32, Jul 4), **`ai_session`** (v1.33/1.35, Jul 5–8), **`lexicon_match`**
  (v1.38/1.41, Jul 10–12) + their vectors (`fact_block`, `ai_session`, `lexicon`) — **too young.**
  Provisional is the data-gathering tier; these are days-to-two-weeks old. Season to the next pass
  ([[feedback_dont_rush_young_projects]]).
- **`format_signatures`, `is_polyglot`** — **held by design** (PUBLIC_CONTRACT §2.4): the signature
  vocabulary intentionally grows on every MIME change, so freezing it would be wrong. Never a
  promotion candidate (reclassified v1.23).

## 5. Contract impact

- **Every extracted VALUE is byte-identical.** Stability lives only in `--schema` — the manifest
  serialization never consults the provisional registries — so no observed/derived value, and no
  manifest field, changes. **LOGIC frozen at 1.24.6** (no observing logic changed).
- **`manifest_checksum` DOES move for every manifest** — but only because `schema_version`
  (1.23→1.24) is itself in the checksum preimage, exactly as on any SCHEMA bump (the v1.31.0
  statement: *"a consumer pinning the checksum will see it change while every extracted value is
  unchanged"*). This is not a value change; it is the SCHEMA-version field changing. A consumer
  that re-derives from values sees nothing move; a consumer pinning the raw checksum re-baselines
  once, as on any SCHEMA release.
- **SCHEMA 1.23 → 1.24.** A promotion is a contract change even with no value change (the
  v0.11/v1.10/v1.14/v1.23/v1.31 precedent): a consumer that keys on `stability` sees these fields
  move provisional → stable, a stronger guarantee (a stable field will not be renamed or removed
  without a SCHEMA-major-style deprecation).
- **`schema_doc_version` unchanged** — the `--schema` envelope *shape* is unchanged (v1.21.2
  contract); only the `stability` annotation *values* for these fields change, and `docs/SCHEMA.md`
  + `docs/manifest.schema.json` regenerate accordingly.
- **PUBLIC_CONTRACT §3** gains a row; the stable-field inventory grows by the 11 fields above.
