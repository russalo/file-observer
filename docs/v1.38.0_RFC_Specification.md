## 1. Motivation

A downstream consumer (Sentinel's player-log path was the prompting case) needs to know,
*before* handing a file to an AI, whether the file is likely to **trip that AI's content
guardrail**. file-observer is the right place to ask because **fo is not an AI** — it reads
bytes deterministically and never invokes a model, so it can look at content that would be
risky to feed to an LLM and report *what is measurably there* without any model ever judging it.

The hard constraints that shaped the design (raised by Russell):
1. **Guardrail specifics are unpublished** — fo cannot and must not claim to predict a
   specific provider's guardrail. It counts the **consumer's own** category-tagged terms.
2. **Building it must not require handling sensitive content.** The author (an AI) would trip
   its own guardrails curating slur/violence/self-harm lists. **Resolution: bring-your-own-lexicon.**
   fo ships a **values-neutral counting mechanism**, tested exclusively with **benign placeholder
   terms** (fruit/animal words). The real sensitive lexicon is **consumer runtime config** — never
   generated by the author, never committed to the repo or tests, never echoed into the manifest.

This is the long-parked "customer-defined vectors" idea (v0.9 reserved `dictionary_id` for exactly
this) getting its first concrete instance: **a values-empty engine; the values are supplied at the edge.**

## 2. Charter fit (observe, don't interpret)

fo reports **per-category hit counts + density** — a fact ("category_a matched 3×"), never a
verdict ("this file is dangerous"). The consumer owns the threshold and the meaning. This is the
same bright line as `ai_session` (observe token sums, never price them) and `safety_flags`
(structural indicators, never threat verdicts).

## 3. What it observes

### 3.1 Input — the consumer's lexicon (runtime config)

`--lexicon <path.json>` (CLI) / `ScannerConfig(lexicon=<dict>)` (API). Shape:

```json
{ "lexicon_id": "sentinel-guardrail-v1",
  "categories": { "cat_a": ["term", "multi word term"], "cat_b": ["…"] } }
```

- Runtime-only — **excluded from `meta.config`** (like `signing_key`; consumer-private).
- **Bounded parse** (`parse_lexicon`, fail-loud → `ValueError`; CLI turns it into `rc=2`):
  `LEXICON_MAX_CATEGORIES=256`, `MAX_TERMS_PER_CATEGORY=100_000`, `MAX_TOTAL_TERMS=1_000_000`,
  `MAX_TERM_TOKENS=16`, `MAX_TERM_LEN=128`, `MAX_ID_LEN=128`. A hostile lexicon can't DoS fo.
- Terms are **case-folded + tokenized** (`[a-z0-9]+`) → canonical space-joined form; deduped, sorted.
  A term with 0 matchable tokens or >16 tokens is **rejected** (no silent miss — a dropped term is a
  false "clear", the dangerous FN for a risk detector).

**Trust boundary.** The lexicon is **consumer-supplied config** (like `extension_overrides` or a
`signing_key`) — trusted-but-bounded: fo enforces the §3.1 size caps but does not defend against a
consumer's *self-crafted* pathological lexicon (e.g. a million phrases sharing a first token). The
**untrusted input is the document**, and that is bounded (64 MiB) and walked **linearly** — single-token
terms cost O(n × categories) (a token's index bucket is bounded by the category count); only a
phrase-heavy adversarial lexicon inflates the per-token bucket, and that is the consumer's own input.

### 3.2 Matching semantics — word-boundary token(-sequence) match

**Measure-first (`scratch/measure_lexicon_match_2026-07-10.*`, benign lexicon):** substring matching
over-counts **9.4×** on benign terms (`cat`→"category", `red`→"required"); two of three categories were
100% false positives under substring, 0 under word-boundary. **Decision: word-boundary token match**
(case-folded, literal). Single-token terms → token-set membership; multi-token terms → contiguous
token-subsequence match (so hyphenated/multi-word terms work). **Literal terms only — never a
consumer-supplied regex** (that would be a ReDoS injection vector). Linear by construction; the one
internal regex is the linear `[a-z0-9]+` tokenizer (covered by the standing ReDoS battery).

### 3.3 Read scope — full-file bounded deviation

**Measure-first confirmed:** benign terms placed past the 64 KB baseline window are silently missed
by a windowed read (false "clear"). A guardrail-tripping term can sit **anywhere** in a long log, so
the observer reads the **full file** bounded to `LEXICON_MAX_FILE_BYTES = 64 MiB` (the v1.33 ai_session
/ v1.34 chatlog-axes precedent), declared `bounded_deviation` in `signal_provenance` (trigger
`lexicon_full_file`). Never-crash: a read failure falls back to the baseline window (flagged truncated).

### 3.4 Output — per file (`specialist_metadata.lexicon_match`, provisional)

```json
"lexicon_match": {
  "lexicon_id": "sentinel-guardrail-v1",
  "categories": { "cat_a": {"count": 3, "density": 0.0012}, "cat_b": {"count": 0, "density": 0.0} },
  "total_hits": 3,
  "total_tokens": 2503
}
```

- **Every defined category emitted** (0 = observed-and-clear; honest-null discipline).
- `density = round(count / total_tokens, 8)` (0.0 when the file has no tokens).
- **Terms are NEVER emitted** — only category names + counts + `lexicon_id`. Sensitive content stays
  out of the manifest by construction.
- Runs at the **baseline tier** (the lightweight pre-screen — no `enable_specialists` needed), on any
  text-decoded file, **gated on a lexicon being supplied**. Stored under `specialist_metadata` (the
  namespace container) so **no lexicon → the field is absent → existing manifests are byte-identical**.

### 3.5 Output — the neutral presence flag

A new `safety_flags` value **`lexicon_match`** fires when `total_hits ≥ 1`. Presence is a *fact*
(the file matched the supplied lexicon), not a verdict — the "canary" bit for a fast pre-screen.
Appears only on hit files → dormant scans unaffected.

### 3.6 Output — the `lexicon` vector (fingerprint + corpus aggregate)

Registered **only when a lexicon is supplied**. Carries the determinism contract:
- `rules_hash = compute_rules_hash(lexicon_rules_fingerprint())` — the **mechanism** (tokenizer
  pattern + match semantics + caps + read policy). An engine edit moves it.
- `dictionary_id = sha256(lexicon_id + sorted categories → sorted terms)` — the **supplied dictionary**.
  Moves on ANY term/category change **even if the consumer's `lexicon_id` label is unchanged** → catches
  silent lexicon drift. The digest is emitted; the terms are not.
- Both feed `identity_digest` (v0.9 §2.4). **Dual-falsification:** no forged count survives (rules_hash)
  and no silent term edit survives (dictionary_id).
- `summary`: `{lexicon_id, files_matched, category_hits: {cat: total}}` — corpus counts, no terms.

## 4. Version axes & determinism

- **SCHEMA 1.21→1.22** — additive: new `lexicon_match` specialist namespace (provisional), new
  `lexicon_match` safety_flag, new `lexicon` vector, new `lexicon_full_file` provenance trigger.
- **LOGIC 1.20.0→1.21.0** — a new baseline derivation. `manifest_checksum` moves **only for
  lexicon-supplied scans** (the v1.30 gated-feature precedent); no-lexicon scans are byte-identical,
  no routing flag flips.
- **Byte-identical across workers** (the v1.9 contract) — the per-file scan stays pure; the lexicon
  index is built once at `Scanner.__init__` from the config; corpus aggregates derive from records.

## 5. Testing (benign placeholders ONLY)

`tests/test_v1_38.py`, falsify-first. The test lexicon is benign fruit/animal words. Coverage:
dormancy (byte-identical when unsupplied), counts+density, **word-boundary-not-substring** (the measured
decision), phrase terms, presence flag, **terms-never-in-manifest**, dictionary_id moves-on-term-change /
stable-on-same, **full-file beats the 64 KB window**, hostile-lexicon fail-loud bounds, vector
registration gating, workers byte-identical, version axes. **No sensitive term appears anywhere in the
code, tests, or fixtures — the real lexicon is the consumer's runtime input.**

## 6. Non-goals / deferred (measure-first follow-ups)

- **Obfuscation resistance** (l33t / embedded / homoglyph) — round one is literal word-boundary; a
  normalization layer is a later measure-first increment if a consumer needs it.
- **Predicting a specific provider's guardrail** — out of scope by design (§1.1). fo counts the
  consumer's categories; the consumer maps categories→risk.
- **Corpus-level "risk profile" verdicts** — fo aggregates counts; interpretation is the consumer's.

Full four-leg decorrelated review (`route.sh --format json`): leg-1 in-house swarm, leg-2 cross-model
