# Scanner v0.3 Design Document

**Project:** Scanner
**Target Version:** 0.3.0
**Status:** Design Proposed
**Date:** 2026-04-07

---

## 1. Overview

### 1.1 Purpose

Scanner v0.3 deepens the observation layer. Each version stretches what we can gather, how we present it, and how far we reach into new file types. v0.3 focuses on three fronts:

1. **Gather more** — richer metadata from formats we already touch, and first contact with formats we don't.
2. **Present better** — give downstream programs enough context to understand not just *what* was found, but *how* and *why* each file was routed.
3. **Expand reach** — new specialist tools for `.msg`, `.png`, and deeper `.pdf` extraction.

The scanner remains an observation layer. It reports the news. The next program in the pipeline reads a v0.3 manifest and gets an organized, consistent dataset — every file accounted for, every routing decision transparent, every specialist signal bounded and deterministic.

Scanner v0.3 remains:

* deterministic
* read-only
* non-semantic
* non-classifying
* non-mutating
* non-OCR

---

### 1.2 Design Principle

> Scanner v0.3 makes the manifest self-explanatory. A downstream program reading a v0.3 manifest should know exactly what was found, how it was found, and what it would take to re-find it.

---

### 1.3 Version Positioning

| Version | Role |
|---------|------|
| v0.1 | Deterministic extraction and routing contract |
| v0.2 | Usable manifest surface + operational metadata + bounded exploration |
| v0.3 | Operational fidelity + specialist depth + format expansion |
| v0.4+ | Streaming pipelines, parallel scanning, broader specialist coverage |

---

## 2. Objectives

### 2.1 Primary Objectives

Scanner v0.3 MUST:

* preserve full v0.1 and v0.2 correctness and compliance
* deepen operational metadata so manifests are self-documenting
* expand specialist metadata extraction for PDF beyond v0.2 baseline
* add specialist extractors for at least two new file formats
* make every routing decision traceable through per-field signal provenance

---

### 2.2 Secondary Objectives

Scanner v0.3 SHOULD:

* make manifests "rescan-ready" — a downstream program can determine exactly why a file was routed, skipped, or failed, enabling targeted remediation
* fingerprint the scan environment so manifests are reproducible
* support partial rescans driven by specialist failure codes from prior manifests

---

### 2.3 Non-Goals

Scanner v0.3 MUST NOT:

* perform classification or infer document meaning
* rank importance or generate semantic summaries
* generate embeddings or run OCR
* mutate source files
* link files into graphs or make ingestion decisions
* execute downstream routing
* parse email bodies, attachment content, or message threads
* perform full image analysis, object detection, or pixel-level inspection

---

## 3. Architecture Direction

### 3.1 Current v0.2 Pipeline

```text
scan_file()
  ├── Universal
  ├── MIME Analysis
  ├── Baseline
  ├── Structural
  └── Specialist (optional, PDF metadata only)

scan()
  ├── File discovery + ignore filtering
  ├── File scan execution
  ├── Manifest assembly (meta, stats, routing, delta, checksum)
  └── Serialization (JSON / JSONL)
```

---

### 3.2 Target v0.3 Pipeline

```text
scan_file()
  ├── Universal
  ├── MIME Analysis
  ├── Baseline
  ├── Structural
  ├── Specialist Metadata      (expanded: PDF, PNG, MSG)
  └── Signal Provenance        (new: per-field derivation map with layer tags)

scan()
  ├── File discovery + ignore filtering
  ├── File scan execution
  ├── Manifest assembly
  │    ├── scan_context         (new: environment fingerprint)
  │    ├── meta, stats, routing_summary
  │    ├── delta (with partial rescan support)
  │    └── manifest_checksum
  └── Serialization (JSON / JSONL)
```

## 4. Design Themes

### 4.1 Theme A — Operational Fidelity

v0.2 tells you *what* was found. v0.3 tells you *how* it was found and *how to find it again*.

This means:

* environment fingerprinting so results are reproducible
* per-field signal provenance so every derived value can be traced to its source
* routing logic versioning so manifests can be compared across scanner versions

---

### 4.2 Theme B — Specialist Depth

v0.2 proved that bounded specialist metadata is safe and useful. v0.3 goes deeper on PDF and adds first-contact extractors for image and email formats.

The rule remains: extract metadata *about* the file, never *from* the file's content.

---

### 4.3 Theme C — Format Expansion

Each version stretches into new file types. v0.3 candidates:

* `.msg` — Outlook email: header-level metadata only
* `.png` / `.jpg` / `.gif` — image dimension and color signals
* `.xml` — structured text, treated like HTML/YAML
* `.toml` — configuration file, key extraction

---

## 5. Signal Layering

Every field in the manifest belongs to exactly one signal layer. The layers define what kind of observation a field represents, what it may depend on, and what rules govern it. Signal provenance (§5.1.3) tags each derived and semantic-local field with its layer.

### 5.1 Layer Definitions

#### Raw

Direct observations with no interpretation. These are byte-level facts about the file that any program reading the same file would independently agree on.

| Examples | Source |
|---|---|
| `path`, `filename`, `extension` | Filesystem path decomposition |
| `size_bytes`, `created_at`, `modified_at` | `stat()` call |
| `checksum_sha256` | SHA-256 of file bytes |
| `mime_type` (content-based) | `libmagic` byte inspection |
| `mime_type` (extension-based) | `mimetypes.guess_type()` |
| `content_preview` | First N bytes decoded to text |
| `frontmatter.raw` | Byte sequence between `---` fences |

**Rules:**
* Raw signals MUST be deterministic for identical file content
* Raw signals MUST NOT depend on other signals — they are computed directly from file bytes, the filesystem, or the path
* Raw signals do not require provenance (their derivation is self-evident)

#### Derived

Computed from one or more raw signals through deterministic logic. These are the scanner's conclusions from raw observations — a downstream program could reproduce them given the same raw inputs and the same logic version.

| Examples | Derived from |
|---|---|
| `is_binary` | sample bytes (NUL check), `mime_type` (MIME prefix/set), text ratio |
| `requires_vision` | `mime_type`, `extension`, sample bytes (text markers) |
| `requires_specialist_tool` | `extension` via `SPECIALIST_TOOLS` registry |
| `encoding` | sample bytes via `chardet` or fallback cascade |
| `mime_analysis.matches_extension` | `mime_type` (detected) vs `mimetypes.guess_type()` (expected) |
| `structural.document_keys` | parsed content (JSON `json.loads`, YAML line parsing, XML element tree) |
| `structural.csv_headers` | first line of decoded text |
| `structural.title` | regex over decoded text (markdown H1 or HTML `<title>`) |
| `structural.technology_hints` | regex patterns over decoded text |
| `tags` | regex over decoded text + frontmatter parsing |
| `specialist_metadata.page_count` | regex over PDF sample bytes |
| `specialist_metadata.width` / `height` | struct parsing of image header bytes |
| `specialist_metadata.encrypted` | `/Encrypt` presence in PDF sample |

**Rules:**
* Derived signals MUST be deterministic for identical raw inputs and identical `routing_logic_version`
* Derived signals MUST document their derivation via signal provenance
* Derived signals MAY depend on raw signals and scanner configuration, but MUST NOT depend on other derived signals (no chaining)
* Exception: `requires_vision` depends on `is_binary` (itself derived). Where derivation chains exist, provenance MUST document the full chain.

#### Semantic-Local

Signals that carry interpretive weight beyond mechanical derivation, but remain bounded to the individual file and do not cross file boundaries. These are the closest the scanner gets to meaning — they still report the news, but they editorialize slightly.

Semantic-local signals are **not present in v0.3 by default**. They are a reserved layer for future expansion.

| Candidate examples (not implemented) | What makes them semantic |
|---|---|
| `document_complexity`: `"simple"` / `"structured"` / `"complex"` | Judgment about document organization |
| `document_complexity`: `"simple"` / `"structured"` / `"complex"` | Judgment about document organization |
| `content_language`: `"en"` | Inference beyond byte-level observation |

**Rules:**
* Semantic-local signals MUST be gated behind explicit configuration (opt-in)
* Semantic-local signals MUST be tagged in signal provenance with `"layer": "semantic_local"`
* Semantic-local signals MUST document their thresholds or decision criteria in the spec
* Semantic-local signals MUST NOT cross file boundaries — no signal on file A may depend on file B
* Semantic-local signals MUST NOT perform classification, ranking, or clustering
* Semantic-local signals MUST remain deterministic

| Field | Layer | Notes |

| `errors` | meta | Error records (not a file signal) |

### 5.3 Provenance and Layers

Signal provenance entries (§5.1.3) MUST include a `layer` field:

```json
{
  "is_binary": {
    "layer": "derived",
    "source": "detect_binary",
    "tier": "universal",
    "trigger": "nul_byte_in_sample"
  },
  "mime_type": {
    "layer": "raw",
    "source": "detect_mime",
    "tier": "universal",
    "trigger": "content_based",
    "detail": "libmagic"
  }
}
```

This connects the signal taxonomy to the per-field derivation map. A downstream program can filter the manifest by layer — e.g., "show me only raw signals" or "which derived signals would change if I upgraded the scanner?"

## 6. Functional Scope

## 6.1 Track A — Operational Fidelity

### 6.1.1 Scan Context

Add an environment fingerprint to the manifest so downstream programs know *where* and *with what* the scan was performed.

#### Proposed shape

```json
{
  "scan_context": {
    "hostname": "build-server-04",
    "platform": "linux",
    "python_version": "3.12.3",
    "scanner_version": "0.3.0",
    "routing_logic_version": "0.3.0",
    "dependencies": {
      "magic": {"available": true, "version": "5.45"},
      "chardet": {"available": true, "version": "5.2.0"},
      "yaml": {"available": true, "version": "6.0.1"},
      "olefile": {"available": false, "version": null}
    }
  }
}
```

#### Requirements

* `scan_context` MUST be deterministic for a given environment (no timestamps, no random values)
* `scanner_version` MUST match the package version from pyproject.toml
* `routing_logic_version` MUST be updated when routing flag logic changes
* `dependencies` MUST report availability and version for every optional library that influences extraction logic
* dependency versions MUST be actual runtime versions (e.g., `magic.version()`, `chardet.__version__`), not package metadata
* when a dependency is unavailable, `version` MUST be `null`
* `scan_context` SHOULD include enough to explain cross-environment variance — two scans of the same files that produce different results MUST differ in their `scan_context`

---

### 6.1.2 Signal Provenance

Signal provenance tells you *which method produced which output and why*. A downstream program looking at `is_binary: true` needs to know whether that came from a NUL byte in the sample, a MIME type match, or a text-ratio failure — without re-implementing the scanner's logic.

Signal provenance covers the derived and routing-critical fields that downstream programs make decisions on. Static/identity fields (`path`, `filename`, `extension`, `size_bytes`) do not need provenance — their derivation is self-evident.

#### Proposed shape

```json
{
  "signal_provenance": {
    "is_binary": {
      "layer": "derived",
      "source": "detect_binary",
      "tier": "universal",
      "trigger": "nul_byte_in_sample"
    },
    "requires_vision": {
      "layer": "derived",
      "source": "detect_requires_vision",
      "tier": "universal",
      "trigger": "image_mime"
    },
    "requires_specialist_tool": {
      "layer": "derived",
      "source": "specialist_tools_registry",
      "tier": "universal",
      "trigger": "extension_match",
      "detail": ".pdf -> pdf_scanner"
    },
    "mime_type": {
      "layer": "raw",
      "source": "detect_mime",
      "tier": "universal",
      "trigger": "content_based",
      "detail": "libmagic"
    },
    "encoding": {
      "layer": "derived",
      "source": "decode_text",
      "tier": "baseline",
      "trigger": "chardet",
      "detail": "confidence=0.92"
    },
    "mime_analysis.matches_extension": {
      "layer": "derived",
      "source": "analyze_mime",
      "tier": "mime_analysis",
      "trigger": "mismatch",
      "detail": "detected=image/png, extension=text/plain"
    }
  }
}
```

#### Covered fields

Signal provenance MUST be provided for these fields:

| Field | Why it needs provenance |
|---|---|
| `is_binary` | Multiple detection paths (NUL byte, MIME prefix, MIME set, text ratio) — downstream needs to know which fired |
| `requires_vision` | Different triggers (image MIME, PDF without text markers) have different remediation paths |
| `requires_specialist_tool` | Extension-based registry lookup — straightforward but documents the mapping |
| `mime_type` | Content-based vs extension fallback changes confidence level |
| `encoding` | Chardet vs cascade fallback affects reliability |
| `mime_analysis.matches_extension` | Mismatch detail is the whole point of this field |

Signal provenance SHOULD be provided for these fields when non-null:

| Field | Why |
|---|---|
| `specialist_metadata` (per key) | Which extraction method produced each specialist signal |
| `structural.title` | Different extractors for markdown vs HTML |
| `structural.document_keys` | Different parsers for JSON vs YAML vs XML vs TOML |

#### Entry structure

Each provenance entry MUST have:

* `source`: string — the method or mechanism that produced the value (e.g., `"detect_binary"`, `"chardet"`, `"libmagic"`)
* `tier`: string — which capability tier (`"universal"`, `"baseline"`, `"structural"`, `"specialist"`, `"mime_analysis"`)
* `trigger`: string — the specific condition that fired (e.g., `"nul_byte_in_sample"`, `"image_mime"`, `"extension_fallback"`, `"chardet"`)

Each provenance entry MAY have:

* `detail`: string — additional context when useful (e.g., confidence score, specific MIME mismatch values, tool version)

#### Requirements

* signal_provenance MUST be present on every file record
* signal_provenance MUST be a dict keyed by field name (dot-notation for nested fields)
* provenance MUST be deterministic for identical inputs and configuration
* provenance MUST reflect what actually happened, not what was configured — if chardet was available but the cascade fired first, the trigger is the cascade, not chardet
* provenance MUST NOT include fields whose derivation is self-evident (path, filename, extension, size_bytes, checksum_sha256, timestamps)
* when a field is `null` or not applicable (e.g., `encoding` on a binary file), its provenance entry SHOULD still be present with trigger `"not_applicable"` or `"binary_file"`

---

### 6.1.3 Routing Logic Version


Add a version identifier for the routing decision logic so manifests from different scanner versions can be compared meaningfully.

#### Requirements

* `routing_logic_version` MUST be a string in `scan_context`
* it MUST change when any of these change: `detect_binary()`, `detect_requires_vision()`, `SPECIALIST_TOOLS`, `SUPPORTED_EXTENSIONS`
* it SHOULD follow the scanner version but MAY diverge if routing logic is stable across releases

---

### 6.1.4 Enhanced Delta Scanning

Extend delta scanning to support partial rescans driven by specialist failure codes.

#### Proposed additions

```json
{
  "delta": {
    "previous_scan_id": "uuid",
    "added": [],
    "modified": [],
    "unchanged": [],
    "removed": [],
    "rescan_candidates": ["docs/report.pdf"]
  }
}
```

#### Requirements

* `rescan_candidates` SHOULD list paths from the previous manifest where specialist extraction failed (had `specialist_probe_failed` errors)
* this list is advisory — it MUST NOT drive automatic rescanning
* the list MUST be sorted and deterministic

## 6.2 Track B — Specialist Depth

### 6.2.1 Deepened PDF Metadata

Expand PDF specialist metadata beyond the v0.2 baseline.

#### v0.2 baseline (preserve)

* `has_text_streams`
* `page_count`
* `title`, `author`, `producer`, `creator`, `creation_date`

#### v0.3 additions

* `encrypted`: boolean — whether the PDF appears to use encryption
* `pdf_version`: string or null — PDF version from the header (e.g., "1.4", "2.0")
* `sample_text_marker_density`: float or null — quantitative ratio of text operator markers (`BT`, `ET`) relative to the sample buffer size, calculated as `(count_BT + count_ET) / sample_size_bytes`

#### Requirements

* all new fields MUST be extractable from the existing sample buffer (no additional file reads)
* `encrypted` MUST be derived from `/Encrypt` dictionary presence in the sample
* `pdf_version` MUST be extracted from the `%PDF-X.Y` header
* `sample_text_marker_density` MUST be computed as `(count_BT + count_ET) / sample_size_bytes` over the sample buffer
* `sample_text_marker_density` is a raw quantitative signal — the scanner MUST NOT interpret it as "sparse" or "dense"; that judgment belongs to the downstream program
* `sample_text_marker_density` MUST be `null` when the sample contains no recognizable PDF content
* all new fields MUST default to `null` when not detectable from the sample

---

### 6.2.2 Image Metadata Specialist

Add a specialist extractor for image files to surface structural signals without performing image analysis.

#### Supported formats

* `.png`
* `.jpg` / `.jpeg`
* `.gif`

#### Proposed shape

```json
{
  "specialist_metadata": {
    "width": 1920,
    "height": 1080,
    "bit_depth": 8,
    "color_type": "rgb",
    "has_alpha": true,
    "format_version": "PNG 1.2"
  }
}
```

#### Requirements

* image metadata MUST be extracted from file headers using stdlib `struct` or equivalent — no Pillow dependency
* PNG: parse IHDR chunk for width, height, bit depth, color type
* JPEG: parse SOF0/SOF2 markers for width, height, component count
* GIF: parse logical screen descriptor for width, height
* all extraction MUST operate on the existing sample buffer
* fields that cannot be determined from the sample MUST be `null`
* this specialist MUST NOT decode pixel data, perform color analysis, or inspect image content

#### Design rule

> Image specialist extracts structural envelope metadata. It answers "what kind of container is this?" not "what does the image show?"

---

### 6.2.3 Email Metadata Specialist (.msg)

Add a specialist extractor for Outlook `.msg` files to surface header-level metadata.

#### Proposed shape

```json
{
  "specialist_metadata": {
    "subject": "RE: Project Update",
    "from": "alice@example.com",
    "to": ["bob@example.com"],
    "date": "2026-03-15T10:30:00",
    "has_attachments": true,
    "attachment_count": 2
  }
}
```

#### Requirements

* `.msg` parsing MAY use the `olefile` library (lightweight OLE2 compound document parser)
* extraction MUST be limited to header-level properties — no body parsing, no attachment content extraction
* if `olefile` is unavailable, specialist MUST degrade gracefully (return `null` specialist_metadata, record error)
* `from`, `to`, `subject`, `date` MUST be extracted from OLE2 property streams
* `has_attachments` and `attachment_count` MUST be derived from the attachment table, not from body parsing
* all string values MUST be UTF-8 serializable
* this specialist MUST NOT parse, decode, or expose email body content

#### Design rule

> Email specialist extracts the envelope. It answers "who sent what to whom and when?" not "what does it say?"

---

## 6.3 Track C — Format Expansion

### 6.3.1 Formal Support for .xml

Add `.xml` to the supported file type list.

#### Baseline behavior

* text decoding via existing cascade
* content preview
* tag extraction (hashtags)
* technology hint detection

#### Structural signals

* `document_keys`: root element name and direct child element names (similar to JSON/YAML key extraction)

#### Requirements

* XML parsing MUST use stdlib `xml.etree.ElementTree` — no lxml dependency
* parsing failures MUST be non-fatal (record error, continue)
* only the root element and its direct children are inspected — no deep traversal
* namespace prefixes SHOULD be preserved in key names

---

### 6.3.2 Formal Support for .toml

Add `.toml` to the supported file type list.

#### Baseline behavior

* text decoding via existing cascade
* content preview
* tag extraction (hashtags)

#### Structural signals

* `document_keys`: top-level keys (same pattern as YAML/JSON)

#### Requirements

* TOML parsing MUST use stdlib `tomllib` (available in Python 3.11+)
* parsing failures MUST be non-fatal
* only top-level keys are extracted — no deep traversal

---

### 6.3.3 Image Files in Supported Extensions

Add `.png`, `.jpg`, `.jpeg`, `.gif` to `SUPPORTED_EXTENSIONS`.

#### Rationale

With the image metadata specialist (§5.2.2), these formats now have meaningful specialist output beyond universal-tier processing. Adding them to `SUPPORTED_EXTENSIONS` removes the `unsupported_extension` error and signals that the scanner has intentional coverage.

#### Requirements

* these extensions MUST remain `is_binary = True`
* these extensions MUST remain `requires_vision = True`
* specialist metadata extraction is gated by `enable_specialists` as with all specialist work
* without specialists enabled, these files still produce universal-tier records with correct routing flags

---

### 6.3.4 Email Files in Supported Extensions

Add `.msg` to `SUPPORTED_EXTENSIONS`.

#### Requirements

* `.msg` MUST be treated as binary
* `requires_specialist_tool` MUST be `True`
* `specialist_tool` MUST be `"msg_parser"`
* specialist metadata extraction is gated by `enable_specialists`

## 7. Data Model Additions

### 7.1 Manifest-Level Additions

```python
scan_context: ScanContext     # new: environment fingerprint
```

Added to `ScanManifest` alongside existing `meta`, `stats`, `routing_summary`, `delta`, `manifest_checksum`.

#### ScanContext dataclass

```python
@dataclass
class DependencyInfo:
    available: bool
    version: str | None         # runtime version, or None if unavailable

@dataclass
class ScanContext:
    hostname: str
    platform: str
    python_version: str
    scanner_version: str
    routing_logic_version: str
    dependencies: dict[str, DependencyInfo]  # "magic", "chardet", "yaml", "olefile"
```

### 7.2 File-Level Additions

```python
signal_provenance: dict[str, ProvenanceEntry]     # new: per-field derivation map
```

Added to `FileRecord` alongside existing fields.

#### ProvenanceEntry dataclass

```python
@dataclass
class ProvenanceEntry:
    layer: str          # "raw", "derived", or "semantic_local" (from §5)
    source: str         # method or mechanism that produced the value
    tier: str           # capability tier that produced it
    trigger: str        # specific condition that fired
    detail: str | None  # optional additional context
```

### 7.3 Delta Additions

```python
rescan_candidates: list[str]    # new: paths with prior specialist failures
```

Added to `DeltaRecord`.

### 7.4 Specialist Tool Registry Expansion

## 8. Dependency Policy

### 8.1 Existing Dependencies (unchanged)

| Dependency | Purpose | Fallback |
|---|---|---|
| `python-magic` | Content-based MIME detection | Extension-based inference + diagnostic error |
| `chardet` | Encoding detection | Fixed cascade (utf-8 → utf-8-sig → cp1252 → latin-1) |
| `PyYAML` (optional) | Frontmatter parsing | String-splitting fallback |

### 8.2 New Dependencies

| Dependency | Purpose | Required | Fallback |
|---|---|---|---|
| `olefile` | .msg OLE2 property extraction | Optional | `specialist_metadata = null` + error record |

### 8.3 Stdlib-Only Extractors

| Format | Stdlib Module | Notes |
|---|---|---|
| PNG | `struct` | IHDR chunk parsing |
| JPEG | `struct` | SOF marker parsing |
| GIF | `struct` | Logical screen descriptor |
| XML | `xml.etree.ElementTree` | Root + child element names |
| TOML | `tomllib` | Top-level key extraction (Python 3.11+) |
| PDF (deepened) | `re` | Regex on existing sample buffer |

## 9. Determinism and Integrity

### 9.1 Determinism Requirements

Scanner v0.3 MUST preserve all v0.2 determinism guarantees and additionally:

* `scan_context` MUST be deterministic for a given environment
* `signal_provenance` MUST be deterministic for identical inputs and configuration
* `rescan_candidates` MUST be sorted
* image metadata extraction MUST be deterministic
* email header extraction MUST be deterministic
* `sample_text_marker_density` MUST be deterministic for identical sample content

### 9.2 Integrity

* `manifest_checksum` computation MUST include `scan_context`, `signal_provenance`, and all new fields
* checksum MUST remain verifiable via `compute_manifest_checksum()`

v0.3 does not require new CLI flags. All new features activate through existing mechanisms:

* specialist metadata: `--specialists`
* new file types: automatic (added to `SUPPORTED_EXTENSIONS`)
* scan context: always included
* signal provenance: always included

### 10.2 Candidate Future Flags

These are noted for consideration but NOT required for v0.3:

| Flag | Purpose |
|---|---|
| `--no-provenance` | Suppress per-file signal provenance for smaller output |
| `--rescan-from` | Combined with `--previous-manifest`, only rescan candidates |

## 11. Testing Requirements

### 11.1 Unit Tests

Must cover:

* scan context assembly and determinism
* signal provenance for all covered fields (is_binary triggers, requires_vision triggers, mime_type source, encoding source, mime_analysis mismatch)
* signal provenance correctness — trigger must match the actual detection path taken
* signal provenance layer assignment matches §5 taxonomy
* PDF deepened metadata: encrypted detection, pdf_version, sample_text_marker_density
* PNG IHDR chunk parsing (valid, truncated, missing)
* JPEG SOF marker parsing (valid, progressive, truncated)
* GIF logical screen descriptor parsing
* .msg header extraction (valid, missing properties, olefile unavailable)
* XML root/child key extraction (valid, malformed, namespace)
* TOML key extraction (valid, malformed)
* delta rescan_candidates generation

### 11.2 Integration Tests

Must cover:

* full scan with specialists enabled produces specialist metadata for PDF, PNG, JPEG, GIF, MSG
* scan context present and correct in manifest
* signal provenance present on every file record with correct triggers and layers for each derived field
* new supported extensions (xml, toml, png, jpg, gif, msg) no longer produce unsupported_extension errors
* JSONL output includes all new fields

### 11.3 Golden Tests

Must confirm:

* scan context deterministic across repeated scans (same machine)
* signal provenance deterministic across repeated scans
* image metadata deterministic
* all new specialist metadata deterministic

### 11.4 Edge Cases

Must include:

* truncated PNG (IHDR chunk incomplete)
* JPEG with no SOF marker in sample
* encrypted PDF
* .msg without olefile installed
* .msg with missing properties (no subject, no date)
* malformed XML (non-fatal error)
* TOML with syntax errors (non-fatal error)
* binary file disguised as .xml
* empty .msg file
* zero-byte image files

## 12. Acceptance Criteria

Scanner v0.3 is complete when:

* v0.1 and v0.2 guarantees remain intact
* scan context is present and deterministic
* signal provenance is present on every file and explains every derived routing/detection field with correct layer tags
* PDF specialist metadata includes encrypted, pdf_version, and sample_text_marker_density
* image specialist metadata extracts dimensions from PNG, JPEG, and GIF
* .msg specialist extracts header-level email metadata
* .xml and .toml are formally supported with structural signals
* .png, .jpg, .jpeg, .gif, .msg are formally supported
* rescan_candidates appears in delta output when applicable
* all changes are tested and deterministic
* all new specialist dependencies degrade gracefully when unavailable

## 13. Explicit Tradeoffs

### 13.1 Chosen Tradeoffs

v0.3 prioritizes:

* traceability — every routing decision is logged
* reproducibility — environment fingerprint enables re-scanning
* breadth — more file types with bounded specialist coverage

over:

* depth — no deep parsing, no content extraction, no body text
* performance — signal provenance adds per-file overhead (acceptable at current scale)
* minimalism — more fields in the manifest (justified by downstream consumption value)

### 13.2 Deferred Work

These are explicitly deferred beyond v0.3:

* OCR
* semantic classification
* email body parsing or attachment extraction
* image content analysis (object detection, text extraction)
* DOCX/RTF specialist metadata (heading counts, word counts)
* parallel scanning
* confidence scoring
* graph linkage between files
* streaming scan output (real-time file-by-file emission)

## 14. Recommended Implementation Order

### Phase 1 — Operational Fidelity

1. scan context (environment fingerprint with dependency versions)
2. signal provenance (per-field derivation map with layer tags)
3. routing logic version

### Phase 2 — Specialist Depth

4. deepened PDF metadata (encrypted, pdf_version, sample_text_marker_density)
5. image metadata specialist (PNG, JPEG, GIF)
6. .msg email metadata specialist

### Phase 3 — Format Expansion

7. formal support for .xml
8. formal support for .toml
9. add image extensions and .msg to SUPPORTED_EXTENSIONS
10. enhanced delta with rescan_candidates

## 15. Summary

Scanner v0.3 makes the manifest tell the full story. Not just what files exist and what they contain, but how the scanner found them, what it tried, what worked, and what it couldn't do. Downstream programs reading a v0.3 manifest get a dataset that is organized, consistent, and self-explanatory — ready for the next stage of the pipeline without guesswork.

The stretch continues: more formats, deeper metadata, better presentation. The discipline stays: observe, record, report. Never interpret, never mutate, never decide.

---

## 16. Final Statement

Scanner v0.3 is successful if a downstream program can read the manifest and never need to ask "why was this file routed this way?", "where did this value come from?", or "what version of the scanner produced this?" The answer should be in the data.
