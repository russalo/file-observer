# Scanner v0.6.0 RFC Specification

**Project:** Scanner
**Target Version:** 0.6.0
**Status:** Approved
**Date:** 2026-04-09
**Extends:** v0.5.0 RFC Specification

---

## 1. Overview

### 1.1 Purpose

v0.6 continues toward scanner 1.0 maturity. It adds three capabilities that are independently useful and build on each other:

1. **Configurable extraction depth** — dip switches for per-extension tuning
2. **Structural file signatures** — raw magic bytes and multi-signature detection
3. **Data integrity envelope** — chain of custody and optional signing

All three are additive. No fields removed, renamed, or retyped. Schema version bumps to `1.1`.

### 1.2 Design Principle

> v0.6 makes the scanner configurable for different jobs, honest about what's inside each file, and verifiable as an integrity record. Three features building toward 1.0 readiness.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 2. Feature A — Configurable Extraction Depth

### 2.1 New Config Fields

```python
@dataclass
class ScannerConfig:
    # ... existing fields ...
    specialist_budget: int = 131072          # 128KB — replaces hardcoded deviation
    extension_overrides: dict[str, dict[str, Any]] = field(default_factory=dict)
```

### 2.2 specialist_budget

* replaces the hardcoded 128KB deviation for XLSX/DOCX specialists
* any specialist that reads beyond the sample buffer uses this value
* recorded in `meta.config` and provenance `detail.read_budget_bytes`

### 2.3 extension_overrides

Per-extension config overrides. Keys are extensions (e.g., `".csv"`), values are dicts of config field overrides:

```python
config = ScannerConfig(
    baseline_max_bytes=65536,
    extension_overrides={
        ".csv": {"baseline_max_bytes": 1048576},
        ".txt": {"baseline_max_bytes": 524288},
        ".pdf": {"specialist_budget": 262144},
    }
)
```

#### Requirements

* overrides apply to `baseline_max_bytes`, `specialist_budget`, and `preview_max_chars`
* overrides MUST NOT apply to `sample_size` (detection buffer must be consistent across all files for deterministic routing)
* per-file effective config MUST be resolved at the start of `scan_file()` by merging global config with extension override
* effective `baseline_max_bytes` MUST be >= `sample_size`
* effective config values MUST be recorded in provenance `detail` for any field where the override was used
* `extension_overrides` MUST appear in `meta.config`

### 2.4 Named Profiles (CLI convenience)

```bash
scanner ./project --profile fast_sort
scanner ./project --profile deep_extract
scanner ./project --profile general --override .csv:baseline_max_bytes=2097152
```

Three built-in profiles:

| Profile | baseline_max_bytes | specialist_budget | enable_specialists |
|---|---|---|---|
| `fast_sort` | 8192 (= sample_size) | 0 | False |
| `general` | 65536 (default) | 131072 | False |
| `deep_extract` | 1048576 (1MB) | 524288 (512KB) | True |

#### Requirements

* profiles are sugar — they set config values, nothing more
* `--override` applies after profile, can override individual extensions
* profiles MUST NOT introduce any behavior not expressible through ScannerConfig

## 3. Feature B — Structural File Signatures

### 3.1 New Fields on FileRecord

#### file_signature (raw)

```json
{
  "file_signature": {
    "magic_bytes": "ffd8ffe0",
    "magic_length": 4
  }
}
```

* first 16 bytes of the file as lowercase hex string
* `magic_length` is the number of raw bytes captured (always 16 unless file is shorter)
* `null` for zero-byte files
* extracted from existing sample buffer
* raw signal — no interpretation

#### format_signatures (derived)

```json
{
  "format_signatures": [
    {"format": "image/jpeg", "offset": 0},
    {"format": "application/pdf", "offset": 42}
  ]
}
```

* all recognized format signatures found in the sample buffer
* scanned against a built-in signature table (no new dependency)
* sorted by offset
* empty list when no known signatures match

#### is_polyglot (derived)

```json
{
  "is_polyglot": true
}
```

* `true` when `len(format_signatures) > 1` with distinct primary formats
* `false` otherwise
* provenance records which signatures triggered the flag

### 3.2 Built-in Signature Table

```python
MAGIC_SIGNATURES = [
    (b"\x89PNG\r\n\x1a\n", 0, "image/png"),
    (b"\xff\xd8\xff",       0, "image/jpeg"),
    (b"%PDF-",              None, "application/pdf"),      # any offset
    (b"PK\x03\x04",         0, "application/zip"),
    (b"\xd0\xcf\x11\xe0",   0, "application/x-ole-storage"),
    (b"{\\rtf",             0, "application/rtf"),
    (b"GIF87a",             0, "image/gif"),
    (b"GIF89a",             0, "image/gif"),
    (b"RIFF",               0, "riff_container"),
    (b"<!DOCTYPE",          None, "text/html"),
    (b"<?xml",              None, "text/xml"),
]
```

* `offset=0` means signature must be at file start
* `offset=None` means scan entire sample for this signature
* table is deterministic and stable — additions only in minor versions

### 3.3 Specialist MIME Guard

Before running a specialist, verify that `mime_type` is compatible with the expected format:

```python
SPECIALIST_MIME_GUARD = {
    "pdf": {"application/pdf"},
    "image": {"image/png", "image/jpeg", "image/gif"},
    "email": {"message/rfc822", "application/vnd.ms-outlook"},
    "spreadsheet": {"application/zip", "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"},
    "document": {"application/zip", "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
                 "application/msword", "application/x-ole-storage", "text/rtf", "application/rtf"},
}
```

* if `mime_type` not in guard set for the specialist namespace, skip extraction
* record `specialist_probe_failed` error with `message: "mime_type mismatch — skipped"`
* prevents misleading metadata (e.g., PDF specialist on a text file named `.pdf`)

## 4. Feature C — Data Integrity Envelope

### 4.1 Chain of Custody

Add `previous_manifest_checksum` to `DeltaRecord`:

```json
{
  "delta": {
    "previous_scan_id": "uuid",
    "previous_manifest_checksum": "sha256hex...",
    "added": [],
    "modified": [],
    "unchanged": [],
    "removed": [],
    "rescan_candidates": []
  }
}
```

* read from the previous manifest's `manifest_checksum` field
* enables chain verification: manifest N's `previous_manifest_checksum` == manifest N-1's `manifest_checksum`
* `null` when no previous manifest provided

### 4.2 Manifest Signing (optional)

Add `manifest_signature` to `ScanManifest`:

```json
{
  "manifest_signature": {
    "algorithm": "hmac-sha256",
    "key_id": "scanner-prod-2026",
    "value": "hex..."
  }
}
```

* `null` when signing is not configured
* signs over `manifest_checksum`
* new config field: `signing_key: str | None = None` and `signing_key_id: str | None = None`
* HMAC-SHA256 only in v0.6 — asymmetric signing deferred

#### Requirements

* `manifest_signature` MUST be `null` when `signing_key` is not set
* `manifest_signature` MUST NOT be included in the deterministic checksum preimage (it depends on the checksum)
* `key_id` MUST be a stable identifier, not the key itself
* signing MUST be deterministic: same checksum + same key = same signature

## 5. Schema Impact

Schema version bumps to `"0.6"`. All changes are additive:

| Field | Location | Type |
|---|---|---|
| `file_signature` | FileRecord | object or null |
| `format_signatures` | FileRecord | list |
| `is_polyglot` | FileRecord | bool |
| `manifest_signature` | ScanManifest | object or null |
| `delta.previous_manifest_checksum` | DeltaRecord | string or null |

No fields removed, renamed, or retyped. v0.5 consumers that ignore unknown fields remain compatible.

## 6. Implementation Order

### Phase 1 — Dip Switches
1. `specialist_budget` config field (replaces hardcoded 128KB)
2. `extension_overrides` config field
3. Per-file effective config resolution in `scan_file()`
4. Provenance records effective config values
5. Named profiles (fast_sort, general, deep_extract)
6. CLI `--profile` and `--override` flags

### Phase 2 — Structural Signatures
7. `file_signature` raw field (first 16 bytes as hex)
8. Built-in signature table + scanner
9. `format_signatures` derived field
10. `is_polyglot` derived flag
11. Specialist MIME guard

### Phase 3 — Integrity Envelope
12. `previous_manifest_checksum` on DeltaRecord
13. `manifest_signature` with HMAC-SHA256
14. `signing_key` and `signing_key_id` config fields
15. Schema version bump to `"0.6"`

## 7. Acceptance Criteria

v0.6 is complete when:

* `specialist_budget` is configurable and replaces hardcoded deviation
* `extension_overrides` works for baseline_max_bytes, specialist_budget, preview_max_chars
* named profiles produce correct config values
* `file_signature` exposes first 16 bytes as hex on every file
* `format_signatures` lists all detected signatures in sample
* `is_polyglot` is true when multiple distinct formats detected
* specialist MIME guard prevents wrong-format extraction
* `previous_manifest_checksum` links delta scans cryptographically
* `manifest_signature` signs the checksum when key is configured
* all v0.5 tests pass without modification (backward compatible)
* schema_version is `"0.6"`

---

## 8. Final Statement

v0.6 is the scanner growing into its responsibilities without outgrowing its architecture. Configurable depth makes it useful for different jobs. Structural signatures make it honest about what's inside files. The integrity envelope makes it trustworthy as a record. All three serve different consumers — but they all come from the same manifest.
