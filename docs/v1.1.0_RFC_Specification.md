## 1. Overview

### 1.1 Purpose

v1.1 is the **first additive release after the v1.0 schema freeze**. Its job is twofold:

1. Add genuinely useful corpus-level observation depth — **duplicate detection** and **per-specialist quality stats**.
2. Be the first proof that the v1.0 public contract holds: new fields appear, `SCHEMA_VERSION` goes `1.0 → 1.1`, and **every v1.0 consumer keeps working unchanged**.

Theme: **Corpus Intelligence.** Both features are pure observation computed from data the scanner already collects — no new file reading, no routing change.

### 1.2 What v1.1 adds (and what it does not)

- **Adds:** `quality.duplicate_clusters` (+ summary counts) and `quality.specialist_stats`. Both **provisional** (per the v0.9 internal-field-set pattern) — promotable to stable in a later release after corpus validation.
- **Does not:** change any existing field, type, or routing decision. `LOGIC_VERSION` stays `1.0.0` — no file routes differently than in v1.0. Nothing is removed or renamed.

### 1.3 Normative Language

Per BCP 14 (RFC 2119 / RFC 8174).

## 2. Duplicate Clustering (provisional)

### 2.1 Rationale

Every `FileRecord` already carries `checksum_sha256`. Files with an identical checksum have identical content. Grouping them is free, deterministic, pure observation — and directly serves migration/dedup, archival, e-discovery, and PKM (all named by external reviewers). The scanner reports the clusters; the consumer decides what to delete. *(Observe, don't act.)*

### 2.2 The `quality.duplicate_clusters` field

A new field on `ScanQuality`:

```json
"duplicate_clusters": [
  {
    "checksum_sha256": "9f86d081884c7d65…",
    "size_bytes": 1024,
    "count": 3,
    "paths": ["a/report.pdf", "b/report.pdf", "c/copy of report.pdf"]
  }
]
```

- MUST contain one entry per checksum shared by **two or more** files (`count >= 2`). Single-occurrence files MUST NOT appear.
- `size_bytes` is the shared file size (identical content ⇒ identical size).
- `paths` MUST be the scan-relative paths of every file in the cluster.
- **Determinism (MUST):** clusters sorted by `count` descending, then `checksum_sha256` ascending (a total order — checksum is unique per cluster). `paths` within each cluster sorted ascending.

### 2.3 Summary counts

`ScanQuality` also gains two convenience scalars:

- `duplicate_cluster_count`: number of clusters (`count >= 2`).
- `redundant_file_count`: `sum(count - 1)` across clusters — the number of files that are redundant copies (what a dedup pass could remove).

The human-readable `summary` SHOULD mention duplicates when any exist (e.g. *"N duplicate clusters, M redundant copies"*).

### 2.4 Edge cases

- **Empty files:** all zero-byte files share the SHA-256 of the empty string and will cluster together. This is correct (they are byte-identical) and MUST NOT be special-cased.
- Clustering operates on every file with a computed `checksum_sha256` (text and binary alike).

## 3. Per-Specialist Stats (provisional)

### 3.1 Rationale

The most-repeated external concern (3+ independent reviews) is **specialist-parser maintenance risk**. The honest answer is to make specialist quality **visible** rather than implied. `ScanQuality.specialist_failures` already exists as an aggregate; v1.1 breaks it down per tool.

### 3.2 The `quality.specialist_stats` field

A new field on `ScanQuality`, keyed by specialist tool name:

```json
"specialist_stats": {
  "image_structure": { "attempted": 40, "succeeded": 40, "failed": 0 },
  "pdf_extraction":  { "attempted": 12, "succeeded": 11, "failed": 1 }
}
```

- Keys are the semantic specialist tool names (`pdf_extraction`, `image_structure`, `email_envelope`, `spreadsheet_structure`, `document_extraction`, `chatlog_signals`).
- `attempted`: files routed to that tool (`requires_specialist_tool` true and `specialist_tool == name`) with specialists enabled.
- `failed`: of those, files carrying `ERR_SPECIALIST_PROBE_FAILED`.
- `succeeded`: `attempted - failed`.
- **Determinism (MUST):** keys serialized in sorted order.
- When `enable_specialists` is false, no tool is attempted, so the field MUST be an empty object.
- The existing aggregate `specialist_failures` is **retained unchanged** (this is the per-tool detail beneath it).

### 3.3 Companion documentation (non-normative)

A specialist **maturity-tier** table SHOULD be added to docs (e.g. CONVENTIONS.md / README) — e.g. "PDF text: mature; OLE2 author: best-effort" — so consumers can read the per-run stats against a stated baseline.

## 4. Schema & Version Constants

- `SCHEMA_VERSION`: `1.0` → `1.1` (additive — new fields only).
- `SCANNER_VERSION`: `1.0.2` → `1.1.0`.
- `LOGIC_VERSION`: **`1.0.0` unchanged.** No routing decision changes; both features are derived aggregates over already-collected data. (`LOGIC_VERSION` tracks routing logic specifically — see CONVENTIONS §1.2.)

## 5. Backward Compatibility

This is the **first exercise of the v1.0 backward-compatibility policy** (PUBLIC_CONTRACT.md §6):

- Purely additive: two new `ScanQuality` fields + two scalars. No field removed, renamed, or retyped.
- A `SCHEMA_VERSION` `1.1` is still major-version `1` → v1.0-targeting consumers MUST keep working (they branch on the MAJOR component and ignore unknown fields, per the contract).
- Both new fields ship **provisional** (§2.4 internal-field-set convention): they MAY change shape in a later MINOR before being promoted to stable. Consumers SHOULD treat provisional fields as such.

---

## 6. Implementation Notes

- **Duplicate clustering** reuses the `{path: checksum_sha256}` mapping the delta logic already builds (`scanner.py` `_build_*`/delta path). Group by checksum, emit clusters with `count >= 2`. O(n) over records.
- **Per-specialist stats** reuses `FileRecord.specialist_tool` + `ERR_SPECIALIST_PROBE_FAILED` (already counted for `specialist_failures`). One pass over records, bucketed by tool.
- Both computed in `_build_summary`/`ScanQuality` assembly after all records exist (corpus scope). No new file I/O.
- New `ScanQuality` fields get safe defaults (`field(default_factory=...)`) so older code paths and tests constructing `ScanQuality` continue to work.

## 7. Validation Plan

- Re-scan corpora with known duplicates (CP jobs data — WinCan `Trash/` mirror trees are a natural duplicate source; self-scan; Tika). Confirm cluster counts, determinism (identical manifest across repeated runs), and that empty-file clustering behaves.
- Confirm `specialist_stats` sums reconcile with the existing `specialist_failures` aggregate.
- All v1.0 tests MUST pass unchanged (no behavioral change); add tests for the two new fields, determinism, empty-file edge case, and the specialists-disabled empty-object case.

## 8. Acceptance Criteria

v1.1 is complete when:

- `SCHEMA_VERSION` is `"1.1"`, `SCANNER_VERSION` is `"1.1.0"`, `LOGIC_VERSION` is `"1.0.0"`.
- `quality.duplicate_clusters`, `duplicate_cluster_count`, `redundant_file_count`, and `quality.specialist_stats` are emitted, deterministic, and documented in PUBLIC_CONTRACT.md §2.4 as provisional.
- Existing v1.0 fields are byte-identical for inputs with no duplicates and specialists disabled (additive-only proof).
- All prior tests pass; new tests cover the additions.
- Compliance report written (`docs/COMPLIANCE-v1.1.md`).
- HISTORY.md, CONVENTIONS.md tracking inventory, README updated.
