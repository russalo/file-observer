## 1. Overview

### 1.1 Purpose
A document pipeline routing on "what is this and where did it come from" increasingly
faces phone-captured media: HEIC/JPEG photos and MP4/MOV video carrying EXIF and
QuickTime metadata — camera make/model, capture datetime, orientation, and GPS. v1.15
made the scanner *detect and recognize* these formats; v1.16 makes it *observe their
capture metadata*, observe-only, with the privacy-bounded `geotagged` disclosure.

### 1.2 Why it fits the provenance seam
v1.6 added the `provenance` vector (WHO authored / WHAT tool / WHEN / digitization).
Capture metadata is the device-origin complement: `Make`/`Model` is the *capturing
device*, `DateTimeOriginal` the *capture moment*, GPS-presence the *was-it-geotagged*
signal. It's the same observe-don't-interpret discipline applied to a new metadata layer.

## 2. Scope discipline (what v1.16 IS and is NOT)
> **SUPERSEDED for video (see the Status correction at the top):** the **video** bullets
> in this section (§2 IN, §5.4) and §9 were written when video was scoped *into* v1.16.
> v1.16.0 shipped the **image** bullets only; all **video** scope/design moved to
> `docs/v1.17.0_RFC_Specification.md` (its own minor). Read the video bullets below as the
> v1.17 design, not as v1.16 deliverables.

**IN:**
- **Image EXIF** (JPEG + HEIC): `Make`, `Model`, `DateTimeOriginal`, `Orientation`,
  and **GPS-presence** (the GPS IFD pointer, tag `0x8825`). Image **dimensions** for
  HEIC (the `ispe` box) — parallels the PNG/JPEG `image_structure` dims (§8 Q3).
- **Video container metadata** (MP4/MOV, the ISOBMFF family): codec, duration,
  resolution, `mvhd` creation_time, Apple `com.apple.quicktime.*` keys
  (make/model/creationdate), and **GPS-presence** via
  `com.apple.quicktime.location.ISO6709` (iPhone) / `udta` `©xyz` (Android).
- **`geotagged` safety-flag** — observe-WITH-disclosure: presence of location metadata
  is flagged, the coordinates are NOT extracted (§5.3). The v1.12
  `extraction_permission_bypassed` pattern (a new well-known value on `safety_flags`).
- **A new `video` specialist** + extending `image_structure`/EXIF to HEIC; video
  extensions recognized in `SUPPORTED_EXTENSIONS` (the v1.15.1 recognition pattern).

**OUT:**
- **GPS coordinates.** We flag presence; we do NOT decode/store latitude/longitude
  (privacy; GDPR-conscious — location is personal data). The coordinates stay in the
  file; the consumer with a need + a basis reads them directly.
- **Vendor MakerNotes** (Apple/Samsung proprietary) — undocumented, reverse-engineered;
  out of observe-only scope. We live entirely in the documented standard tags.
- **Metadata reconciliation** (§5.2) — when EXIF/XMP/IPTC disagree we REPORT each
  source's value, we do NOT pick a winner (the MWG finding).
- **Full XMP / IPTC extraction** — XMP is presence + a couple of fields at most (§8 Q1);
  IPTC and C2PA are tracked for later (STANDARDS_TRACKING).
- **A new runtime dependency** (§5.1).

## 3. Measure-first (done — `scratch/measure_capture_metadata.py`)
A stdlib hand-parser prototype was built against a real corpus (`scratch/v1_16_corpus/`:
iPhone-13 HEIC + GPS-tagged Nikon/Canon jpgs + camera jpgs + a sample mp4). Findings:
- **JPEG EXIF is fully hand-parseable in stdlib/`struct`** — `Make`/`Model`/`Orientation`/
  `DateTimeOriginal` + GPS-presence extracted cleanly (Canon 40D + GPS, Nikon P6000 +
  GPS, Nikon D70 / Sony no-GPS). No Pillow, no library.
- **GPS-presence works** via the GPS IFD pointer; real-world prevalence is mixed (2 of 4
  cameras) — exactly the variance measure-first wanted.
- **HEIC: full extraction PROVEN in the prototype.** A ~30-line version-aware `iloc`
  parser (ISO 14496-12: version-dependent item_count/item_ID widths, construction_method,
  index_size) resolves the `Exif` item byte range, and the TIFF block parses identically
  to JPEG. Real results: `IMG_5195.HEIC` → Apple/iPhone 11 Pro Max + **GPS-present**,
  `iphone_13_pro_max.HEIC` → Apple/iPhone 13 Pro Max (no GPS). The one feared cost is
  closed — it's stdlib, no library load-bearing. (7/7 corpus images carry EXIF; 4/7 are
  geotagged — mixed, as measure-first expected.)
- **Video `moov` is not necessarily first** (the sample's boxes: `ftyp free mdat moov`)
  → the **head + bounded-tail read** design is warranted (the recurring tail-read lesson:
  PDF trailer v1.5/v1.7, OLE2 v0.7.1). Full real-phone-video metadata (QuickTime keys +
  GPS + true moov-at-end) is measured via the parked iPhone-`.mov` path before locking
  the video specialist.

## 4. Specs (researched 2026-06-15; in STANDARDS_TRACKING "Moving toward v1.16")
- **EXIF — CIPA DC-008** (freely published): TIFF/IFD0 (`Make` 0x010F, `Model` 0x0110,
  `Orientation` 0x0112), Exif sub-IFD (`DateTimeOriginal` 0x9003), GPS IFD (pointer
  0x8825). Tag structure stable across Exif 2.x–3.1.
- **HEIF Exif item — ISO/IEC 23008-12**: EXIF is an item via `meta`→`iinf`/`infe`
  (item_type `Exif`) + `iloc`, NOT an APP1 marker. Image dims in `ispe`.
- **Video — ISO 14496-12 (ISOBMFF)** + **Apple QuickTime keys** (published) + **ISO
  6709** (the location string format). `moov`/`mvhd` for creation_time; `meta`/`keys`/
  `ilst` for the Apple keys; `udta`/`©xyz` for Android location.
- **XMP — ISO 16684-1** (presence marker `http://ns.adobe.com/xap/1.0/`).
- **MWG / IPTC / C2PA** — awareness; C2PA is the high-value future provenance extension.

## 5. Design decisions

### 5.1 Dependencies: NONE added
v1.16 ships **zero new runtime dependencies.** EXIF (JPEG + HEIC `iloc`) and ISOBMFF
video metadata are parsed in **stdlib + `struct`**, consistent with the project's
"PNG IHDR / JPEG SOF / ISOBMFF via struct, not Pillow" ethos and proven by the §3
prototype. This contrasts v1.8 (which added optional `pypdf` because the stdlib decoder
had a *real gap* — exotic predictors); v1.16 has no such gap, so no library is
load-bearing. It also aligns with v1.15's direction (we made `python-magic`
Windows-conditional to *reduce* dependency friction). **ExifTool is a dev-time oracle
only** (§6), never a shipped dependency. (A future full-MakerNote-decode effort — out
of scope here — could revisit an optional extra.)

### 5.2 Observe, don't reconcile (report per-source)
The MWG "Guidelines for Handling Image Metadata" map equivalent EXIF/IPTC/XMP fields but
**stalled on precedence** (ExifTool became the de-facto authority; no agreed "which
wins"). For an observe-don't-interpret tool that's the answer: **surface each source's
value as observed; never pick a winner.** Reconciliation is the consumer's job. This
also avoids the "which date is real" bug class we met with PDF `/Info`.

### 5.3 GPS: presence, not coordinates (observe-with-disclosure)
The `geotagged` `safety_flag` fires when location metadata is present (GPS IFD in EXIF;
ISO-6709 location box in video). **Coordinates are not extracted or stored** — the
disclosure says "this file carries location," the consumer decides. Mirrors v1.12's
`extraction_permission_bypassed` (a flag, not an action) and honors the privacy line
from the photo-source discussion (GPS is personal data).

### 5.4 Recognition + new specialist (the v1.15.1 pattern)
- **HEIC** gains real extraction: the `image_structure`/EXIF specialist runs on it
  (v1.15.1 recognized it without a specialist; v1.16 adds the specialist). `iloc`-based
  Exif item + `ispe` dims.
- **Video**: a new `video` specialist (`video_structure`?) + the ISOBMFF-family
  extensions (`.mp4`/`.mov`/`.m4v`; `.mkv`/`.avi` per §8 Q5) added to
  `SUPPORTED_EXTENSIONS` and `SPECIALIST_TOOLS`/`SPECIALIST_NAMESPACE`. Reuses/extends
  the existing hand-rolled ISOBMFF walk (`ftyp`, the v1.8 ObjStm decoder).
- **Head + bounded-tail read** for video (§3 — `moov` may be at the end), capped like
  the PDF whole-file read (`PDF_FULL_READ_CAP` analog).

### 5.5 New fields (all provisional)
- `specialist_metadata.image`: `make`, `model`, `datetime_original`, `orientation`,
  `gps_present` (bool), `width`/`height` (HEIC, parallel to PNG/JPEG).
- `specialist_metadata.video`: `codec`, `duration_s`, `width`/`height`, `creation_date`,
  `make`/`model` (QuickTime keys), `gps_present` (bool).
- `safety_flags`: new value `geotagged`.
- All start **provisional** (new observations; the candidate "image EXIF" graduates
  candidate→provisional — the v1.10 ladder).

## 6. Falsify-first contract (`tests/test_v1_16.py`) + the ExifTool oracle
- **ExifTool as oracle (dev-only):** the hand-parser's extracted fields are gated by
  agreement with `exiftool` on the measurement corpus — exactly as `pypdf` gated the
  v1.8 stdlib decoder. We accept a field only where it matches ExifTool (never a wrong
  value; null on the exotic cases we don't cover).
- `geotagged` fires iff location metadata is present, and **no coordinate appears in the
  manifest** (a grep-the-manifest test — the privacy contract, falsifiable).
- EXIF fields byte-stable across `--workers` (Pillar 1).
- Never-crash on malformed/truncated EXIF + ISOBMFF (the v1.8.1 bounded-observation
  discipline carried into the new parsers).
- Self-generated + CC fixtures (Wikimedia geotagged is publishable; the iPhone-specific
  validation stays local-gitignored per the privacy line).

## 8. Sign-off items — RESOLVED (Russell, 2026-06-15)
1. **XMP depth** → **presence + creator-ish** for v1.16; **full XMP depth flagged as a
   future upgrade** (§9).
2. **Video metadata depth** → **both container-level AND per-track**, observe-only
   (applies to v1.16's video, which is in-scope, gated — see #7).
3. **HEIC dimensions** → **include** (`width`/`height` from `ispe`, parallel to PNG/JPEG).
4. **`geotagged`** → **both** — a `safety_flags` value (disclosure headline) AND a
   per-specialist `gps_present` bool (structured observable).
5. **Video extensions** → ISOBMFF family (`.mp4`/`.mov`/`.m4v`) in v1.16; `.mkv`
   (Matroska) / `.avi` (RIFF) deferred (different containers).
6. **Specialist name** → **`video_structure`** (v1.16's video specialist).
7. **Scope/sequencing** → *(original decision, SUPERSEDED — see the Status correction at
   the top.)* The RFC originally scoped video to ship *within* v1.16, gated on real-`.mov`
   validation. As it played out, only the image half was de-risked and shipped as v1.16.0;
   the video half adds a new namespace + specialist + SCHEMA bump, so it is **its own
   minor, v1.17.0, with its own RFC** (`docs/v1.17.0_RFC_Specification.md`) — still gated
   on the parked iPhone-`.mov` validation, but no longer framed as a 1.16.x follow-on (a
   new observable surface is never a patch). The §3/§5 video design carries forward. The
   broader **ungated upgrade** (§9) remains separately flagged for later.

## 9. Ungated upgrade — flagged for later (undated, NOT gated to this RFC)
A separate, undated upgrade that is *not* part of v1.16's gated scope — flagged so it
isn't lost, to be picked up on its own when we choose, not blocked behind a precondition:
- **Full XMP depth** — beyond v1.16's presence + creator-ish: the wider
  Dublin-Core/rights/edit-history XMP property set (#1).
- **Broader capture/provenance expansion** — e.g. **C2PA / Content Credentials**
  (signed authenticity manifests from cameras + AI generators — the strategic provenance
  extension), and deeper per-vendor signals. Tracked in `STANDARDS_TRACKING.md` Awareness.

(Video capture metadata is NOT here — it became its own minor, **v1.17.0**; the
container/track half shipped there, the iPhone QuickTime-keys + GPS half stays gated on
