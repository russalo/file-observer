# File Observer v1.11.0 RFC Specification

**Status: SHIPPED** — released as v1.11.0 (see `docs/HISTORY.md` for the date and the patch releases that rode on this minor). The status line below is the RFC's state at approval time, kept as written.

> **Status (at approval time): Specification (approved 2026-06-06).** First minor after the v1.10 provisional-lifecycle release. Adds **`--watch`** — a continuous trigger loop that re-runs file-observer on FS events and emits each scan's delta to stdout. **No change to what is observed**; `--watch` only controls *when* observation triggers. Headline contract: **each individual scan in the stream is byte-identical to a one-shot `file-observer` invocation against the filesystem state at the moment of trigger.** `LOGIC_VERSION` and `SCHEMA_VERSION` unchanged. The release is **use-case-anchored**: Sentinel's NPC / item / lore watchers (and any equivalent downstream interpreter) read the emitted deltas and fan their schemas at the consumer layer; file-observer stays one-pass, per-event.
>
> **§3 decisions resolved at approval (with recommended priors; §6.1 measurement still gates final mechanism details):** §3.1 debounced batch rescan; §3.2 watcher library decided by measurement (lean watchfiles); §3.3 stdout JSONL deltas. **§7 open questions resolved at approval:** files[] excluded by default with opt-in `--watch-include-files`; initial scan emits a full delta-vs-empty at startup; Sentinel named as anchor consumer in §1.1, design generic.

## 1. Overview

### 1.1 Purpose

Let downstream consumers (Sentinel's NPC / item / lore watchers, ingest pipelines, dashboards, anything that wants near-real-time signal from observed files) consume file-observer's manifest **as the filesystem changes**, instead of running file-observer batch-style on a schedule. Each rescan is still the same deterministic one-shot scan; the watcher is the trigger loop.

The use case anchoring scope: the seven-project chatlogs corpus that just landed at `/srv/projects/pkplab/chatlogs/` (~200 MB across 19 files at v1.10.0 release time, growing) is exactly the realistic workload — long-lived processes (project Claude sessions) continuously appending to large `.jsonl` files, several simultaneously, in well-defined subdirs. Sentinel's downstream watchers (NPC/item/lore) want to know *when chatlog deltas land*, not poll every minute.

### 1.2 What `--watch` is NOT (the positioning question, addressed up front)

The biggest risk: `--watch` could muddy file-observer's "deterministic observer, not a watcher" positioning. The RFC resolves it explicitly:

> file-observer is a deterministic observer that emits a manifest on each invocation. `--watch` is a **trigger loop** — the same scan, fired on FS events, output streamed. The contract on each individual scan is unchanged. This is the `tsc --watch` / `sass --watch` model: a known harness for re-running a deterministic operation, not "an intelligently-reasoning watcher." We are not watching *for* anything; we are re-running the observer when something changed.

This is the same lesson as `--workers N` in v1.9: a runtime control over *when/how fast*, not *what*. `LOGIC_VERSION` and `SCHEMA_VERSION` stay frozen because nothing about the observation logic changed.

### 1.3 Normative Language

MUST / MUST NOT / SHOULD / MAY per BCP 14.

## 2. Scope discipline (what v1.11 is NOT)

- **NOT a change to what is observed.** No field changes. No new vectors. No new specialists. No new detection logic. Output of any single rescan is byte-identical to a one-shot `file-observer` invocation against the same filesystem state. `LOGIC_VERSION` stays `1.4.3`; `SCHEMA_VERSION` stays `1.8`.
- **NOT recorded in the manifest.** `--watch` (and any watch-related flags) is a pure runtime trigger, with no causal link to any single scan's output. It MUST NOT appear in `ScanContext`, `meta.config`, or any checksummed field — same precedent as `--workers` / `--progress` (v1.9, runtime-only, excluded from `meta.config`).
- **NOT a daemon / systemd unit.** Runs in the foreground; the user invokes it (or wires their own systemd / cron / supervisor around it). Same as the existing CLI.
- **NOT a network service.** Output goes to stdout. Downstream consumers pipe it (a Sentinel ingestor, a script, `jq`, whatever). The `--watch` CLI does NOT expose a port, callback URL, or webhook.
- **NOT incremental-hash optimization.** The parked "incremental read from last-known offset" idea (relevant because chatlog appends to a 35 MB jsonl currently re-hash the whole file) is **out of scope** for v1.11 — separate optimization, its own release. This RFC is just the trigger loop.
- **NOT a multi-schema scanner.** The decision between "fan vectors across workers" vs "let multiple downstream consumers each interpret in their own schema" is settled at the *consumer* layer (Sentinel watchers fan NPC/item/lore), not inside file-observer. file-observer stays one-pass per event.
- **NOT cross-platform certified at ship time.** Linux is the only certified platform for v1.11 (the build host is origin-core Linux; the realistic adopter — Sentinel's ingestor — also runs Linux). macOS and Windows may work depending on watcher-library backend, but are not validated; future polish.

## 3. The central decisions (UNRESOLVED, for approval after §6 prototype)

These three decisions interact. The build's first step (§6) is to **prototype enough to measure**, then choose. Recommendations below are the *prior*, not commitments.

### 3.1 Triggering granularity — what does the watcher rescan on an event?

- **(a) Whole-tree rescan on every event.** Simplest; the determinism guarantee is the existing v0.3 contract verbatim. **Cost:** rescans the full tree even on a 1-file change — on `chatlogs/` today that's ~2.1 s of work per event (measured at workers=4). At high event rates (multiple simultaneous active sessions appending) this dominates.
- **(b) Single-file rescan + delta-merge.** Cheap per event; only touches the changed file. **Cost:** complex. Requires the scanner to support "scan-one-file-into-an-existing-manifest"; vector aggregates need incremental update or recompute. The current contract ("each `Scanner.scan()` is a deterministic one-shot") would have to be extended to "each emitted manifest is deterministic given the cumulative event stream" — a NEW determinism contract, which is harder to specify and harder to verify.
- **(c) Debounced batch rescan.** Collect FS events over a debounce window (e.g. 200 ms; configurable `--watch-debounce-ms`), then trigger one whole-tree rescan. Hybrid: still whole-tree (preserves the existing contract verbatim) but skips when no events fired in the window, and amortizes bursts. Adds debounce latency (up to the window).

**Prior recommendation: (c) — debounced batch rescan.** Preserves the existing one-shot determinism contract (no new contract needed), bounds the rescan rate, handles bursts cleanly. (a) is the same shape but unbounded; (b) is the most clever but the contract change is meaningful work. § 6 measures whether (c)'s rescan cost on `chatlogs/` is acceptable for the realistic event rate.

### 3.2 Watcher library — what listens to the FS?

- **(a) `watchdog`.** Most popular Python FS-watcher; wide platform support (Linux inotify, macOS FSEvents, Windows ReadDirectoryChangesW). Mature, dependency-heavy, ~5+ years actively maintained.
- **(b) `watchfiles`.** Rust-backed (Notify library), faster startup, lower overhead, used by uvicorn / FastAPI. Newer; tighter API.
- **(c) Stdlib polling fallback.** `os.scandir()` + `mtime` check on a loop. No new dep. Bad latency (poll interval ≥100 ms), and unable to detect content-only changes that don't move mtime. Useful only as a fallback if inotify limits are hit on very large trees.

**Prior recommendation: lean toward (b) `watchfiles`** for cold-start cost and lower-overhead steady-state. **Both backends require new optional deps** — likely `file-observer[watch]` extra, gated like `olefile` and `pypdf`. `--watch` without the dep installed: print an actionable error message and exit. § 6 measures cold-start cost + event latency for both on `chatlogs/`.

### 3.3 Output mode — what does `--watch` emit?

- **(a) Stream of deltas to stdout (JSONL).** Each rescan emits a single JSON line: `{delta: {...}, stats: {...}, scan_id: ..., timestamp: ...}` or similar. Downstream consumers (Sentinel watchers, scripts) read from stdin. Pipeline-friendly.
- **(b) Periodic snapshot manifests to disk.** Write a full manifest file on each rescan, like the existing `--output` model. Larger volume; better for archive but harder to consume in a pipeline.
- **(c) Both.** Stdout deltas + optional `--watch-snapshot-interval N` writing full manifests to a configured dir.

**Prior recommendation: (a) stdout JSONL.** Unix-pipeline-native, matches how Sentinel's watchers consume the substrate, smallest surface to specify and verify. If snapshots become a real need they can ship in a later minor.

## 4. Design — implementation shape (assuming the recommended decisions)

### 4.1 CLI

```
file-observer --watch [SOURCE]
  --watch-debounce-ms N    # default 200; events within window collapse to one rescan
  --workers N              # carries over from v1.9; uses kept-warm process pool (§4.3)
  --progress               # carries over from v1.9; stderr only
```

`--watch` is incompatible with `--format jsonl` and `--output PATH` at the top level (those are about a single one-shot manifest; `--watch` *is* a stream). Specifying both = exit 2 with a message.

### 4.2 Initial scan + event loop

1. **Initial scan at startup.** Run a full scan and emit it as the first delta (with empty `previous_manifest_checksum`, so the consumer sees the world state at watch-start). This anchors the stream — downstream consumers don't need to do their own initial discovery.
2. **Subscribe to FS events** on the source dir (recursive). 
3. **Event loop:**
   - Collect events into a buffer.
   - Wait `--watch-debounce-ms` from the *last* event in the buffer.
   - Trigger a rescan; emit the resulting delta as one JSONL line on stdout.
   - Empty the buffer; resume.

Each emitted delta carries `previous_manifest_checksum` from the prior emit, so consumers can verify the chain (existing v0.6 chain-of-custody mechanism, reused).

### 4.3 Process pool kept warm (interacts with `--workers`)

The v1.9 `ProcessPoolExecutor` has a non-trivial cold-spawn cost; respawning per rescan would dominate at high event rates. So `--watch` MUST open the pool **once at startup** and reuse it across rescans. `_scan_paths_parallel` gains an optional `pool=` parameter; the watch driver constructs the pool and passes it in. Existing one-shot CLI behaviour unchanged (each invocation still constructs + tears down its own pool).

### 4.4 Never-crash carried into the watch loop

Any exception from a single rescan (a worker failure, an inotify hiccup, an I/O blip) MUST NOT terminate the watch loop. The driver catches at the rescan boundary, emits a structured error line to stderr, and continues. Same v1.8.1 lesson, applied to the new execution path.

### 4.5 Graceful shutdown

SIGTERM / SIGINT terminates cleanly: stop accepting new events, finish the in-flight rescan if any, emit the final delta, close the pool, exit 0. Important for systemd-managed setups.

### 4.6 What the manifest looks like in stream mode

Each line on stdout is one JSON object:
```json
{
  "scan_id": "…",
  "timestamp": "…",      // emit time, not stable (excluded from any per-scan checksum)
  "manifest_checksum": "…",  // identical to a one-shot scan at the same FS state
  "previous_manifest_checksum": "…",  // chain to previous emit
  "schema_version": "1.8",
  "context": {...},
  "stats": {...},
  "quality": {...},
  "routing_summary": {...},
  "delta": {...},                  // the load-bearing field — what changed
  "vectors_collected": [...],
  "summary": "…"
}
```

Note: `files[]` is **excluded** by default to keep each emit small (the delta tells the consumer what to look up); a `--watch-include-files` flag MAY add it back if a consumer needs the full record set per emit. **Open question (§7)**: is the default right? Sentinel watchers may want the full FileRecord for any changed file inline, to avoid a follow-up read.

## 5. Schema & Version Constants

| Constant | v1.10.0 | v1.11.0 | Why |
|---|---|---|---|
| `SCANNER_VERSION` | 1.10.0 | **1.11.0** | New `--watch` capability; new optional `[watch]` dep |
| `LOGIC_VERSION` | 1.4.3 | **1.4.3 (unchanged)** | No detection/routing change; each rescan's output is identical to a one-shot |
| `SCHEMA_VERSION` | 1.8 | **1.8 (unchanged)** | Stream format reuses existing manifest + delta shapes; no new fields |

No vector `method_version` changes. New optional error code MAY be needed for watch-loop errors (e.g. `watch_event_failed`, `watch_pool_failed`) — TBD in §7.

## 6. Validation Plan (measure-first, then falsify-first)

1. **Measure before building (the gating step, as in v1.8 §6 and v1.9 §6.1).** A minimal prototype to answer the three §3 decisions:
   - **§3.1**: How long does a whole-tree rescan of `chatlogs/` take in steady state? (v1.10 shakedown said 2.1 s @ workers=4; re-confirm for `--watch` with kept-warm pool.) Is debounced-batch acceptable for the use case, or is single-file delta required?
   - **§3.2**: `watchdog` vs `watchfiles` cold-start cost + per-event latency on `chatlogs/`.
   - **§3.3**: Stdout JSONL delta size — is it small enough that an emit-per-event is reasonable? (likely yes for 19 files; verify.)
   - **The honest gate:** if event-to-emit latency is >1 s on a single chatlog append, `--watch` isn't actually realtime; the design must either commit to "near-realtime" framing or pull in incremental-hash (out of scope). Either is OK, but the RFC must state which.
2. **Falsify-first determinism unit test.** Snapshot a fixture tree, run a one-shot `file-observer` against it (manifest A), then `--watch` for a single event-triggered rescan against the same tree (manifest B), assert `A.manifest_checksum == B.manifest_checksum`. This is the contract; it MUST pass.
3. **Empirical sweep — watch-vs-one-shot equality as a Layer-A invariant.** Extend `corpus_sweep.py` to scan the real corpora at `--workers 4` one-shot AND via `--watch` with a single forced rescan; assert byte-identical manifests. Layer-A: no baseline; divergence is always real.
4. **Never-crash under the watch loop.** A red-team file that fails specialist extraction MUST be caught at the rescan boundary; the watch loop continues; a structured error line goes to stderr — a `tests/test_v1_11.py` repro.
5. **All four review legs** per `decorrelated-code-review`. Important angles: (in-house) "find an order-dependence in the watch loop" / "find a way the kept-warm pool can drift across rescans"; (Gemini cross-model) /maestro on the watch driver; (sweep) extended Layer-A; (PR bots) standard.

## 7. Open questions to resolve at approval

1. **§3.1 triggering granularity** — debounced batch (recommended), whole-tree-always, or invest in single-file delta? Coupled to §6.1 measurement.
2. **§3.2 watcher library** — `watchfiles` (recommended) or `watchdog`? Decided on §6.1 measurement; new optional extra `file-observer[watch]`.
3. **§3.3 output mode** — stdout JSONL only (recommended) or also periodic snapshot manifests?
4. **§4.6 `files[]` inclusion default** — exclude by default to keep emits small, with `--watch-include-files` opt-in (current default); OR include by default since the realistic consumer (Sentinel watchers) needs per-file detail anyway. Lean exclude; revisit on first real consumer feedback.
5. **§4.2 initial-scan behaviour** — emit a full delta-vs-empty at startup (recommended; anchors the stream), or skip and wait for the first FS event?
6. **Sentinel use-case commitment** — does the RFC commit to the NPC/item/lore watcher shape as a named anchor consumer (drives `files[]` default, debounce default, etc.), or stay use-case-agnostic? Lean: name Sentinel as the anchor consumer in §1.1 but design generically. The shape that works for Sentinel will work for the other plausible consumers.

SCANNER 1.10.0→1.11.0; LOGIC + SCHEMA unchanged. The §6.1 prototype + measurement is the first build step, before any §4 code lands.*
