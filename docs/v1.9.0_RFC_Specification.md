# File Observer v1.9.0 RFC Specification

> **Status: Specification (approved 2026-06-05).** First minor after the post-v1.5 PDF arc.
> Adds **opt-in parallel scanning (`--workers N`)** plus a **stderr-only progress
> indicator** — a *performance* change with **no change to what is observed**. The
> headline and the hard bar are the same statement: the manifest is **byte-identical
> regardless of worker count**, so **`LOGIC_VERSION` and `SCHEMA_VERSION` do not
> move** (§5). If any output differs across worker counts, the feature is not
> shippable — that is the falsifiable claim, not an aspiration (§6).
>
> **Central fork (§3) — RESOLVED by measurement (2026-06-05): a process pool.** The
> §6.1 payoff measurement is done (table in §6.1). A **process pool gives 3.4–5.4×**
> on realistic trees (and ≈4× even on the many-tiny-files overhead worst-case), while
> a **thread pool is net-negative** on the common cases (0.42–0.95× — GIL-bound, and
> the shared libmagic cookie is thread-unsafe). So **Option A (multiprocessing)**;
> threads and the hybrid are declined. **Build, not defer** — the payoff is real. The
> only remaining open items are the smaller defaults (§7), now resolved per the
> recommendations. **Approved 2026-06-05.**

## 1. Overview

### 1.1 Purpose

Let File Observer scan a large tree faster by processing files concurrently, while
preserving the v0.3 capability-locked-determinism pillar **exactly**: identical
inputs + identical `ScanContext` → identical manifest, *independent of how many
workers ran*. Parallelism changes **how fast**, never **what**.

Motivation is real-corpus scale: the CP jobs corpus is ~34k files and the review
sweep covers ~18k; a single-process scan leaves cores idle on I/O- and parse-bound
work. This is the perf upgrade flagged as backlog item **D** ("`--workers N`,
determinism-bound") paired with its companion ("a progress indicator, stderr only,
never touches the manifest").

### 1.2 What is parallel, and what is not

The per-file unit — `scan_file(path)` — is **embarrassingly parallel**: each
`FileRecord` is derived from one file's bytes + filesystem metadata, with no
dependence on any other file. The serial tail is the **corpus-scoped aggregation**
(author_aggregate, provenance, duplicate_clusters, the per-directory summary, the
file-scoped vector folds), which reads the *collected* records.

The one obstacle is that `scan_file` is **not currently pure**: it mutates Scanner
instance state mid-scan (`_filename_patterns_applied_count`,
`_filename_patterns_sums`, `_reference_tokens_*`, and it registers file-scoped
vectors into the `VectorRegistry`). Parallel completion order would leak into those
aggregates. The core of v1.9 is therefore a **purity refactor** (§4.1), not the
pool itself.

### 1.3 Normative Language

The key words MUST, MUST NOT, SHOULD, MAY are to be interpreted per BCP 14.

## 2. Scope discipline (what v1.9 is NOT)

- **NOT a change to what is observed.** Every field, in every record, in every
  aggregate, is byte-identical to a `--workers 1` (serial) scan. `LOGIC_VERSION`
  stays `1.4.2`; `SCHEMA_VERSION` stays `1.7`. (§5)
- **NOT recorded in the manifest.** `--workers` is a pure runtime knob with **no
  causal link to output**, so it MUST NOT appear in `ScanContext`, `meta`, or any
  checksummed field — recording it would both imply false causality and break the
  byte-identical guarantee. Same for the progress indicator (stderr only).
- **NOT default-on.** Default is `--workers 1` (today's exact serial path). Parallel
  is **opt-in**; the determinism guarantee is opt-in-verified, never forced on an
  unsuspecting consumer.
- **NOT distributed / multi-node.** Single machine, one pool. No network, no shared
  queue service.
- **NOT an async/await rewrite.** The synchronous `scan_file` stays synchronous; we
  parallelize *across* files, we do not make the per-file path async.
- **NOT a relaxation of the never-crash contract.** A worker dying on a hostile file
  MUST degrade to an `ErrorRecord`, exactly as the serial path does (§4.3) — the
  v1.8.1 bounded-observation discipline is carried into the parallel path.

## 3. The central decision — concurrency model (FORK, for approval)

Where the per-file cost lives decides the model. Per file the scanner does: a
bounded `read_sample` + a full-file `hash_file` (I/O + `hashlib`, **both release the
GIL**), MIME sniff, and pure-Python work (regex passes, dict building, the
specialist parsers) which is **GIL-bound**. The mix is the whole question.

**Option A — `multiprocessing.Pool` (true parallelism).**
- *Pro:* real parallelism for the GIL-bound parse/regex work; the determinism story
  is clean (workers return values, parent orders them).
- *Con:* per-file pickling of `FileRecord` back to the parent + worker spawn cost +
  higher memory. For a tree of many *tiny* files, that overhead can **erase** the
  gain (measure — §6). `olefile`/`pypdf`/libmagic must be import-safe per process.

**Option B — `ThreadPoolExecutor` (GIL-bound, but I/O + hashing overlap).**
- *Pro:* zero serialization, low overhead, trivially shares the read sample. The
  I/O wait + `hashlib`/zlib C sections (which release the GIL) overlap well.
- *Con:* the pure-Python parse/regex half stays effectively serialized by the GIL —
  speedup caps at the I/O+C fraction.

**Option C — measured hybrid.** Threads for I/O/hash-dominated trees, processes for
parse-dominated trees, chosen by a cheap heuristic or an explicit `--pool {thread,
process}`. More surface; only justified if §6 shows the two regimes both matter.

**Not considered:** free-threaded (no-GIL) CPython — 3.13+ experimental, below our
support floor; revisit when stable.

**RESOLVED (2026-06-05) — Option A (multiprocessing).** The §6.1 measurement *killed*
the Option-B hypothesis. The GIL bounds the pure-Python parse/regex half, so a thread
pool caps at ~1.6× in the best (parse-heavy) case and is **net-negative** (0.42–0.95×)
on both common cases — *slower than serial*. It is also unsafe as written: the shared
`self._magic` libmagic cookie (`scanner.py:994`) is not thread-safe, so threads would
need a per-thread Scanner (the measurement used one, and threads still lost). With
threads dead, the **hybrid (C) has no thread regime worth keeping**. A **process pool
delivers 3.4–5.4×**, including ≈4× on the many-tiny-files overhead worst-case —
refuting the worry that IPC/pickling would erase the gain. → **Option A.** (Fork start
method on Linux means workers inherit cheaply; we use a per-process Scanner via the
pool initializer for portability + a clean libmagic cookie per worker.)

## 4. Design — determinism-preserving structure

### 4.1 Make per-file scanning pure (the load-bearing refactor)

`scan_file` (and its helpers) MUST stop mutating Scanner instance state. Instead the
per-file unit returns a pure result:

```
PerFileResult = (FileRecord, vector_contributions, counter_contributions)
```

where `counter_contributions` are this file's deltas to `_filename_patterns_*` /
`_reference_tokens_*`, and `vector_contributions` are the file-scoped vector
registrations (chatlog, reference_tokens, filename_patterns). The driver:

1. dispatches `scan_file` across the pool over `iter_files()`'s output;
2. collects `PerFileResult`s and **sorts them by `path`** (the single source of
   order — independent of completion order);
3. **folds** the counter/vector contributions into the aggregates **in sorted
   order**, then runs the corpus-scoped vectors over the sorted records.

Determinism becomes **structural**: the only order that touches output is the path
sort, which is identical for any worker count. This is also a clean improvement on
its own (pure functions, explicit data flow) independent of parallelism.

### 4.2 `--workers` is absent from the manifest

`ScannerConfig` gains `workers: int = 1`. The CLI gains `--workers N`. Neither is
serialized into the manifest or `ScanContext` (§2). `manifest_checksum` already
excludes only `scan_id`/`generated_at`; nothing new is excluded because nothing new
is added.

### 4.3 Failure isolation (never-crash carried into the pool)

A `scan_file` that raises already degrades to a `FileRecord` + `ErrorRecord`
in-band. Additionally, the **driver MUST tolerate a dead worker** (OOM, a segfault
in a C dependency on a hostile input): a worker that dies mid-file yields a
synthesized degraded `FileRecord` + `ErrorRecord` (a new `worker_failed` code) for
the in-flight path, and the pool continues. One pathological file MUST NOT abort the
scan — the exact v1.8.1 lesson, applied to the new IO/execution path.

### 4.4 Progress indicator (stderr only)

A periodic `… N / TOTAL files` line to **stderr**, shown when stderr is a TTY or
when `--progress` is passed; suppressed when stderr is not a TTY (so piped logs stay
clean) unless explicitly requested. It MUST NEVER touch stdout, the manifest, or any
checksummed value — it is determinism-safe by construction. Counts only; no
per-file content.

## 5. Schema & Version Constants

| Constant | v1.8.2 | v1.9.0 | Why |
|---|---|---|---|
| `SCANNER_VERSION` | 1.8.2 | **1.9.0** | New capability (CLI `--workers`, `--progress`) — a minor. |
| `LOGIC_VERSION` | 1.4.2 | **1.4.2 (unchanged)** | Output is byte-identical across worker counts. **An unchanged LOGIC is both the design goal and the falsifiable claim** (§6). |
| `SCHEMA_VERSION` | 1.7 | **1.7 (unchanged)** | Manifest shape unchanged; `--workers` is not recorded. |

No vector `method_version` changes. New optional error code `worker_failed`
(diagnostic; same class as `universal_read_failed`).

## 6. Validation Plan (measure the payoff first, then falsify-first)

1. **Measure before building — DONE (2026-06-05, `scratch/measure_workers.py`).**
   Timed the per-file pass (discovery + the serial aggregation tail excluded) at
   serial / thread-pool / process-pool, on an 8-core box, best of 2 trials. Thread
   mode used a per-thread Scanner (the shared libmagic cookie forced it); process mode
   used a per-process Scanner + `FileRecord` pickled back (that IPC cost is in the
   numbers):

   | Target | serial | thread (best) | **process (best)** |
   |---|---|---|---|
   | A parse-heavy (600 PDFs, specialists ON) | 1.64s | 1.65× @2 *(caps ~1.6×)* | **4.33× @4** |
   | B realistic default (3000 mixed, specialists off) | 12.24s | **0.62–0.77×** *(slower)* | **5.41× @8** |
   | C many-tiny (5000 tiny, specialists off) | 3.62s | **0.42–0.95×** *(slower, degrades)* | **3.96× @8** |

   **Conclusion:** threads are net-negative on the common cases (GIL + per-thread
   construction); the process pool gives **3.4–5.4×** and ≈4× even on the overhead
   worst-case → **build (not defer), Option A** (§3). **Honest bounds:** (a) these
   measure the *parallelizable per-file pass only* — end-to-end is Amdahl-bounded by
   the serial discovery + aggregation + manifest-serialization tail, so real-world is
   *less* (estimate ~2.5–4×); (b) memory scales ~N× the per-file footprint (PDFs read
   whole, capped 64 MB) → up to ~0.5 GB transient at `--workers 8` (document it).
2. **Falsify-first determinism unit test (write it failing first).** Scan a fixture
   tree at `--workers` 1/2/4/8 and assert **identical `manifest_checksum`** (and a
   field-level diff on `files[]`/aggregates). This is the contract; it MUST pass for
   every worker count.
3. **Empirical sweep — workers-equality as a Layer-A invariant.** Extend
   `corpus_sweep.py` to scan the real corpus at `--workers 1` and `--workers N` and
   assert **byte-identical** manifests (no baseline needed — divergence is *always*
   real). This is the killer gate: it runs against ~18k real files, not fixtures.
4. **Never-crash under parallelism.** A red-team file that kills a worker (OOM,
   decompression bomb already capped, a C-dep segfault) MUST yield a degraded record,
   not a dead scan (§4.3) — a `tests/` repro.
5. **All four review legs** (in-house swarm + Gemini cross-model + the extended sweep
   + PR bots), per `decorrelated-code-review`. The swarm angle that matters most:
   "find an order-dependence that survives the path sort."

2. **Default cap** — **RESOLVED: default `--workers 1`** (opt-in only; no existing
